# Run installer-gui

Paths below are relative to the repo root (`<repo>/`), not to this skill
directory.

This project's real deliverable, `installer_core.py`, is itself a
`--noconsole` PyInstaller GUI (a pywebview window loading `ui/index.html`).
`webview.start()` blocks, and the app reads its config via
`get_resource_path()`, which falls back to the current working directory
when not frozen (`sys._MEIPASS` absent) — so running it directly means
placing a fake `installer_config.json` + `app_contents/` next to
`installer_core.py` in the repo root first.

**Driver: `.claude/skills/run-installer-gui/driver.py`** (stdlib +
`ctypes` only — no pywin32/Pillow dependency; Pillow is only used below to
convert the driver's `.bmp` output to `.png` for viewing, not by the
driver itself).

## Run (agent path)

```bash
# 1. Create a fake installer_config.json + app_contents/ in the repo root
python .claude/skills/run-installer-gui/driver.py setup --app-name "TestApp"
# ...or to test the password-protection gate specifically:
python .claude/skills/run-installer-gui/driver.py setup --password-protected --password test1234 --app-name "TestApp"

# 2. Launch in the background (webview.start() blocks)
python .claude/skills/run-installer-gui/driver.py launch --entry installer_core.py

# 3. Wait ~3s for the window, then screenshot it (PrintWindow — works even
#    occluded, does not require the window to be foregrounded, and does
#    NOT capture the rest of the screen the way a full-desktop screenshot
#    tool would). Use a plain Windows-style path (e.g. under
#    C:\Users\<you>\AppData\Local\Temp), not /tmp/... — this environment's
#    Bash-to-Windows path translation is inconsistent between the driver's
#    own argv handling and a follow-up plain `python -c`, and /tmp/foo.bmp
#    silently resolves to two different files across the two calls.
python .claude/skills/run-installer-gui/driver.py screenshot --out "C:\Users\<you>\AppData\Local\Temp\shot.bmp"

# 4. .bmp -> .png to view with the Read tool (same explicit path both times)
python -c "from PIL import Image; Image.open(r'C:\Users\<you>\AppData\Local\Temp\shot.bmp').save(r'C:\Users\<you>\AppData\Local\Temp\shot.png')"

# 5. Clean up
python .claude/skills/run-installer-gui/driver.py stop
python .claude/skills/run-installer-gui/driver.py teardown
```

Then use the `Read` tool on the `.png` to actually look at it. A blank or
unchanged frame means the launch failed silently — check `tasklist` for a
lingering `python.exe` and that `setup` ran first.

### Optional: keyboard focus / accessibility checks

```bash
python .claude/skills/run-installer-gui/driver.py send-keys --key TAB --count 2
python .claude/skills/run-installer-gui/driver.py screenshot --out /tmp/tab.bmp
```

`send-keys` briefly steals foreground focus (required — Windows only
routes keyboard input to the foreground window) and sends a real
`SendInput` keystroke. **This is best-effort, not verified reliable** —
see Gotchas.

### Testing `uninstall.py` instead

`--entry uninstall.py` launches the uninstaller GUI instead. It reads the
same `installer_config.json` plus an `install_manifest.json` (not
generated by `setup` — write one by hand if you need this path); the
window title differs (check `uninstall.py`'s `webview.create_window(title=...)`
call for the current string before using `--title` on `screenshot`/
`send-keys`).

## Gotchas

- **Use explicit Windows-style paths for screenshot output, not `/tmp/...`.**
  In this environment, `/tmp/shot.bmp` passed to the driver's `--out` and
  the same literal string passed to a follow-up plain `python -c` do not
  reliably resolve to the same file (Bash-to-Windows path translation
  differs between argv-consumed-by-a-script and a bare Python call). The
  driver silently wrote to `C:\Users\...\AppData\Local\Temp\shot.bmp`
  while the conversion step looked for `/tmp/shot.bmp` and got
  `FileNotFoundError`. Always use one consistent, explicit
  `C:\Users\<you>\AppData\Local\Temp\...` path across every step.
- **DPI awareness is declared at import time — do not remove it.** Without
  it, `GetWindowRect()` returns the *scaled logical* size, not physical
  pixels: on a 150%-scaled display a 600x420 window is reported as
  586x382, and the screenshot comes out narrower than the window with the
  right-hand content cut off. That symptom is actively misleading — it
  looks exactly like a layout overflow with truncated text, which is one
  of the things CLAUDE.md asks you to check screenshots *for*. It did
  mislead once (verifying the MSIX destination label), and was only caught
  by re-capturing with awareness declared. `driver.py` now calls
  `SetProcessDpiAwareness` before touching user32; the call must stay
  *before* any window API, otherwise Windows has already classified the
  process as DPI-unaware.

- **BMP height sign must match between the in-memory `GetDIBits` call and
  the on-disk header.** The first version of this driver used
  `biHeight = -h` (top-down) for the `GetDIBits` call but wrote a
  *positive* height into the file's `BITMAPINFOHEADER` — every screenshot
  came out flipped both vertically and horizontally (equivalent to a
  180° rotation), while still clearly being a real capture of the window
  (readable-but-mirrored text). Fixed by using a positive height (bottom-up,
  BMP's native row order) consistently in both places. If screenshots ever
  look rotated 180° again, check this first.
- **`send-keys` (`SendInput` after `SetForegroundWindow`) did not
  reliably move focus inside the WebView2 content in this session** — two
  `TAB` sends were confirmed by real Win32 `SendInput` calls (no errors),
  but the follow-up screenshot still showed the password input focused,
  not the button. Top-level window foreground focus apparently doesn't
  guarantee the embedded WebView2 child control receives the synthetic
  keystrokes. **Static screenshots (no `send-keys`) are the verified-reliable
  path.** If you need to confirm keyboard-driven behavior (e.g. focus
  rings), either ask the user to check on their own machine, or try
  clicking into the WebView2 content first (not yet implemented in this
  driver) before sending `TAB`.
- **A leftover process from a previous test run blocks the next launch
  silently.** `installer_core.py` takes a single-instance mutex
  (`_acquire_single_instance_lock`); if a prior driver session's process
  is still alive, the new one shows a "already running" `MessageBoxW` (a
  *different* top-level window, not titled `安裝應用程式`) and exits —
  `screenshot`/`send-keys` will then report "window not found" even
  though a `python.exe` is running. Always run `stop` (or check
  `tasklist | findstr python`) before a fresh `launch`.
- **`setup --password-protected` requires `install_encryption.py`**
  (this repo's own module — imported directly, not installed separately)
  to build `app_contents.enc`; it derives its key with PBKDF2 at 600,000
  iterations, so `setup` takes a noticeable fraction of a second longer
  than the non-protected path. Not a bug, just don't be surprised.
- **`teardown` only removes what `setup` creates** (`installer_config.json`,
  `app_contents/`, `app_contents.enc`, `_driver_scratch_app/`). It does not
  touch `install_manifest.json` or other files you create by hand for
  `uninstall.py` testing — remove those yourself.
- **Screenshots are intentionally scoped to the one window** (`PrintWindow`
  targeting a specific `HWND`), not a full-desktop capture. A full-screen
  `CopyFromScreen`-style capture was tried earlier in this project's
  history and repeatedly picked up unrelated content elsewhere on the
  developer's screen — don't reintroduce that approach.

## Troubleshooting

| Symptom | Fix |
|---|---|
| `screenshot`/`send-keys` says "window titled … not found" | Run `setup` then `launch` first; if you just ran `launch` and it still fails, check for a stale instance (`stop`, then re-`launch`) — see Gotchas. |
| Screenshot is a small gray/blank rectangle | Window hadn't finished rendering yet — increase the sleep between `launch` and `screenshot` (3s was reliable in this session; slower machines may need more). |
| Screenshot looks rotated 180° / mirrored | The BMP height-sign bug described in Gotchas — if you've modified `driver.py`'s `cmd_screenshot`, check `biHeight` is positive and consistent in both the `GetDIBits` call and the file header. |
| `ModuleNotFoundError: No module named 'install_encryption'` from `setup --password-protected` | Run the driver with cwd at the repo root (the script inserts `REPO_ROOT` onto `sys.path`, but only if `REPO_ROOT` was computed correctly — confirm you didn't move `driver.py` out of `.claude/skills/run-installer-gui/`, which is how `REPO_ROOT` is derived). |
