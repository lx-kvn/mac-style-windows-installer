## 重現方式

在繁體中文 Windows 11（系統地區編碼為 cp950）上執行：

```
python builder_cli.py pack --config <設定檔>
```

打包過程中主控台會出現以下訊息，但打包本身回報成功：

```
Exception in thread Thread-1 (_readerthread):
Traceback (most recent call last):
  File "...\Lib\subprocess.py", line 1615, in _readerthread
    buffer.append(fh.read())
UnicodeDecodeError: 'cp950' codec can't decode byte 0x88 in position 270:
illegal multibyte sequence
```

同一台機器上以最小案例確認過：子行程輸出含有無法以 cp950 解碼的位元組時，
`subprocess.run(..., capture_output=True, text=True)` 的 `returncode` 仍然
正確，`stdout` 卻是 `None`。

## 機制分析

`subprocess` 的 `text=True` 若未同時指定 `encoding`，會依系統地區編碼解碼
子行程輸出。該編碼無法解碼的位元組會使解碼作業失敗，而失敗的形態取決於
讀取管線的方式，共有三種，嚴重程度不同：

1. **`capture_output=True`（背景讀取執行緒）**——例外發生在 `subprocess`
   自己建立的讀取執行緒裡，不會傳到呼叫端。呼叫端拿到的 `returncode` 正確，
   但 `stdout` 與 `stderr` 是 `None`。程式繼續往下跑，輸出整段消失且沒有任何
   回傳值上的跡象。這是最難察覺的一種：命令成功時完全看不出異狀，只有在
   命令失敗、需要那段輸出說明原因時才顯露——而那正是最需要它的時候。
2. **`check_output`（呼叫端同步讀取）**——例外在呼叫端當場拋出。這個專案裡
   四個 `check_output` 呼叫端外層都有 `except` 把例外轉成一個「否定」的回傳值
   （沒有在執行／不是 explorer.exe），因此症狀是偵測邏輯靜默失效，而不是報錯。
3. **逐行讀取 `Popen.stdout`**——例外在主流程當場拋出，中斷整個打包，錯誤
   訊息指向解碼而非真正的失敗原因。

三者的共同點是「輸出被丟棄」，差別只在丟棄之後的表現。

## 方案評估

**方案一：改用 `bytes` 模式，呼叫端自行解碼。** 可行但侵入性最大——每個
呼叫端都要自己處理解碼與換行，且逐行讀取的呼叫端要重寫迭代邏輯。不採用。

**方案二：只加 `errors="replace"`，維持依系統地區編碼解碼。** 保證任何位元組
組合都不會讓讀取失敗，無法解碼的位元組換成替代字元。對輸出以主控台編碼呈現的
子行程（Windows 內建命令、使用者自備的批次檔）而言，非 ASCII 內容仍然正確。

**方案三：指定 `encoding="utf-8"` 並加上 `errors="replace"`。** 對本身以
UTF-8 輸出的子行程（Python 程式）是正確的解碼方式；對以主控台編碼輸出的
子行程則會把非 ASCII 內容換成替代字元。

最終採用「依子行程性質二選一」：子行程是 Python 程式時用方案三，其餘用
方案二。判斷依據是實際觀察到無法解碼的位元組來自 UTF-8 編碼的內容，而該
子行程（PyInstaller）正是 Python 程式。

兩個方案都保證「不再有輸出被丟棄」，差別只在非 ASCII 內容的還原度；ASCII
骨幹（錯誤代碼、模組名稱、英文訊息、要比對的執行檔檔名）在兩者之下都完整
保留，因此選錯的代價有限，不需要為此引入更複雜的機制（例如先以 UTF-8 嘗試、
失敗再退回地區編碼）。

## 實際做了什麼

十三個呼叫端全部補上解碼參數：

| 檔案 | 子行程 | 採用 |
|---|---|---|
| `builder.py`（三處，共用 `SUBPROCESS_TEXT_KWARGS`） | signtool、PyInstaller ×2 | UTF-8 + replace |
| `build_config_tool.py` 逐行讀取 | PyInstaller | UTF-8 + replace |
| `packaging_core.py` 環境探測 | python 直譯器 | UTF-8 + replace |
| `build_config_tool.py` 執行中偵測 | tasklist | replace |
| `installer_core.py` 執行中偵測 | tasklist | replace |
| `uninstall.py` 執行中偵測 | tasklist | replace |
| `explorer_lock_release.py` 反查執行檔名 | tasklist | replace |
| `installer_core.py` 安裝腳本 | 使用者自備的腳本 | replace |
| `msix_package.py` 工具呼叫 | makeappx／makepri／signtool | replace |
| `windows_service.py` 狀態查詢 | sc.exe | replace |
| `tools/vms.py` 指令轉呼叫 | vmrun | replace |

`builder.py` 的三處抽成 `SUBPROCESS_TEXT_KWARGS` 常數，讓解碼方式在該檔案裡
只有一個定義處；其餘檔案各自只有一到兩處，在呼叫端直接標示並附上該處失效時
的實際後果。

`builder.py` 的 signtool 呼叫沿用該檔案共用的 UTF-8 設定，未單獨改成地區
編碼——Windows SDK 工具的訊息是英文，兩種解碼方式的結果相同，為此把常數
拆成兩份不會換到任何實質差異。

## 驗收

測試共用的解碼探針放在 `tests/_fakes.py`（`decode_probe_script()` 與三個
`decode_probe_*` 轉呼叫工廠）。作法是真的起一個子行程，讓它輸出指定內容加上
`b"\x81\x8d"`——這兩個位元組在 cp950、cp1252 與 UTF-8 底下都無法解碼，因此
測試結果不隨執行機器的地區設定改變——再檢查受測函式最後拿到什麼。

驗證的是「輸出有沒有被完整取回」，不是實作傳了哪些參數。後者只是覆述實作
自己寫下的常數，實作改錯時測試會跟著改錯，起不到驗證作用。

每個呼叫端各有一個測試，斷言的是該處失效時真正會壞掉的行為：偵測結果是否
正確、錯誤訊息裡有沒有子行程實際印出的內容、逐行輸出有沒有進到記錄。十三個
測試在修正前全部失敗、修正後全部通過；全套測試 1327 項通過。

## 已知限制

- 子行程若以主控台編碼輸出非 ASCII 文字，採用 UTF-8 解碼的三類呼叫端會把
  那段文字換成替代字元；反之亦然。這是「一個呼叫端只能選一種編碼」的必然
  結果，不是可以同時滿足的兩件事。
- `errors="replace"` 只保證讀取不失敗，不保證還原內容。真正需要位元組層級
  精確度的用途（例如把子行程輸出原封不動寫進檔案）不適用這個作法。
- Windows 主控台程式輸出使用的是 OEM 編碼，而 `text=True` 未指定 `encoding`
  時採用的是 ANSI 編碼。繁體中文環境下兩者都是 950，因此一致；在兩者不同的
  語系（例如俄文的 ANSI 1251 與 OEM 866）底下，採用 `replace` 的呼叫端會把
  非 ASCII 內容換成替代字元。這個專案的驗證環境沒有這類語系。
