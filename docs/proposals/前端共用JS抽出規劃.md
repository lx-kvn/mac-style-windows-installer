# 前端共用 JS 抽出規劃

**狀態：已勘查，尚未實作。這份文件記錄發現與作法評估，不含任何程式碼變更。**

勘查基準：`0.14.1` 之後、跨模組一致性稽核五輪修正完成的工作樹（測試 806 項
全數通過）。

## 動機

`ui/index.html`（安裝端）、`ui/uninstall.html`（解除安裝端）、
`ui/config.html`（打包工具）三份畫面各自內嵌一段 `<script>`，其中有四個
函式在三份檔案裡各有一份複本，而且**已經彼此不同步**：

| 函式 | 職責 | index↔uninstall | index↔config | index 版行數 |
|---|---|---|---|---|
| `t` | 取翻譯字串（含 `{{變數}}` 代換） | 94% | 94% | 7 |
| `applyI18n` | 把翻譯套用到帶 `data-i18n` 的元素 | 84% | 51% | 7 |
| `setupCustomDrag` | 無邊框視窗的自訂拖曳 | 89% | 85% | 35 |
| `dragLoop` | 拖曳的每幀位移計算 | 87% | 84% | 30 |

（相似度為 `difflib.SequenceMatcher` 對函式本體原文的比對結果。）

相似度不是 100% 代表這幾份複本各自被改過。`applyI18n` 只剩 51% 相似最明顯
——三份畫面對「翻譯要怎麼套到元素上」已經是三套不同的實作。

這正是這個專案在 Python 端反覆處理過的同一種形態，且**視窗拖曳這一項在
Python 端早就收斂完成**：`window_drag.py` 的模組說明記載
「`ConfigAPI`（製作工具視窗）跟 `InstallerAPI`（安裝端視窗）共用同一份
實作」。後端共用了，前端呼叫它的那一段卻仍是三份各寫各的——收斂只做了
一半。

`CONTEXT.md` 對 `file_assoc.py` 記載的理由同樣適用於這裡：「修過幾輪 bug
之後，這個『兩邊手動對齊』的協定已經漏改過，所以收斂成這一份共用實作」。

## 勘查範圍與方法

以正規表示式取出三份 HTML 的 `<script>` 區塊，比對其中最上層 `function`
宣告的名稱集合與函式本體，找出重複定義；再沿著打包流程確認「新增一份共用
`.js` 檔案」在現有機制下會發生什麼事。

各檔案的 JavaScript 份量：

| 檔案 | 總行數 | `<script>` 內行數 | 獨有函式數 |
|---|---|---|---|
| `ui/index.html` | 1233 | 795 | 37 |
| `ui/uninstall.html` | 683 | 369 | 15 |
| `ui/config.html` | 1738 | 1323 | 未計（打包工具自己的表單邏輯，不在共用範圍） |

## 發現清單

### F01：新增的共用 `.js` 檔案會落進「只在缺少時才補」的分支

`packaging_core.ensure_workspace_files()` 複製 `ui/` 內容到工作目錄時，
依**檔名白名單**決定覆蓋策略：

```python
if name in ("index.html", "uninstall.html"):
    shutil.copy2(src, dest)          # 實作檔案，一律覆蓋
elif not os.path.exists(dest):
    shutil.copy2(src, dest)          # 其他靜態資源，只在缺少時才補
```

新增的共用 `.js` 會落進第二個分支。這代表**重複使用同一個工作目錄的
使用者，工作目錄裡卡著的舊版 `.js` 永遠不會被換掉**——不管重新編譯幾次
新的打包工具，實際被拿去打包的都還是最早那次留下的過期程式碼，而且沒有
任何錯誤訊息。

這正是該函式說明文字裡以「【重要】」標記、已經修過一次的同一個缺陷，只是
換一道門重新出現。根因不是那次修正沒做完，而是**修正的形式是一份寫死的
檔名白名單**——白名單天生無法涵蓋之後新增的檔案。

### F02：新檔案要手動登記在兩份清單裡，且沒有任何測試會抓漏

新增一份 `ui/*.js` 需要同步更新：

1. `build_config_tool._REQUIRED_FILES`——編譯打包工具 exe 前的存在性檢查，
   目前逐項列出 `ui/config.html`／`ui/index.html`／`ui/uninstall.html`。
2. `packaging_core.ensure_workspace_files()` 的覆蓋白名單（見 F01）。

`--add-data=ui;ui` 是整個資料夾一起帶，不需要改動。

`tests/test_shared_module_packaging.py` 用 `ast` 解析 `installer_core.py`／
`uninstall.py` 的 import、反推應該被打包的**Python 模組**，藉此自動抓出
漏登記的模組。這個機制**不涵蓋 `ui/` 底下的資源**，所以上面兩份清單漏改
不會有任何測試轉紅——跟該測試檔案開頭描述的、當初導致
`ModuleNotFoundError` 的情境完全相同，只是對象換成前端資源。

### F03：三份畫面的載入時機不同，共用檔案不能假設同一種初始化方式

- `ui/index.html`／`ui/uninstall.html`：由 `webview.create_window()` 載入，
  等 `pywebviewready` 事件後才能呼叫 `pywebview.api.*`。
- `ui/config.html`：同樣是 `pywebviewready`，但它額外有
  `initLanguage()`／`checkEnvironmentOnLoad()`／`initWorkspaceDir()` 一串
  非同步初始化，且語言偏好存在 `localStorage`（另外兩份沒有這段）。

`applyI18n` 相似度只有 51% 多半源自這個差異。抽共用時要先確認「哪些是
真正共用的行為、哪些是各畫面自己的初始化順序」，不能把差異一起併掉。

## 作法評估

### 方案一：抽成 `ui/shared.js`，三份 HTML 以 `<script src>` 載入

最直觀，但要先解決 F01／F02，否則會製造一個比現況更難察覺的問題——現況是
「三份複本不同步」，看得到；漏覆蓋則是「舊檔案靜默生效」，看不到。

配套修正：

- `ensure_workspace_files()` 的覆蓋策略改成**依用途判斷而非依檔名**。例如
  把「實作檔案」與「使用者可自訂的靜態資源」拆成兩份明確的清單，或改成
  「除了已知的可自訂資源（目前是 `folder_icon.png`／`app_icon.png`／
  `trash_*.svg`）以外一律覆蓋」——後者是白名單反轉，新增實作檔案時不需要
  記得更新任何清單，跟這個專案偏好的「新增時不用記得同步」方向一致。
- 為 `ui/` 資源補上類似 `test_shared_module_packaging.py` 的自動比對：解析
  三份 HTML 實際 `<script src=>`／`<img src=>` 引用到的相對路徑，比對
  `build_config_tool._REQUIRED_FILES` 有沒有漏登記。

### 方案二：維持內嵌，改以建置期樣板拼接

在打包流程把共用片段插進三份 HTML。可以完全迴避 F01／F02（產物仍然只有
三個 HTML 檔案），但會讓「原始碼裡看到的 HTML」與「實際跑的 HTML」不一致，
增加除錯難度，也讓 `tests/test_ui_*.py` 這幾份靜態解析測試需要改成解析
拼接後的結果。**不建議**，記錄下來是為了說明為何不走這條路。

### 方案三：只收斂拖曳邏輯，翻譯機制暫不動

`setupCustomDrag`／`dragLoop` 三份相似度都在 84% 以上、職責單純、且後端
（`window_drag.py`）已經是共用的，收斂風險最低、收益明確。`t`／`applyI18n`
牽涉各畫面不同的初始化順序（F03），可以留到下一步。

適合作為第一刀，讓 F01／F02 的配套修正先在一個範圍較小的改動上驗證過。

## 建議順序

1. 先修 F01／F02 的機制問題（覆蓋策略與自動比對測試），這一步不搬動任何
   前端程式碼，可獨立驗證。
2. 依方案三收斂拖曳邏輯，確認整條打包流程在多了一個 `ui/*.js` 之後仍然
   正確（含重複使用同一個工作目錄的情境）。
3. 再處理 `t`／`applyI18n`，並先釐清 F03 列出的初始化差異。

## 已知限制

- 相似度數字以函式本體原文比對得出，反映的是文字差異而非語意差異；84% 相似
  也可能是行為完全等價、只有變數命名不同。實際收斂前仍需逐一閱讀三份實作，
  確認差異是「已經長歪」還是「各畫面真正需要的不同行為」。
- 本次勘查未實際嘗試新增 `.js` 檔案跑一次完整打包流程，F01 的實際表現
  （舊檔案靜默生效）是依 `ensure_workspace_files()` 的程式碼推論，動工時
  應先以「重複使用同一個工作目錄」的情境實機重現確認。
- 未評估 `ui/config.html` 那 1323 行打包工具自身的表單邏輯。它與另外兩份
  畫面的共用面只有上述四個函式，其餘不在這份規劃範圍內。
