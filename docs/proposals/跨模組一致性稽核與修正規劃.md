# 跨模組一致性稽核與修正規劃

**狀態：稽核已完成，修正尚未開始。這份文件記錄發現清單與分輪修正計畫，
不含任何程式碼變更。**

稽核基準：`v0.14.1`（`VERSION` 檔案內容），工作區乾淨，
`python -m unittest discover -s tests -p "test_*.py"` 全數通過（666 項）。

## 動機

上一輪架構稽核（2026-08-11，針對 `v0.13.0`）列出的缺陷已全數修正，本輪
重新以「跨模組一致性」為主軸重跑一次，目標不是找單一函式內部的錯誤，而是
找出「每個模組單獨看都合理、合起來卻互相矛盾或斷鏈」的地方。

這類問題有一個共同特徵：它們不會讓測試變紅，因為每一份測試都只驗證單一
模組自己的行為契約，而矛盾發生在契約與契約之間。本輪 15 項發現裡，有 9 項
是這種形態。

## 稽核範圍與方法

涵蓋打包端（`packaging_core.py`/`builder.py`/`builder_cli.py`/`gui_config.py`/
`ui/config.html`）、安裝端（`installer_core.py`/`ui/index.html` 與其依賴的
深模組）、解除安裝端（`uninstall.py`/`ui/uninstall.html`/`system_entries.py`）
三條流程，以及三者共用的設定結構（`installer_config.json` 欄位、
`install_manifest.json` 欄位）。

方法是沿著資料的流向逐段比對：同一個欄位在打包端被驗證成什麼樣、寫進設定
檔是什麼樣、安裝端讀出來怎麼用、解除安裝端從清單讀回來怎麼用，找出中間
任何一段語義改變或整段被丟棄的位置。

## 發現清單

編號 F01–F15 於下面的修正輪次規劃中引用。

### 「無聲失敗」群組

**F01：兩端後端回傳的警告清單，前端與靜默流程都沒有讀取。**

安裝端 `installer_core.py:1065` 在成功結果裡回傳 `warnings`（Windows 服務
建立失敗、排程工作建立失敗），`ui/index.html:1145` 的結果處理只判斷
`result.status === 'success'` 就顯示安裝成功畫面，`warnings` 未被讀取；
`run_silent_install()`（`installer_core.py:1360` 附近）同樣只寫入
`result.get("message")`，警告內容不進靜默安裝紀錄。

解除安裝端形態相同：`uninstall.py:645` 回傳 `{"status": "success",
"warnings": failures}`，`ui/uninstall.html:529` 與 `ui/uninstall.html:599`
兩個呼叫點都只判斷 status。

`uninstall.py:361-368` 的說明文字明確記載這個 `failures` 清單存在的理由是
「讓使用者不會在 PATH／捷徑／登錄表項目全部沒清乾淨的情況下，還是看到一個
解除安裝完成的畫面」。後端已收集完成，但沒有任何出口，該情境的實際行為
與修正前相同。

**F02：同一個函式內六個移除步驟，只有四個會被記錄為失敗。**

`_perform_uninstall_steps()`（`uninstall.py:381-433`）對登錄表項目、捷徑、
Windows 服務、排程工作四步都有 `failures.append()`，但檔案關聯
（`uninstall.py:408`）與 PATH（`uninstall.py:413`）兩步無條件記錄成功。

根因在被呼叫的兩個函式本身：`file_assoc.unregister()` 對每一次 `DeleteKey`
都 `try/except: pass` 且不回傳值；`system_entries.remove_from_path()` 整段
包在一個 `try/except: pass` 裡，同樣不回傳值。同一個 `system_entries.py`
裡的 `remove_registry_entry()`／`remove_shortcut()` 則都回傳布林值，模組內
的回傳值契約本身不一致。

**F03：檔案刪除失敗時，回報給使用者的訊息與事實相反。**

`uninstall.py:474` 對刪除失敗的檔案只寫入警告紀錄，不併入 `failures`。
接著 `uninstall.py:495` 依「安裝目錄裡還剩什麼」判斷能否整個移除資料夾，
剩餘項目一律描述為「可能是使用者自行產生的資料」——但剛才刪除失敗的檔案
正好也會出現在這份剩餘清單裡，使用者看到的訊息與實際原因相反。

同一段的剩餘項目檢查只涵蓋安裝目錄（`current_dir`），
`local_appdata_dir` 底下刪剩什麼完全沒有對應檢查。

**F04（本輪新增，與 F01 有執行順序相依）：移除函式把「本來就不存在」
與「移除失敗」回報成同一個值。**

`system_entries.remove_shortcut()` 在捷徑檔案不存在時走到函式結尾回傳
`False`；`remove_registry_entry()` 在兩個 hive 都找不到目標機碼時，兩次
`DeleteKey` 都拋 `FileNotFoundError`，同樣回傳 `False`。

目前這個語義沒有造成可見問題，是因為 F01 讓 `failures` 沒有出口。一旦
F01 修好、警告真的顯示到畫面上，使用者手動刪過捷徑、或安裝時捷徑建立
本來就失敗過（`_create_shortcut()` 的失敗是可忽略的設計）這些正常情境，
都會變成解除安裝結束時的假警告。

**因此 F04 必須與 F01 同一輪修正，且順序在 F01 之前**——只做前端接線會
讓假警告直接暴露給使用者，比現狀更糟。

**F05：安裝端「非致命失敗」的收集點不完整。**

`_trigger_installation_impl_inner()` 對 Windows 服務、排程工作建立失敗會
`warnings.append()`，但同樣性質、同樣不中止安裝的三種失敗只寫入紀錄檔：
安裝後置腳本執行失敗（`installer_core.py:1029`）、系統還原點建立失敗、
捷徑建立失敗。五種失敗的嚴重性相當，處理方式分成兩類。

### 「產出物未經驗證」群組

**F06：`sha256` 欄位在內嵌模式下完全不生效。**

打包端 `builder._download_file()`（`builder.py:56`）只有讀取與寫檔，沒有
Content-Length 完整性比對，也沒有 sha256 驗證；`builder.py:388-402` 的
內嵌迴圈直接呼叫它，`custom_dependencies` 裡的 `sha256` 未被傳入。

安裝端 `dependency_install.install()` 兩項驗證都有，但 sha256 檢查位於
「需要連線下載」的分支內（`dependency_install.py:394`），走內嵌路徑
（`dependency_install.py:339`）時整段跳過。

合併效果：使用者同時填寫 `sha256` 並勾選內嵌時，該檔案從打包到安裝沒有
任何一個環節驗證過。打包當下網路中斷會把一顆內容截斷的執行檔內嵌進
Setup.exe，之後每一位終端使用者都會執行它。

`builder.py:57-63` 的說明文字記載了「不與安裝端合併成同一份程式碼」的
理由（兩端呼叫情境與錯誤處理不同），這個理由成立，但兩端的驗證強度不應
因此產生落差。

**F07：主程式檔名含 shell 特殊字元時行程偵測會失效。**

`_is_process_running()`（`installer_core.py:107`）以 `shell=True` 搭配
字串拼接組出 `tasklist` 指令。Windows 檔名允許 `&` 等字元，打包端只驗證
`main_exe` 是否存在於來源資料夾，未限制字元。改為傳入參數陣列並移除
`shell=True` 即可，同一支檔案內其他 subprocess 呼叫已是這個寫法。

**F08：磁碟空間檢查只涵蓋一顆磁碟。**

`_required_size()`（`installer_core.py:412`）加總來源資料夾全部檔案，
`_check_disk_space()`（`installer_core.py:415`）只檢查 `selected_path`
所在磁碟。但 `local_appdata_files` 指定的檔案實際落在
`%LOCALAPPDATA%\Programs\<folder_name>`，可能位於另一顆磁碟——該磁碟從未
被檢查，而目標磁碟的需求量被高估。

覆蓋安裝時整份舊安裝資料夾會複製到 `%TEMP%`（`upgrade.backup()`）、密碼
保護的安裝會把解密內容展開到 `%TEMP%`，兩者都未計入空間需求。

### 「矛盾組合未被攔截」群組

**F09：「免管理員權限安裝」與「建立 Windows 服務／系統還原點」可同時設定。**

`no_admin_install` 開啟時 `builder.py:324` 不加入提權設定，整個安裝流程在
一般權限下執行。但 `sc.exe create` 與系統還原點建立都需要管理員權限，必定
失敗，且失敗只轉成 F01 描述的、沒有出口的警告。

`packaging_core.validate_and_build_pack_data()` 對欄位之間的矛盾是有在驗證
的（`dependencies_min_version` 與 `dependencies` 交叉比對、`doc_icons` 與
`file_associations` 交叉比對），本項是少數會在終端使用者機器上實際失敗、
卻沒有對應驗證的組合。GUI 端 `ui/config.html:1454` 由「安裝位置」三選一
推導 `no_admin_install`，服務設定欄位就在同一頁下方，無互斥提示。

**F10：版本號的合法定義，打包端與安裝端互相矛盾。**

`version_compare.py` 完整處理帶預發布後綴的版本（`has_prerelease_suffix()`
判定 `1.0.0-rc2` 比 `1.0.0` 舊），但打包端 `version_info._parse_version_tuple()`
（`version_info.py:21`）要求每一段都是純整數，`1.0.0-rc1` 會拋 `ValueError`
中止建置——這種版本號根本無法打包產出，安裝端的預發布比較邏輯永遠不會被
執行到。

附帶問題：`packaging_core.py:402` 對版本號只檢查非空字串，真正的格式檢查
發生在 `builder.py:240`，此時 `dist/`／`build/` 已於流程開頭被清空。純函式
`validate_and_build_pack_data()` 的設計目的正是在產生任何副作用之前攔截
設定錯誤，本項未走這條路徑。

**F11：部分設定欄位以未正規化的原始值進入設定檔。**

`packaging_core.py` 對 `windows_service`／`scheduled_task` 的驗證會先
`.strip()` 再檢查，但 `pack_data` 是由 `dict(data)` 整包複製而來，這幾個
欄位沒有像其他欄位那樣把正規化後的值寫回。結果是 `start_type` 填成
`"auto "` 能通過驗證，實際傳給 `sc.exe` 時失敗。

### 「一致性補完」群組

**F12：「manifest 可能不可信」的處理只套用在四個移除點的其中一個。**

`system_entries.remove_registry_entry()` 會依序嘗試兩個登錄表 hive，說明
文字記載的理由是 manifest 裡的 `no_admin_install` 可能與當初實際安裝時
不符（欄位遺失時回退成 `False`、或 manifest 被手動編輯）。

同一個理由完全適用於捷徑位置、PATH 所在 hive、檔案關聯所在 hive，但
`remove_shortcut()`、`remove_from_path()`、`file_assoc.unregister()` 三者
都只認 manifest 推導出的單一位置。

**F13：兩個同為預發布的版本之間無法區分先後。**

`version_compare.compare_versions()`（`version_compare.py:41`）在數字段相同
且兩邊都有後綴時回傳 0，`1.0.0-rc1` 升級到 `1.0.0-rc2` 會被判定為「版本
完全一致」的重新安裝。目前因 F10 無法產生這種版本號而踩不到，放寬版本號
格式後會立即浮現。

### 「文件與現況脫節、冗餘」群組

**F14：安裝密碼保護在 GUI 沒有對應欄位，且文件記載為未實作。**

`install_password_env` 在 CLI、打包驗證、`builder.py` 加密、安裝端密碼關卡、
靜默安裝 `/PASSWORD=` 參數、`CLI_USAGE.md` 皆已完成，只有 `ui/config.html`
沒有對應輸入欄位，GUI 使用者無法使用這個功能。

`CONTEXT.md:238` 該節首行仍記載「設計階段，尚未實作」，與現況不符。

**F15：冗餘與死碼。**

- `builder.py:199` 寫入設定檔的 `display_name` 欄位，全專案沒有任何讀取點。
- `installer_core.py` 檔案複製之前有三處 `_restore_upgrade_backup()` 呼叫，
  三處都位於「移除舊版本」步驟之前，此時備份尚未建立，必為空操作。
- 覆蓋安裝流程中登錄表被查詢三次：前端一次、`installer_core.py:829` 一次、
  `upgrade.run()` 內部再一次。三次之間狀態可能改變。

## 修正輪次規劃

分輪依據是「使用者實際受到的傷害」優先於「程式碼整潔度」，同時讓同一輪
內的項目共用同一組測試與同一次 GUI 驗證，減少重複的驗證成本。

每一輪都適用 `CLAUDE.md` 既有規範：先寫測試並確認測試如預期失敗，再寫
實作讓它轉綠；包裝外部契約（`sc.exe`／`schtasks.exe`／Win32 列舉值）的
測試，斷言對象是外部規格本身，不是模組自己的常數。

### 第一輪：讓失敗不再無聲

**涵蓋 F04 → F01 → F02 → F03 → F05，順序不可調換。**

這是唯一一輪有內部順序約束的：F04 若不先修，F01 完成後會把假警告直接推到
使用者眼前。

1. **F04**：把 `remove_shortcut()`／`remove_registry_entry()` 的回傳語義
   從「有沒有刪到東西」改成「結束後目標是否確實不存在」——目標本來就不存在
   視為成功，只有實際移除失敗才回傳 `False`。`DeleteKey` 需區分
   `FileNotFoundError`（視為成功）與其他例外（視為失敗）。
2. **F02**：`file_assoc.unregister()` 與 `system_entries.remove_from_path()`
   改為回傳布林值，語義與上一項一致。`remove_from_path()` 的登錄表寫入成功
   即算成功，環境變數變更廣播失敗不影響回傳值（該廣播已於既有修正中定性為
   best-effort）。
3. **F03**：檔案刪除失敗併入 `failures`；剩餘項目訊息依「是否為刪除失敗的
   檔案」分成兩種措辭；`local_appdata_dir` 補上對應的剩餘項目檢查。
4. **F01**：`_perform_uninstall_steps()` 六個步驟全部接上 `failures`；
   安裝端與解除安裝端的前端在成功畫面顯示警告清單；靜默安裝與靜默解除
   安裝把警告寫進既有的紀錄檔。
5. **F05**：安裝後置腳本、系統還原點、捷徑建立三種非致命失敗併入
   `warnings`，與服務／排程工作採同一處理方式。

**驗證**：新增測試涵蓋「目標本來就不存在」與「移除確實失敗」兩種情境，
確認前者不進 `failures`、後者會進。前端變更依 `CLAUDE.md` 的 UI 檢查清單
處理，並以 `.claude/skills/run-installer-gui` 實際截圖確認警告區塊在最窄
視窗寬度下不會截斷文字。

**風險**：F04 改變兩個既有函式的回傳語義，現有測試若斷言「不存在時回傳
False」會轉紅。這種轉紅是預期的契約修正，需逐一檢視測試意圖後更新，不是
把測試改到能通過為止。

### 第二輪：不讓使用者拿到未經驗證的產出物

**涵蓋 F06、F07、F08。**

1. **F06**：`builder._download_file()` 加入 Content-Length 比對，並新增
   選填的預期 sha256 參數；內嵌迴圈把該相依元件設定裡的 `sha256` 傳入。
   安裝端把 sha256 驗證從下載分支移到兩條路徑的共同位置，內嵌檔案同樣
   驗證（成本極低，且能涵蓋打包後檔案被替換的情況）。
2. **F07**：`_is_process_running()` 改為參數陣列形式並移除 `shell=True`。
3. **F08**：磁碟空間檢查改為依「落地磁碟」分組計算需求量，逐一檢查；
   `%TEMP%` 的需求（覆蓋安裝備份、密碼保護解密內容）併入評估。

**驗證**：F06 的測試以「下載內容短少」「sha256 不符」兩種情境驗證打包
流程確實中止；F07 以含 `&` 的檔名驗證指令組成正確；F08 以「兩顆磁碟」的
情境驗證兩邊都被檢查。

**風險**：F08 改變 `disk_space.check_disk_space()` 的介面形狀，呼叫端只有
`installer_core.py` 一處，範圍可控。

### 第三輪：把矛盾攔截在打包階段

**涵蓋 F09、F10、F11。**

1. **F09**：`validate_and_build_pack_data()` 新增交叉驗證——`no_admin_install`
   為真時，設定了 Windows 服務或系統還原點一律回傳明確的中文錯誤訊息，
   說明這兩項需要管理員權限、與免權限安裝互斥。GUI 端在「安裝位置」切換時
   同步停用或提示對應區塊。
2. **F10**：版本號格式驗證前移到 `validate_and_build_pack_data()`，在任何
   副作用發生前回報。**先決定案已於 2026-08-29 拍板：支援帶預發布後綴的
   版本號。** 作法是 Win32 VERSIONINFO 的數值欄位（`filevers`／`prodvers`）
   只取數字段，字串欄位（`FileVersion`／`ProductVersion`）保留原始文字
   ——該格式本來就允許任意字串。採用這個作法會讓 `version_compare.py`
   既有的預發布比較邏輯真正生效。決定與理由記錄於
   `docs/adr/0003-allow-prerelease-suffix-in-version-string.md`，F13 因此
   為必做項（見第四輪）。
3. **F11**：`windows_service`／`scheduled_task` 驗證後的正規化值寫回
   `pack_data`，與其他欄位一致。

**驗證**：三項都落在純函式 `validate_and_build_pack_data()` 上，可直接
單元測試，不需啟動建置流程。

**風險**：F10 若決定支援預發布後綴，會連動第四輪的 F13，兩者需一併考量。

### 第四輪：一致性補完
