## 動機

現在的安裝檔本體是 PyInstaller 打包的一顆自訂 exe（`Setup_XXX.exe`），
所有落地檔案、寫登錄表、解除安裝清理都是這個工具自己動手做（見
`installer_core.py`/`uninstall.py`）。這個做法彈性最大，但解除安裝乾不
乾淨完全取決於這個工具自己有沒有把每一筆寫入都記進
`install_manifest.json`——理論上只要漏記一筆，就會殘留。

MSIX 是 Windows 目前唯一「保證乾淨解除安裝」的原生機制：整個安裝改由
系統的容器化套件引擎接管，所有寫入都在系統層級被追蹤，解除安裝時系統
自己保證清空，不依賴應用程式自己記清單記得夠不夠完整。這份文件研究
「如果要讓輸出格式支援 MSIX，可以怎麼做、要付出什麼代價」。

## 兩條路線

### 路線 A：純原生 MSIX

使用者對 `.msix`/`.msixbundle` 按兩下（或走安裝網址協定），交給系統內建
的 **App Installer** 處理整個安裝流程。

**代價**：安裝畫面完全由 Windows 自己畫（Publisher/版本/「安裝」按鈕的
制式對話框），開發者沒有任何客製化空間——**不能保留現在這套「把圖示拖進
資料夾」的拖拽介面**，也沒有 EULA 頁面可以放。MSIX 的容器沙盒模型還會
擋掉現在好幾個既有功能：

- `pre_install_script`/`post_install_script`（沙盒內不能任意執行外部腳本）
- `custom_install_dir`（自訂安裝路徑，MSIX 應用只能裝在系統管理的套件目錄）
- `--uac-admin`/相依元件靜默安裝（沙盒內沒有提權這回事，`bundle_dependencies`
  現在會執行外部安裝程式，這在 MSIX 容器內基本上做不到）
- `no_admin_install`/`local_appdata_files` 這類「跨 hive 選安裝位置」的
  彈性設計，在 MSIX 裡沒有意義（套件位置由系統決定）

**第二輪修正——上面這份清單過度悲觀，其中數項並未被擋掉。** 經重新查證，
現有功能在 MSIX 下分為三類，完整分類與處置見下方「第二輪定案決議」第
七、八項。此處先更正本節的具體錯誤：

- **`no_admin_install` 並未被擋掉，且方向相反**——MSIX 套件預設即安裝給
  當前使用者、不要求提權。這不是被移除的功能，而是變成該模式的預設行為。
- **檔案關聯並未被擋掉**——MSIX 原生支援，改為在套件清單中宣告，不再由
  本專案自行寫入登錄表。
- **`add_to_path` 並未被擋掉**——MSIX 有對應機制，效果相同。
- **安裝前建立系統還原點並未被擋掉**——執行該動作的是 bootstrapper exe
  本身，它是一般程式、不在套件沙盒內，於交付系統部署之前執行不受限制。
- **`bundle_dependencies` 的需求大部分消失而非被擋掉**——MSIX 的做法是
  將所需的執行階段檔案直接包入套件，不再執行第三方安裝程式。

真正屬於「格式本身不允許、無替代方案」的只有三項：`custom_install_dir`、
`pre_install_script`/`post_install_script`、以及內嵌第三方安裝程式靜默
執行。前述其餘項目屬於「可對應但需另行設計」或「本來就沒問題」。

### 路線 B：混合式 bootstrapper

打包出來的東西表面上還是一顆 exe（跟現在一樣的 bootstrapper 性質），但
內嵌的不是「app 本體檔案 + `installer_core.py` 邏輯」，而是一份
`.msix`/`.msixbundle` 檔案本身——概念上跟現在用 `--add-data` 把
`uninstall.exe`/`app_contents` 塞進 exe 資源裡是同一招，只是這次塞進去
的是整包 MSIX。

exe 執行時的工作從「自己動手複製檔案、寫登錄表」變成：把內嵌的 `.msix`
解壓到暫存路徑 → 呼叫 Windows 的部署 API
（`Windows.Management.Deployment.PackageManager.AddPackageAsync`）讓系統
自己把這包 MSIX 裝進去。真正落地檔案這件事完全交給 OS 的套件引擎，
「保證乾淨解除安裝」這個特性也是從這裡來的。

**進度條可以保留**：`AddPackageAsync` 回傳的是
`IAsyncOperationWithProgress<DeploymentResult, DeploymentProgress>`，
`DeploymentProgress.percentage` 會即時回報整個部署過程的完成百分比，
可以掛 callback 持續接收——代表現有拖拽安裝介面的進度條，理論上不會
因為改成把落地檔案這件事交給 MSIX 引擎，就退化成只能顯示一個轉圈圈的
等待畫面。**但這只在 C#/WinRT 原生呼叫下是確定的**；Python 這邊要透過
`winsdk`/`pywinrt` 才能呼叫，這類綁定套件對「回傳結果＋進度回報」這種
複雜非同步型別（`IAsyncOperationWithProgress`，跟只回傳單一結果的
`IAsyncOperation` 不同）的支援完整度不確定，有可能只拿得到最終結果、
拿不到中途的 `Progress` callback，這件事不能假設一定行得通，要留到下面
第 3 項的 spike 一起驗證，不是只測「能不能裝」，還要測「進度回報能不能
透過 Python 綁定接得到」。

**第二輪修正——本項在第一輪被評估為可能否決整條路線的判準，該評估權重
過高。** 採用 MSIX 的目的是「由系統保證解除安裝乾淨」，進度條的精細度
是體驗上的加分項，不是採用理由。以一項加分功能作為整條路線的存廢判準，
與採用目的不相稱。且本機部署一份已在磁碟上的套件通常為數秒之內的操作，
該期間顯示不確定進度動畫與顯示百分比之間的體驗差距有限。

第二輪決議：進度回報若無法透過 Python 綁定取得，進度條退化為不確定進度
動畫，不因此放棄 MSIX 路線；亦不採用依檔案大小推估的假進度（假進度會
產生「停在特定百分比不動」這類比不確定動畫更差的畫面，且與本專案不假裝
執行狀態的既有慣例不符）。spike 的判準因此簡化為「能否部署」，進度回報
降為附帶確認項目。

**代價**：

1. **雙層簽章信任鏈**——現在 `signing` 參數只是幫 exe 簽 Authenticode；
   MSIX 額外要求「這包 MSIX 的簽章憑證」必須被目標電腦信任，不然
   `AddPackageAsync` 直接失敗。如果不是走 Store 上架，等於 bootstrapper
   exe 還要先想辦法把憑證裝進使用者電腦的「受信任的人」憑證存放區
   （這一步本身就要系統管理員權限）。
2. **WinRT API 是全新的技術堆疊**——現在整個專案是 ctypes/pywin32 這條
   路線（`Rstrtmgr.dll`、`winreg`、Win32 API 直接呼叫），
   `PackageManager.AddPackageAsync` 屬於 WinRT，Python 這邊要另外引入
   `winsdk`/`pywinrt` 這類綁定套件才呼叫得到，跟現在整個程式碼庫慣用的
   手法是兩套不同的東西，不是加個參數就能接上。
3. 容器沙盒的功能限制（見路線 A 那份清單）**依然存在**——差別只在於
   「使用者看到的安裝畫面」還是自訂的，但 app 本體實際落地之後，一樣要
   活在 MSIX 的沙盒規則底下，路線 A 列出的那些功能限制對路線 B 同樣成立。

## 簽章要求（跟一般 exe 的 Authenticode 簽章不一樣）

MSIX 套件**必須**數位簽章，而且簽章憑證的 Subject 必須跟
`AppxManifest.xml` 裡宣告的 Publisher 完全一致，不然系統的部署引擎
（`AddPackageAsync`／App Installer）會直接拒絕安裝——這跟現有 `signing`
參數（選填、只影響 SmartScreen 警告，不簽也能執行）是完全不同等級的
硬性要求。

**憑證等級不需要到 EV**：EV（Extended Validation）憑證的價值只在
「讓一般 exe 立刻拿到 SmartScreen 信譽」，MSIX 只在乎憑證鏈不鏈得到
Windows 信任的根，一般等級的 OV（Organization Validation）憑證就夠用，
不需要為了 MSIX 特地去買貴很多的 EV 憑證。

**憑證要「被信任」的三條路**：

1. **走 Microsoft Store 上架**——Store 審核通過後用 Store 自己的憑證重新
   簽過，使用者端完全不用額外處理，是最省事的一條路。
2. **用公開 CA 簽發的正式 OV 程式碼簽章憑證**——只要鏈到系統內建的信任
   根，裝機端一樣不用額外處理。
3. **自簽/企業內部 CA**——使用者電腦必須先把憑證手動裝進「受信任的人」
   憑證存放區（或群組原則批次佈署），單機側載給一般使用者不現實，只
   適合企業內網統一佈署。

**具體服務選項——SignPath**：查證屬實，[SignPath](https://signpath.io/solutions/open-source-community)
支援 MSIX/AppX 的「深度簽章」（deep signing），跟前面 §10 待辦清單 #12
提的 Azure Trusted Signing 是同一類雲端代簽服務，可以透過 GitHub Actions
等 CI/CD 整合自動簽。更重要的是：**SignPath Foundation 對符合資格的
開源專案提供免費簽章**（[資格條件](https://signpath.org/terms.html)：
公開原始碼 + 採用受認可的開源授權），這個專案是 MIT 授權、公開在
GitHub 上，很可能直接符合資格。

**但有一個取捨要先想清楚**：SignPath Foundation 免費方案發出的憑證，
Subject（也就是簽章顯示的發行者）固定是 `SignPath Foundation`，不是
這個專案自己的名字或 `lx.k`——套用到 MSIX 上，代表 `AppxManifest.xml`
的 Publisher 欄位就得填 `SignPath Foundation`，使用者安裝時看到的
發行者也是這個名字，不是專案自己的品牌。如果介意這一點，就要考慮自費
買一張 OV 憑證（不用 EV，成本比想像中低很多），換取發行者名稱可以是
自己的名字。這個取捨要留到真的要動工時再定案，不是這輪要決定的事。

## 推薦方向

**如果之後真的要做，走路線 B（混合式 bootstrapper）**，不要做路線 A。

理由：這個專案的核心賣點就是「mac 風格拖拽安裝」的 UX 本身（連專案名稱
都叫 `mac-style-windows-installer`），路線 A 會直接把整個安裝畫面的主控
權交給系統，等於放棄這個專案的核心識別，拿到的「保證乾淨」這個好處，
用「這個工具存在的理由都不見了」去換，不划算。

路線 A（純原生 MSIX）可以留著，但只定位成**額外的、平行的輸出選項**
（例如給想上架 Microsoft Store、或企業內側載部署的使用者），不是取代
現有的 `Setup_XXX.exe` 拖拽流程。

**修正（路線 A 的產物其實是路線 B 建置流程的免費副產品，不用另外規劃）**：
路線 B 的建置流程裡，「已簽章的 `.msix`」本來就是編 bootstrapper exe
之前的一個中間產物（見下方 CI 建置順序的 `sign-msix` job）。與其把它
用完即丟，建置流程最後多一步「把這份已簽章的 `.msix` 也一併發布」，
幾乎是零成本——不需要為路線 A 另外規劃一條獨立的建置邏輯。也就是說
「路線 A vs. 路線 B」不是二選一，而是**做了路線 B 之後，同一次建置
自然產生兩種輸出**：`Setup_XXX.exe`（拖拽安裝體驗）跟 `XXX.msix`
（直接給 winget/企業側載/App Installer 雙擊安裝用）。這個工具最終給
下游專案的產物清單會變成：GUI exe、CLI exe（工具本身固定會有，跟
MSIX 功能無關）、`Setup_XXX.exe`、`XXX.msix`。

## 下游專案的 CI 建置順序（路線 B 確定後才適用）

**下游專案不需要 vendor 這個工具的原始碼**——這個工具本來就會編出一顆
獨立的 CLI exe 發布在 GitHub Releases（`mac-style-windows-installer_CLI_vX.Y.Z.exe`），
下游專案的 CI 只要下載這顆現成的 exe 當一般命令列工具呼叫即可（跟 CI 裡
`choco install` 或下載其他工具的 release asset 是同一種模式），不用把
整個 repo checkout 進自己的建置環境。

**簽章一定要在「合併進 bootstrapper exe」這一步之前完成，不能事後補**：
混合式 bootstrapper 的機制是把 MSIX 檔案本身塞進 exe 的資源區塊
（`--add-data`），一旦已經塞進去，要換成簽過章的版本等於要整個重新編
一次 exe。所以 CI 步驟順序是有嚴格相依性的，不能顛倒：

```
1. 建置 app 內容 → makeappx 打包成未簽章的 .msix
2. 呼叫 SignPath（或其他簽章服務）簽這份 .msix
   —— 這一步必須完全跑完，下一步才能開始 ——
3. 用「已簽章」的 .msix 當輸入，編出 bootstrapper exe（--add-data 塞入）
4.（選擇性）bootstrapper exe 本身也另外簽一次 Authenticode
5. 發布產物
```

**修正：第 2 步是否「呼叫就立刻拿到結果」要看簽章政策設定，不能假設
一定是同步的**。SignPath 用「簽章政策」（signing policy）區分不同用途：
測試簽章可以設成全自動（呼叫 API/CLI 立刻拿到簽好的檔案），但官方文件
明講**正式發版簽章建議額外加一道人工核准關卡**——即使身分驗證早就通過，
每次要簽一份要正式發布的東西，預設建議做法是要有人（可以是專案維護者
自己）手動核准這次簽章請求，不是無條件自動簽完。這件事可以設定成全
自動（略過人工核准這道關），但那不是官方預設推薦的「正式發版」政策。

這對 CI 設計有實際影響，有兩條路可以選：

- **維護者自己手動核准**：`sign-msix` 這個 job 執行到呼叫 SignPath 那步
  會卡住，等維護者去 SignPath 網頁點核准，CI 流程需要能夠「暫停等待」
  （GitHub Actions 有 `environment` + 手動核准這類機制可以做到），不是
  單純的同步 step。
- **把簽章政策設成全自動、或另外寫程式呼叫 SignPath REST API 自動核准**：
  這樣才能維持「一路無人值守跑到底」的全自動 CI，但等於自己主動放棄了
  官方建議的這道人工把關，安全性上的取捨要自己承擔。

這個決定屬於「動工前要先定案」的範圍，見下方清單，這裡先如實記錄兩種
選項都存在，不預設哪一種一定是對的。

**簽章這件事本身，每個下游專案各自處理，不會因為都用同一個打包工具而
共用**：SignPath 的審核是綁定特定 repo 的，下游專案想要簽章過的 MSIX
要自己另外申請一次，這個工具（`builder.py`）也不會把任何特定簽章服務
寫死進打包邏輯——延續現有 `signing` 參數（本機 `.pfx`）的設計哲學，
「打包」跟「簽章」保持解耦，簽章永遠是打包完成之後，呼叫端自己的 CI
再接一段處理的事。

### 下游專案 build.yml 概念範例（FileLocker 這類專案自己的 CI，不是這個 repo 的）

概念性描述 job 拆分跟相依順序，**不是可以直接貼上去跑的 YAML**，實際
語法要等真的動工、確認 SignPath 的 GitHub Actions 整合怎麼呼叫之後
再補：

```
job: build-msix
  - checkout FileLocker 自己的原始碼
  - 下載 mac-style-windows-installer 的 CLI exe（GitHub Releases release asset）
  - 用這顆 CLI 呼叫打包（假設的 --output-format msix 選項），
    產出未簽章的 .msix，當成這個 job 的 artifact 上傳

job: sign-msix
  needs: build-msix
  - 下載上一個 job 的 .msix artifact
  - 呼叫 SignPath 的簽章 action/CLI（FileLocker 自己申請到的帳戶），
    產出已簽章的 .msix
    （若簽章政策設成正式發版要人工核准，這一步會停在這裡等維護者
    去 SignPath 網頁點核准，job 本身要能「暫停等待」，不是單純同步 step）
  - 這份已簽章的 .msix 同時做兩件事：(a) 直接當成 release asset 發布
    （給 winget/企業側載/App Installer 雙擊安裝用，路線 A 的產物）、
    (b) 當成 artifact 傳給下一個 job 當輸入

job: build-bootstrapper
  needs: sign-msix
  - 下載已簽章的 .msix artifact
  - 用這個工具的打包邏輯，把已簽章的 .msix 塞進 bootstrapper exe
  - （選填）呼叫 SignPath 再簽一次這顆 bootstrapper exe 本身
  - 上傳最終的 Setup_XXX.exe 當 release asset
```

最終 release 頁面上，同一次建置會同時掛著 `Setup_XXX.exe`（路線 B）跟
`XXX.msix`（路線 A）兩個檔案，讓下游專案的使用者自己選要用哪一種
安裝方式，不用這個工具/下游專案額外決定「只能提供一種」。

用三個獨立 job（而不是同一個 job 裡三個 step）是刻意的：GitHub Actions
的 `needs:` 關鍵字本來就是設計來表達「這個 job 必須等前一個 job 完全
成功才能開始」，比在單一 job 裡疊 step 更清楚表達出「簽章完成是編
bootstrapper exe 的硬性前置條件」這個順序要求，也方便之後個別重跑
（例如簽章失敗要重試，不用連 build-msix 那個 job 也重跑一次）。

## 第二輪定案決議（2026-08-31）

以下決議透過 `/grill-with-docs` 逐項確認，涵蓋第一輪列為「動工前必須先有
答案」的產品範圍問題。其中三項因具備「不易反轉、後續維護者會質疑、來自
真實取捨」三項特徵而另立 ADR，於各項中標註。

### 一、服務對象是下游專案，不是本工具自身

MSIX 是本工具提供給下游專案的一種輸出選項，不是本工具自身的發布形式。
本工具自身若採用 MSIX 發布，是「以本工具打包自己」的結果，不是獨立的
工程項目。

自簽憑證的定位為開發與測試階段的手段，不是散布給終端使用者的方案。此
定位使「自簽憑證如何取得終端使用者電腦的信任」這個問題在現階段不需解決
——測試環境的信任由環境擁有者自行建立。

### 二、輸出形狀：兩種引擎二選一，MSIX 引擎附帶產出獨立套件

打包設定指定使用哪一種引擎，一次打包產出一顆 `Setup_XXX.exe`。選用 MSIX
引擎時，額外產出一顆獨立的 `.msix`（該檔案本為編 bootstrapper exe 之前的
中間產物，發布它的成本接近於零）。

不採用「同一次打包產出兩顆 `Setup_XXX.exe`」，理由是下游專案若將兩者同時
發布，終端使用者會面對兩個名稱相近的安裝檔，而區別它們的依據（檔案落地
的內部機制）對使用者不具意義，無從判斷應下載何者。附帶產出的 `.msix`
不具此問題——其副檔名與用途明顯不同，指向的是 winget、企業側載這類進階
情境。

引擎的差別對終端使用者的可見程度限於兩處，見 [`CONTEXT.md`](../../CONTEXT.md)
「傳統引擎與 MSIX 引擎」一節。

### 三、打包流程分為兩截，一體式為疊加於其上的便捷路徑

由於已簽章的 `.msix` 必須在編 bootstrapper exe 之前備妥（見上方「下游
專案的 CI 建置順序」），流程存在一個不可消除的斷點。指令設計以「兩截式」
為骨架：第一個指令產出未簽章的 `.msix`，簽章由呼叫端自行處理，第二個
指令接受已簽章的 `.msix` 並編出 bootstrapper exe。

在此骨架之上提供「一體式」便捷路徑：憑證為本機檔案時，由工具串接三個
步驟一次完成。

順序上先建立兩截式骨架，理由是它是唯一容納得下雲端代簽（簽章非即時完成、
可能需人工核准）的形狀；一體式僅為將既有兩步驟自動串接，於骨架完成後
補上的成本低。反向順序（先做一體式）則需在事後拆解整條流程。

### 四、拖曳目的地：獨立圖示，不可點選

MSIX 的安裝位置由系統決定。現有拖曳目的地是可點選的資料夾圖示，點選會
開啟資料夾選擇對話框（`ui/index.html`，`chooseInstallFolder()`），該行為
在 MSIX 模式下無對應語意。

決議：MSIX 模式使用另一張資料夾圖示（`ui/windows_folder_icon.png`，
保留資料夾造型並加上系統標記），移除點選行為，圖示下方的路徑文字改為
說明性文字，不顯示系統實際的套件路徑（該路徑對使用者不具意義）。

保留資料夾造型而非改用其他圖形，理由是「目的地固定、不可選擇」正是
macOS DMG 的原始形式——使用者將應用程式拖入固定的「應用程式」資料夾，
無位置選擇。現行可點選的設計是本專案在原始形式之外的延伸，移除它在
視覺語彙上是回歸而非退化。

兩張圖示的內容佔畫布比例經實測相近（寬 93.8% 對 94.1%，高 78.3% 對
78.5%），替換不需調整版面。

### 五、MSIX 模式不提供自訂解除安裝介面

見 [ADR-0006](../adr/0006-msix-mode-has-no-custom-uninstall-ui.md)。

### 六、進度回報取得失敗時退化為不確定進度動畫

見上方路線 B 說明的「第二輪修正」。

### 七、現有功能依 MSIX 支援程度分為三類

- **第一類（無阻礙）**：免管理員權限安裝、檔案關聯、`add_to_path`、
  安裝前建立系統還原點、安裝密碼保護。
- **第二類（可對應，需另行設計）**：開機自動啟動（MSIX 的對應機制僅
  涵蓋登入時觸發，現有排程工作的其他觸發時機無對應）、Windows 服務
  （MSIX 有支援但限制較多）、相依元件（多數情況改為將執行階段檔案直接
  包入套件）。
- **第三類（格式本身不允許）**：`custom_install_dir`、
  `pre_install_script`/`post_install_script`、內嵌第三方安裝程式靜默執行。

**第五輪修正——本分類缺少一類，且 `local_appdata_files` 原本的歸類不
精確。** 該欄位在本項中與 `no_admin_install` 一併列入第一類，但兩者性質
不同：`no_admin_install` 確實成為 MSIX 的預設行為；`local_appdata_files`
是「把指定檔案改裝到使用者目錄」的檔案配置指令，MSIX 無法執行——套件內
所有檔案皆位於系統管理的套件目錄，不能指定部分檔案落在他處。

但該功能存在的理由在 MSIX 下消失：其用途是「跟主程式分開的 CLI 工具，
讓使用者事後單純執行它不用每次都提權」（`CLI_USAGE.md`），而 MSIX 本來
就安裝於使用者層級、本來就不需要提權。指令無法執行，使用者的目的卻已
達成。

因此新增第四類，處置見第五輪定案決議第三項：

- **第四類（動機消失，設定無害失效）**：`local_appdata_files`。

其餘欄位是否也應改列此類，需依同一判準逐項重新檢查，見待辦事項。

### 八、第一版範圍限於第一類，其餘報錯且訊息語氣分開

第一版實作第一類；第二類與第三類一律報錯。不採用「靜默忽略」與「印出
警告後繼續」：本工具的產物是安裝程式，功能被無聲移除的後果要到終端使用者
安裝完畢、應用程式行為異常時才會顯現，而警告訊息在 CI 環境中無人閱讀。

第二類不列入第一版，理由是三者各自需要獨立研究，同時納入第一版的可能
結果是三者皆為半成品，而安裝程式的半成品功能較諸沒有該功能更不利——
使用者會依據它存在而作出錯誤假設。

兩類的錯誤訊息語氣須可區分：第二類使用「MSIX 模式目前尚未支援 X」，
第三類使用「MSIX 無法 X，此為格式本身的限制」。此區別決定下游專案應
等待本工具補上功能、或應立即重新設計其安裝流程。

### 九、安裝前偵測並移除傳統模式的既有安裝

任何中途改採 MSIX 的下游專案，其既有使用者皆處於「已安裝傳統模式版本」
的狀態。MSIX 部署不知悉該安裝的存在，不處理將導致新舊並存：兩筆同名的
應用程式清單項目、檔案關聯衝突、以及使用者手動清除時刪錯的風險。

決議：MSIX 模式的 bootstrapper 在交付系統部署之前，先執行既有的舊版
偵測與靜默移除流程（[`upgrade.py`](../../upgrade.py) 的
`check_existing()`／`UpgradeCoordinator`，含跨 UAC 提權），並於介面明確
告知將先移除舊版。bootstrapper 為一般程式、不在沙盒內，執行此流程不受
限制，且所需機制已完整存在。

不採用「於文件提醒下游專案自行處理」，理由是實際執行升級動作的是終端
使用者，而終端使用者無從得知「傳統模式」與「MSIX 模式」的區別；亦不採用
「偵測到即報錯要求使用者自行移除」，理由是工具具備自行完成該動作的能力。

此決議的前提是應用程式名稱未變更。名稱變更導致偵測失效的情形無法由工具
端解決，須於文件記載。

### 十、版本號：三段自動補為四段，預發布後綴報錯

MSIX 要求版本號為正好四段純數字，不接受文字後綴，與
[ADR-0003](../adr/0003-allow-prerelease-suffix-in-version-string.md) 所
定義的現行格式（一至四段數字，可選預發布後綴）不一致。

決議：三段版本號自動補為四段（無損轉換）；帶預發布後綴的版本號在 MSIX
模式報錯。傳統模式維持現狀。

不採用「捨棄後綴」，理由是 Windows 判定套件是否需要升級的依據是版本號
遞增：`1.0.0-rc1` 與 `1.0.0` 捨棄後綴後版本號相同，系統將認定兩者為同一
版本而不執行升級，且該問題於打包階段不產生任何錯誤，須至實際升級失敗
時方能發現。亦不採用「將後綴編碼為第四段數字」，理由是該對應規則由工具
自行定義、使用者未曾要求，且規則一經確立即不可變更（變更會使已發布的
套件版本序中斷）。

### 十一、發行者：可讀取憑證時自動填入，否則由使用者指定

套件清單的發行者必須與簽章憑證上記載的名稱完全一致，不一致時系統拒絕
安裝，且其錯誤訊息不指向此原因。現有 `publisher` 欄位為自由文字（用於
VERSIONINFO 的公司名），格式與用途皆不同，不可直接沿用。

決議：憑證檔案可取得時由工具自動讀取並填入；不可取得時（雲端代簽情境下
憑證不在本機）由使用者於設定中指定。

兩者皆需支援而非僅取其一，原因來自決議三：兩截式流程的第一個步驟即產出
含發行者宣告的套件清單，而該步驟先於簽章發生——工具在該時點必須已知發行者
為何，無法延後至簽章時再行取得。

實作時於打包階段執行一致性檢查（憑證可取得時比對，不一致即報錯），避免
錯誤延後至終端使用者安裝失敗時方顯現。

### 十二、套件身分名稱為獨立必填欄位

見 [ADR-0007](../adr/0007-package-identity-name-is-an-explicit-required-field.md)。

### 十三、Windows SDK 工具的定位方式

`makeappx.exe` 與現有的 `signtool` 同屬 Windows SDK。現行做法是
`shutil.which("signtool")`，僅檢索 PATH，找不到即中止建置
（`builder.py:138`）。Windows SDK 安裝後不將這些工具加入 PATH，因此該
做法在多數環境下會對已正確安裝 SDK 的使用者回報「找不到，請安裝
Windows SDK」。此問題現已存在，因簽章為選填功能而少被觸發；MSIX 模式下
SDK 工具為必要相依，此問題將成為每位使用者的第一道障礙。

決議：自動檢索 SDK 的標準安裝位置（多版本並存時取最新），並提供設定
欄位供手動指定路徑。既有的 `signtool` 檢索一併改用同一套邏輯——同一
目錄下的兩支工具採用兩套檢索方式，是後續缺陷的來源。

**第三輪修正——本項假設「使用者需自行安裝 Windows SDK，工具的職責僅為
定位既有安裝」，該假設經 spike 實測後不再成立。** `makeappx`／`signtool`
可經由 `Microsoft.Windows.SDK.BuildTools` 這個 22 MB 的 NuGet 套件取得，
解壓即可執行，不需安裝 SDK（見「第三輪 spike 結果」第五項）。由此產生
的取得機制決議見下方「第四輪定案決議」，另立
[ADR-0008](../adr/0008-sdk-build-tools-are-fetched-on-explicit-request-only.md)。
本項的自動檢索與手動指定仍然成立，但降為三個來源中的兩個，優先序見
該 ADR 決定五。

**本項已實作（2026-08-31）**，見 `sdk_tools.py` 與 `tests/test_sdk_tools.py`。
既有的 `signtool` 檢索已一併改用同一套邏輯，`builder.py` 不再自行檢索
PATH，原本那則誤導性的錯誤訊息（要求使用者「確認它在 PATH 裡」）已移除。

### 十四、產出物不寫入憑證信任存放區

見 [ADR-0005](../adr/0005-installer-never-installs-certificates-into-trust-stores.md)。

### 十五、測試策略：部署動作設計為可注入的接縫

MSIX 的核心動作是請求系統部署套件，該動作無法在每次執行測試時實際發生
（耗時，且失敗時於開發機留下殘留）。

決議：比照 [`CONTEXT.md`](../../CONTEXT.md) 記載的 registry seam
（`file_assoc.py` 的 `registry` 參數），將「請求系統部署套件」設計為
可注入的參數，測試傳入替身，僅記錄呼叫參數而不實際部署。

此設計須自實作第一天即成立。若先寫成直接呼叫、事後再行拆解，即違反
[`CLAUDE.md`](../../CLAUDE.md) 所訂「先寫測試再寫實作」的順序，且測試
易被寫成描述實作的實際行為，而非描述其應有行為。

替身無法驗證「實際部署是否成功」，該部分由真機驗證涵蓋，見下一項。

### 十六、真機驗證沿用既有的 CI workflow

[`test-packaging-options.yml`](../../.github/workflows/test-packaging-options.yml)
已建立「實際打包、靜默安裝至一次性 runner、以指令驗證系統層級效果、靜默
解除安裝並確認清除」的模式，MSIX 的真機驗證於其上擴充。一次性 runner
亦是自簽憑證信任的適當執行環境（其信任存放區不具持續性，見 ADR-0005
決定三）。

兩項須先行驗證、不得假設成立的前提：

1. **runner 為伺服器版 Windows。** MSIX 在伺服器版上的支援與桌面版不
   完全相同，可能需要額外啟用設定，部分行為亦可能相異。
2. **runner 預設以系統管理員身分執行。** 此點使 CI 的通過結果說服力
   受限（既有稽核已記錄此問題），而 MSIX 的特性之一正是「不需管理員
   權限即可安裝」——以管理員身分通過的驗證不足以證明一般使用者可安裝
   成功。須另行設計降權執行的驗證步驟。

上述兩項併入下方 spike 一併確認，理由是其結果決定 MSIX 這部分程式碼
長期是否具備自動化的真機驗證。若 CI 無法涵蓋，該部分的可靠度將持續
低於專案其餘部分，此為投入之前即應知悉的條件。

## 第三輪 spike 結果（2026-08-31，本機）

在一台未安裝 Windows SDK、以非系統管理員身分執行的 Windows 11
（10.0.26200）上進行。所有產物寫入暫存目錄，未變更系統狀態；驗證結束後
確認系統上無殘留套件，憑證與私鑰檔案已刪除。

### 一、綁定套件：`winsdk` 不可用，正確的是 `winrt-*` 系列

第一輪文中所述的 `winsdk` 已不適用：PyPI 上該套件對 Python 3.13 只提供
原始碼壓縮檔、無預先編譯的 wheel，安裝時會在本機編譯一個大型 C++ 專案。
`pip index versions winsdk` 回報 `No matching distribution found`。

實際可用的是 pywinrt 改名後的 `winrt-*` 系列，且為模組化封裝，只需安裝
用得到的命名空間：

```
winrt-runtime                          241 KB
winrt-Windows.Management.Deployment    174 KB
winrt-Windows.Foundation               118 KB
winrt-Windows.Foundation.Collections    69 KB
winrt-Windows.ApplicationModel         162 KB
```

版本 3.2.1，皆有 `cp313-win_amd64` wheel，合計約 800 KB。此體積對後續
併入 PyInstaller 產物有利。

### 二、Python 可完整呼叫部署 API，且不需要系統管理員權限

`PackageManager` 建立成功，介面完整暴露 68 個方法。以非系統管理員身分
呼叫 `find_packages_by_user_security_id(sid)` 成功讀取 253 個已安裝套件。

呼叫 `find_packages()`（列舉全機器所有使用者的套件）回報
`PermissionError: 存取被拒`。該結果為作業系統正確執行權限檢查，不是綁定
故障——同一個物件上的當前使用者版本可正常運作即為佐證。

### 三、進度回報的介面存在

`add_package_async()` 回傳 `_IAsyncOperationWithProgress`，即第一輪擔心
Python 綁定可能不支援的型別。其成員包含 `progress`，指派 callback 成功。

**尚未驗證 callback 在真實部署過程中是否實際被呼叫**——本輪的部署嘗試
在簽章驗證階段即被拒絕，未進入實際部署，進度回報次數為 0。此項留待 CI
驗證（見第五項）。

### 四、發現一個會導致「安裝失敗卻回報成功」的實作陷阱

非同步操作有兩種取得結果的方式，行為不同：

- `get_results()` **不等待操作完成**。在操作仍進行中呼叫，會回傳一個
  `extended_error_code = 0`、`error_text = ""`、`is_registered = False`
  的 `DeploymentResult`——該內容與「成功」難以區分。
- `get()` 會等待操作實際完成。同一次呼叫改用 `get()` 之後，
  `op.status` 為 3（錯誤），`error_code` 為 `0x80073cf0`。

實作必須使用 `get()`，並檢查 `status` 與 `is_registered`，不可僅依賴
例外或錯誤碼。此陷阱在本機測試環境中不易顯現（本機部署快速，誤用
`get_results()` 的結果看起來與成功相同），但會導致產出的安裝檔在部署
失敗時向使用者回報成功。

### 五、Windows SDK 工具可經 NuGet 套件取得，無須安裝 SDK

`Microsoft.Windows.SDK.BuildTools`（版本 10.0.26100.4948）為一個 22 MB
的 zip 檔案，可自 nuget.org 直接下載。解壓後 `bin/10.0.26100.0/x64/`
底下即含 `makeappx.exe`、`signtool.exe`、`MakeCert.exe`，三種處理器架構
（x64／x86／arm64）皆有。實測 `makeappx.exe` 自解壓目錄直接執行成功，
不需安裝程序、不需註冊、不需系統管理員權限。

此結果影響第二輪決議第十三項：該項假設使用者需自行安裝 Windows SDK，
工具的職責僅為定位既有安裝。實測顯示工具可自行取得這些執行檔，使「必須
先安裝數 GB 的 Windows SDK」這道門檻得以消除。本專案開發者自己的機器上
即未安裝 Windows SDK，可佐證該門檻對下游專案開發者而言並非罕見情況。

此發現需要一項新的決策：工具是否應自行下載該 NuGet 套件（涉及打包時的
網路相依），或維持定位既有安裝、僅於文件指引使用者手動取得。見下方
待辦事項。

### 六、打包與簽章流程實測通過

依第二輪決議第三項的兩截式順序完整執行一次：

1. 以 `cryptography` 產生自簽憑證，寫成 `.pfx` 檔案。不使用
   PowerShell 的 `New-SelfSignedCertificate`，因為後者會將憑證寫入使用者
   的憑證存放區，此處不需要該副作用。
2. 準備 app 內容（借用系統的 `notepad.exe` 為替身，比照
   `test-packaging-options.yml` 的既有做法）與 `AppxManifest.xml`。
3. `makeappx pack` 產出未簽章的 `.msix`（205,733 bytes）。
4. `signtool sign` 簽章成功（208,679 bytes）。

`AppxManifest.xml` 的 `Publisher` 與憑證 Subject 皆為 `CN=MswiSpikeTest`，
由同一個常數供給兩處。

### 七、憑證信任要求經實測確認為硬性

部署已簽章的套件遭系統拒絕，`res.error_text` 內容為：

> 錯誤 0x800B0109: 應用程式套件或套件組合中之簽章的根憑證必須受信任。

套件本身通過驗證，唯一的阻擋因素為憑證未被信任，與第一輪「簽章要求」
一節的敘述一致。

附帶發現：`DeploymentResult.error_text` 提供的是完整且已在地化的說明
文字，而非僅有錯誤碼。實作錯誤處理時可直接轉呈該欄位內容。

### 八、PyInstaller 相容性通過（第一輪列為主要風險的項目）

第一輪指出的主要風險是「WinRT 元件靠 COM 啟動，PyInstaller 的
`--onefile` 模式對這類原生互操作套件偶爾會有相容性問題」。實測結果為
通過。

作法：寫一支探針程式，先在一般 Python 環境確認三項全部通過作為基準，
再以 `--onefile` 打包成 exe，清空 `PYTHONPATH` 後執行，比對結果。三項為
匯入綁定、建立 `PackageManager` 並執行唯讀呼叫、非同步部署呼叫與掛載
進度 callback。

第二項是關鍵：匯入成功不代表可用——WinRT 物件經由 COM 啟動，打包環境
若缺少執行階段檔案，會在建立物件的當下才失敗，而非匯入時。

結果：打包後的 exe 三項全部通過，唯讀呼叫同樣讀到 253 個套件，與一般
Python 環境的基準一致。

附帶數據：

- 探針 exe 為 10.5 MB（PyInstaller 啟動器 + Python 執行階段 + `winrt-*`）。
- PyInstaller 未需要任何額外設定即正確收集 `winrt-*` 套件，無須指定
  hidden imports 或自訂 hook。

此結果不涵蓋將 `winrt-*` 與本專案現有相依（pywebview、pywin32）併入
同一顆 exe 的情形，該組合的相容性仍待實作階段確認。

### 九、本輪未涵蓋的項目

- 進度 callback 在真實部署中是否實際觸發。
- 伺服器版 Windows（GitHub Actions runner）能否部署 MSIX。
- 降權執行時能否部署（驗證「不需系統管理員權限」這項特性）。
- `winrt-*` 與本專案現有相依（pywebview、pywin32）併入同一顆 exe 時的
  相容性（第八項僅驗證了 `winrt-*` 單獨打包）。

第一項需要一台可信任測試憑證的機器；第二、三項本即規劃於 CI 進行。三項
一併留待下一輪在 `test-packaging-options.yml` 的擴充中驗證——一次性的
runner 是信任測試憑證的適當環境，其信任存放區不具持續性。第四項屬於
實作階段的確認事項，不需要獨立的 spike。

## 第四輪定案決議（2026-08-31）

第三輪 spike 發現 SDK 工具可經 NuGet 套件取得而不需安裝 Windows SDK，
由此產生「工具是否應自行下載」這個新問題。本輪透過 `/grill-with-docs`
確認，五項決議完整內容與理由見
[ADR-0008](../adr/0008-sdk-build-tools-are-fetched-on-explicit-request-only.md)，
此處僅列結論：

1. **不自動下載**，偵測不到時於錯誤訊息中提供可直接執行的取得指令。
   判準不是「打包時是否連網」（既有的 `bundle_dependencies` 本來就會），
   而是下載物在打包機器上是被**內嵌**還是被**執行**——既有先例只涵蓋
   前者，而打包機器通常存放簽章憑證。
2. **固定版本並驗證 SHA-256**，兩者皆寫死。除安全性外亦為可重現性：
   版本未固定時，不同時間的兩次打包會使用不同的 `makeappx`。與既有
   內建相依元件不驗雜湊的做法不矛盾，理由見 ADR-0008 決定二。
3. **快取為獨立且持久的使用者層級位置，路徑含版本號**，並提供覆蓋設定
   供 CI 使用。不放編譯工作目錄——該處每次建置開頭即清空。
4. **既有的 exe 簽章功能共用同一套取得機制**，不因功能分歧。順帶修正
   既有錯誤訊息的誤導性（現行訊息要求「確認它在 PATH 裡」，但 Windows
   SDK 安裝後不會將這些工具加入 PATH）。
5. **來源優先序：手動指定 → 下載的快取 → 系統 SDK**，依據為使用者表達
   意圖的明確程度。建置過程須輸出本次實際採用的來源與版本。

## 第五輪定案決議（2026-08-31）

處理「MSIX 套件本身怎麼產生」這個第一輪即列出、前四輪未觸及的問題。
本輪聚焦於套件清單（`AppxManifest.xml`）各欄位的來源——哪些由工具推導、
哪些需要使用者輸入。

### 一、清單所需的圖示：預設沿用既有 PNG，允許覆蓋

套件清單至少需要三張圖示（磚塊 150×150、工作列 44×44、商店 50×50）。
本專案目前無任何影像處理能力——production 程式碼不含 Pillow 或任何縮放、
轉檔邏輯，圖示是原封不動傳遞的；`packaging_core.py:553` 一帶的驗證亦
只檢查副檔名，不檢查尺寸。

決議：預設將既有的 `png_icon` 同一份用於三個位置，不做縮放，由 Windows
顯示時自行縮小；另提供設定欄位供使用者個別指定，供在意顯示品質或計畫
上架 Microsoft Store 者使用。

不採用「自動縮放產生」，理由是代價與效益不相稱：使用者提供的 PNG 通常
為大圖（本專案自己的圖示為 1024×1024），填入 150 與 44 這些位置全部是
**縮小**，而縮小是安全的操作，Windows 處理得宜；會產生明顯劣化的是放大，
此處不會發生。為此引進一個影像處理相依（且需一併打包進 exe），換得的
僅是「由誰執行縮小」的差別。

不採用「要求使用者提供三張」作為預設，理由是它會使每一位 MSIX 使用者
都必須先產生三張特定尺寸的圖，而多數使用者不在意工作列圖示的像素級
差異。

此決議需補上兩項既有驗證所缺的檢查：圖示必須為正方形（三個位置皆為
正方形，長方形圖會被拉扁），且邊長不得小於 150 像素（低於此值即發生
放大）。

**此決議的成立以一項未驗證的前提為條件**：尺寸與宣告不符的圖示是否會
被系統拒絕部署。第三輪 spike 使用的是正確尺寸的圖示，未測試錯誤尺寸的
行為。若系統會拒絕，本決議不成立，須改採自動縮放或要求使用者提供。
此項列入待驗清單。

### 二、最低 Windows 版本：固定預設值，允許覆蓋

套件清單必須宣告最低支援的 Windows 版本，該值直接決定哪些機器可以安裝
——低於宣告版本的系統會拒絕部署。

該值有兩個來源，而工具僅知其一：MSIX 格式本身的下限（固定，工具可知），
以及該應用程式自身的需求（工具無從得知）。

決議：工具提供固定的預設值，並開放設定欄位供下游專案覆蓋。此結構直接
對應上述兩個來源——工具知道的部分由工具負責，工具不知道的部分留出接口。
不採用「寫死不可改」（缺少下游表達自身需求的管道），亦不採用「必填」
（多數使用者不知道應填何值，結果不是隨意填寫就是抄用來源不明的數字，
較諸一個有依據的預設值更差）。

兩項注意事項：

1. **預設值須查證後方可寫死。** 第三輪 spike 使用的是 Windows 10 1809，
   該值為憑印象選定、未經查證，且在 Windows 11 上可運作不代表它是下限。
   訂得過高會排除本可支援的使用者。**已於第六輪查證，見「第六輪查證
   結果」第一項——1809（`10.0.17763.0`）成立，但成立的理由與 spike 當時
   的推測無關。**
2. **不可與 WebView2 的既有限制混淆。** README 與規格文件記載「較舊、
   未更新的 Windows 10 可能缺少 WebView2，畫面會空白」，該限制的對象是
   `Setup.exe`（安裝介面能否繪製），清單中的版本宣告則決定套件能否部署，
   兩者是不同的東西，不應合併為同一個數字。

清單另有「已測試到的最高版本」欄位，影響限於相容性提示，依工具自身的
建置環境填入即可，不開放設定。

### 三、`local_appdata_files`：接受並於建置訊息說明

處置為接受該設定、不報錯，並在建置訊息中說明「MSIX 模式下此設定不需要，
因為套件本來就安裝於使用者層級」。

此處置不違反第二輪決議第八項的「不得靜默忽略」。該項的理由是「功能被
無聲移除，後果要到終端使用者安裝完畢、應用程式行為異常時才會顯現」；
本例中沒有功能消失——使用者所求的「不需提權即可執行」依然成立，且以更
直接的方式達成。沒有損失，即沒有需要警告的對象。

不採用報錯，理由是報錯等同要求使用者刪除一個設定，而刪除與否結果完全
相同，屬於無實質意義的工作。不採用完全靜默，理由是使用者填入的設定未
產生作用時有權得知原因，否則會被理解為工具吞掉了設定。

**連帶影響**：`path_target_exe` 與此欄位有互動——若該執行檔列於
`local_appdata_files`，加入 PATH 的路徑會改為那個別位目錄
（`CLI_USAGE.md` 第 104 列）。MSIX 模式下不存在別位目錄，該互動一併
失效，加入 PATH 的即為套件內的執行檔。此行為須併入同一則說明訊息，
避免成為第二個「設定為何沒有作用」的疑問。

### 四、應用程式識別碼由工具填入，不出現在設定檔

套件清單中另有一個識別欄位，其唯一性要求僅限於套件內部，與第二輪決議
第十二項的套件身分名稱（全域唯一）不同。該欄位有字元限制，`app_name`
（自由文字，可為中文）不能直接沿用。

決議：由工具填入固定值，不開放設定、不出現在設定檔。

理由是本工具的模型為「一個套件內含一支主程式」，套件內唯一性因此自動
成立；全域唯一性已由套件身分名稱承擔。固定值同時消除了「變更此值會使
使用者釘選於工作列的捷徑失效」這項風險。不採用由 `app_name` 推導，因為
那會使變更顯示名稱這個無害動作連帶改動內部識別碼——與第二輪決議第十二項
所避開的是同一類問題，僅後果較輕。

**一項未驗證的前提**：`path_target_exe` 允許與 `main_exe` 不同，而 MSIX
中「使程式可於命令列直接呼叫」的宣告掛在應用程式項目之下。若兩者不同時
需要宣告兩個應用程式項目，則「一個套件一支主程式」的前提不成立。此情形
下的結論仍為「由工具填入固定值」，僅需固定兩個而非一個，不改為開放設定。
此項列入待查。**已於第六輪查證，確認需要兩個應用程式項目，本項預備的
結論成立；另有一項該結論未涵蓋的細節，見「第六輪查證結果」第二項。**

## 第六輪查證結果（2026-08-31）

處理第五輪決議所列的兩項待查前提。本輪不產生新的決策，僅以官方文件確認
或推翻既有的推測；查證來源為 Microsoft Learn 的 MSIX 與套件清單結構描述
文件。

### 一、最低 Windows 版本：`10.0.17763.0`（Windows 10 1809）

第三輪 spike 憑印象選定的值查證後成立，但**成立的理由與當時的推測無關**
——當時的依據是「在這台 Windows 11 上可以運作」，而該依據無法推導出下限。
實際的依據如下：

- **MSIX 格式本身的下限是 Windows 10 1709（`10.0.16299.0`）**，更舊的系統
  需另行安裝 MSIX Core 才能安裝套件。此為格式的絕對下限。
- **但微軟自己的支援矩陣從 1809 起算**：`.msix`／`.msixbundle` 的格式
  支援表、桌面版的功能支援表，第一欄皆為 1809。1709 與 1803 僅在內文中
  被描述為「支援主流企業部署情境」，未列入該表。
- 1709 與 1803 已終止支援，1809 對應 LTSC 2019，支援至 2029 年。宣告
  `10.0.16299.0` 會對兩個已無人維護、且不在微軟支援矩陣內的版本作出承諾，
  而該承諾無人驗證。
- 佐證：Windows App SDK 專案的預設 `MinVersion` 即為 `10.0.17763.0`；
  微軟自己的「將命令列執行檔打包為 MSIX」指引，前置條件寫的是
  「Windows 10 version 1809 或更新」。

因此預設值定為 `10.0.17763.0`，理由是「微軟支援矩陣的起點」，不是「格式
的絕對下限」。開放覆蓋的設計不變（見第五輪決議第二項）：需要支援 1709
的下游專案可自行下調，工具不代為判斷該承諾是否成立。

**兩項連帶的實作約束**（本輪查證的附帶發現，皆與此預設值直接相關）：

1. **`uap10:RuntimeBehavior`／`uap10:TrustLevel` 這組屬性需要 Windows 10
   2004（`10.0.19041.0`）**。在 `MinVersion` 低於該值的套件中使用它們，
   啟動資訊會不完整而導致安裝失敗。1809 的等效寫法是
   `EntryPoint="windows.fullTrustApplication"`（等同
   `RuntimeBehavior="packagedClassicApp"` 加 `TrustLevel="mediumIL"`）。
   預設值取 1809 即代表清單必須採用後者這種舊寫法。
2. **Windows 10 2004 之前，Enterprise／Education／LTSC 版必須先開啟側載**
   才能安裝非 Store 應用程式（Home 與 Professional 版預設即開啟）。這是
   終端使用者端的環境條件，不是打包端可處理的事項，須於文件記載。

此外確認：第二輪決議第七項列為第二類的 Windows 服務，其 MSIX 支援需要
Windows 10 2004（清單中的最低版本會被拉到 `10.0.19025.0`）。第一版不涵蓋
該功能，此處不構成衝突，但若日後補上，最低版本預設值需一併重新評估。

### 二、`path_target_exe` 與 `main_exe` 不同時需要兩個應用程式項目

確認需要。命令列別名的宣告位置為
`Package > Applications > Application > Extensions > uap5:Extension >
uap5:AppExecutionAlias`，而該別名啟動的是**其所屬應用程式項目自身的
執行檔**，無法指向另一支執行檔。兩者不同時，命令列工具必須擁有自己的
應用程式項目。

第五輪決議第四項預備的結論因此成立：處置仍為「由工具填入固定值」，只是
固定兩個而非一個，不改為開放設定。應用程式識別碼的唯一性要求限於套件
內部一點亦獲確認（官方描述為「套件內唯一，非全域唯一」），且明確記載
「發布後不應變更，變更會打亂開始畫面上磚的位置」——與第五輪決議第四項
所述的釘選失效風險為同一件事。

**一項該結論未涵蓋的細節**：第二個應用程式項目預設會出現在開始功能表，
使終端使用者的開始功能表多出一個他未要求的項目。微軟自己的命令列打包
指引的處置是於該項目的 `uap:VisualElements` 上設定 `AppListEntry="none"`。
本工具在產生第二個項目時須一併設定此屬性。

另注意每個應用程式項目各自需要自己的 `uap:VisualElements`（含圖示宣告），
第五輪決議第一項的圖示來源因此適用於兩個項目，不是一個。

## 第七輪：設定欄位歸類的逐項重新檢查（2026-08-31）

第五輪新增第四類（動機消失，設定無害失效）時，僅就 `local_appdata_files`
一項作出判定，其餘欄位是否也應改列該類未逐項檢查。本輪以
`CLI_USAGE.md` 欄位對照表所列的 28 個使用者可設定欄位為母體，逐項對照
第二輪決議第七項的分類與第五輪的第四類判準。

第四類的判準有兩個條件，須同時成立：**指令在 MSIX 下無法執行**，且
**使用者設定它的目的已經以其他方式達成或不再存在**。僅符合前者而後者
不成立者，屬第二類或第三類，不是第四類——差別在於有無實質損失。

本輪不作出決定。第一項的發現改變第二輪決議第八項的適用範圍，需另行定案。

### 一、安裝位置的三個選項分屬三個不同類別

**第八輪修正——本項原以 `no_admin_install` 這個欄位為單位敘述，該單位不
正確。** 使用者在打包工具的介面上做的選擇是「安裝位置三選一」，
`no_admin_install` 是由該選擇推導出來的機制名稱（`ui/config.html` 的
`isNoAdminInstall()`），介面上沒有與之對應的勾選框。以欄位為單位敘述會
遺漏兩件事：三個選項中的「自訂路徑」早已列為第三類、與另外兩支的處置不
可能一致；以及這是三選一而非布林的二選一。本節以下保留原敘述，正確的
單位與完整處置見「第八輪定案決議」。

原敘述（單位不正確，結論仍成立）：

第二輪決議第七項將 `no_admin_install` 整項列為第一類（無阻礙），第五輪
修正並確認「該欄位確實成為 MSIX 的預設行為」。此判斷對 `true` 一側成立，
對 `false` 一側不成立，而 **`false` 是預設值**。

- **`no_admin_install=true`**（不要求提權、裝到使用者層級）——第一類成立。
  使用者的目的即為 MSIX 的預設行為，無須任何動作。
- **`no_admin_install=false`**（預設值；裝到 `Program Files`、寫 HKLM、
  捷徑給機器上所有使用者共用）——**第二類，不是第一類**。查證結果：
  `PackageManager.AddPackageAsync` 僅為當前使用者安裝。要讓機器上所有
  使用者都能使用，須改用 `ProvisionPackageForAllUsersAsync`，而該方法
  要求呼叫端具備系統管理員權限、套件須先經過 stage、且須位於系統磁碟區。
  對應機制存在，但部署動作從一次呼叫變成兩段流程，屬「可對應，需另行
  設計」。

此項的影響超出單一欄位的歸類。第二輪決議第八項規定第一版範圍限於第一類，
第二類一律報錯，其成立的前提是「第二類為少數人使用的進階功能，同時納入
第一版的可能結果是三者皆為半成品」。但 `no_admin_install` 的預設值落在
第二類這一側，代表**任何未主動開啟該選項的下游專案，在 MSIX 模式下都會
直接撞上第二類的報錯**——第二類不再是進階功能的分支，而是預設路徑。

此項已於第八輪定案，見「第八輪定案決議」與
[ADR-0009](../adr/0009-msix-engine-first-version-is-per-user-scope-only.md)：
第一版只提供當前使用者範圍，設定要求全機器時以第二類語氣報錯並附替代方案。

### 二、`folder_name` 應改列第四類

唯一用途為組出安裝路徑（`C:\Program Files\<folder_name>`，或
`no_admin_install=true` 時的 `%LOCALAPPDATA%\Programs\<folder_name>`，見
`builder.py` 的 `build_all()` 說明與 `install_scope.py`）。MSIX 的套件目錄
由系統管理、名稱衍生自套件身分名稱，指令無法執行。

使用者在意此欄位的理由是安裝資料夾的名稱會被看見與進入（該欄位的既有
說明即建議使用英數字，以避免路徑含非英數字元在少數環境下出問題）；MSIX
模式下不存在使用者會操作的安裝資料夾，該理由消失。兩個條件皆成立，屬
第四類。

連帶關係：此欄位是 `local_appdata_files`（第五輪已列第四類）目的地路徑的
組成部分，兩者的失效是同一件事的兩個位置，處置訊息宜合併為同一則，不
分開輸出兩次。

### 三、`dependencies_min_version` 未曾列入分類，應與 `dependencies` 同列第二類

該欄位是相依元件的附屬判定條件（判斷已安裝的版本是否足夠），無獨立於
相依元件的意義。相依元件列第二類，此欄位隨之。

### 四、`bundle_dependencies` 與 `dependencies` 分屬不同類，實作時須分別處理

第二輪決議第七項將「相依元件」列第二類、將「內嵌第三方安裝程式靜默執行」
列第三類，兩者對應的是不同欄位：`dependencies`／`custom_dependencies`
（線上下載後安裝）為第二類，`bundle_dependencies`（內嵌進安裝檔）為第三類。
兩者在設定檔中相鄰且名稱相近，錯誤訊息的語氣依第八項須可區分，實作時
不可合併判斷。

### 五、其餘欄位的歸屬（補齊母體，皆為第一類）

第二輪決議第七項的分類以功能為單位，未逐一列出欄位。以下欄位經檢查皆
屬第一類，於此補齊，使 28 個欄位皆有明確歸屬：

`app_dir`、`png_icon`、`ico_icon`、`doc_icon`、`doc_icons`、`app_name`、
`version`、`publisher`、`exe_name`、`main_exe`、`eula_texts`、
`eula_default_lang`、`file_associations`、`add_to_path`、
`path_target_exe`、`signing`、`create_restore_point_before_install`、
`install_password_env`。

三項附註：

- `version` 的第一類歸屬帶第二輪決議第十項的轉換規則（三段補四段、
  預發布後綴報錯），不是原樣沿用。
- `eula_texts`／`eula_default_lang` 的第一類歸屬是推論，尚未驗證，見
  「動工前仍需先有答案的問題」第 5 項。
- `signing` 的第一類歸屬成立（該欄位供 bootstrapper exe 的 Authenticode
  簽章使用，與 MSIX 套件簽章是不同的東西），但兩者在設定上是共用或分立
  仍待決定，見「動工前仍需先有答案的問題」第 4 項。

### 六、`restart_explorer_on_update` 不參與本次歸類

該項自 v0.12.0 起不再是使用者可設定的欄位——`packaging_core.py` 於
`validate_and_build_pack_data()` 中一律設為 `True`（見該處說明：實際結束
任何程式之前必定先有互動確認，讓開發者關閉這個偵測沒有實質防護效果）。
`builder.py`／`gui_config.py`／`builder_cli.py` 仍保留參數傳遞，但兩個
介面皆無入口。因此它不是設定欄位，不列入母體。

其在 MSIX 模式仍有作用範圍：第二輪決議第九項的「安裝前偵測並移除傳統
模式的既有安裝」會呼叫舊版的 `uninstall.exe` 並帶 `--restart-explorer`，
該執行路徑屬於 bootstrapper，不在套件沙盒內，不受 MSIX 限制。

## 第八輪定案決議（2026-08-31）

以 `/grill-with-docs` 處理第七輪第一項所引出的待決事項。四項決議中的前三項
另立 [ADR-0009](../adr/0009-msix-engine-first-version-is-per-user-scope-only.md)，
此處僅列結論與該 ADR 未涵蓋的部分。

### 一、敘述單位改為「安裝位置」，並拆為兩個概念

本項的敘述單位由 `no_admin_install` 欄位改為「安裝位置三選一」，理由見
第七輪第一項的第八輪修正。

「安裝位置」進一步拆為兩個概念——**安裝路徑**（檔案落在哪裡）與**使用者
範圍**（這台電腦上哪些使用者用得到），詞彙見
[`CONTEXT.md`](../../CONTEXT.md)「安裝路徑與使用者範圍」一節。傳統引擎將
兩者焊在同一個選擇上，MSIX 打斷該焊點：安裝路徑消失，使用者範圍保留。

拆分的必要性在於，不拆就無法正確描述損失。不拆時只能說「MSIX 裝不到
`Program Files`」，而該事實對使用者不具意義；真正的損失是「這台電腦上其他
使用者不會有這個應用程式」。兩種說法會導向不同的分類——前者聽起來屬第四類
（動機消失、無害），後者屬第二類（功能確實缺少）。第七輪之所以幾乎將其歸錯
類別，原因即為語彙中只有「安裝位置」一詞同時涵蓋兩件事。

### 二、三個選項的處置

| 安裝位置的選擇 | 安裝路徑 | 使用者範圍 | 類別與處置 |
| --- | --- | --- | --- |
| 使用者目錄 | 消失（無損失） | 當前使用者 | 第一類，通過 |
| `Program Files` | 消失（無損失） | 全機器 | 第二類，報錯（見 ADR-0009 決定二） |
| 自訂路徑 | 指定的路徑無法實現 | 依「需要管理員權限」而定 | 第三類，報錯（`custom_install_dir`，第二輪決議第七項既有） |

自訂路徑同時要求全機器範圍時，兩則訊息依決定四一併列出。

### 三、第一版不做全機器範圍

見 [ADR-0009](../adr/0009-msix-engine-first-version-is-per-user-scope-only.md)
決定一至三：第一版只提供當前使用者範圍；設定要求全機器時以第二輪決議第八項
的第二類語氣報錯，並附加一句指向傳統引擎；不採用靜默降級（該 ADR 記錄了否決
理由，因為該作法成本明顯較低、日後極可能被重新提出）。

不為此新增第三種訊息語氣。第八項的兩種語氣分的是「等待本工具補上」與「立即
重新設計」，本項仍屬前者；附加的替代方案只是告知等待期間有路可走。目前僅此
一例，為單一案例新增類別過早。

### 四、MSIX 的類別檢查一次列出全部違規項

見 ADR-0009 決定四。此項與其餘三項的性質不同：它易於反轉（僅影響錯誤訊息的
呈現，無任何外部依賴），列入該 ADR 是因為它與其餘三項在同一次討論中定案、
且實作時屬同一段程式碼，分開記錄會使實作者漏看其中一項。

## 第九輪定案決議（2026-08-31）：設定欄位與指令命名

定案第二輪決議第十一、十二項與第五輪決議第一、二項所涉欄位的名稱。命名
依循兩項從現有程式碼歸納出的既有慣例：**成組的功能用巢狀物件**（`signing`、
`windows_service`、`scheduled_task` 皆是，不採前綴攤平）、**子指令用短橫線**
（`init`、`list-files`、`pack`、`fetch-sdk-tools`）。

```json
{
  "install_engine": "traditional",

  "msix": {
    "identity_name": "MyCompany.MyApp",
    "certificate_subject": "CN=My Company, O=My Company, C=TW",
    "min_windows_version": "10.0.17763.0",
    "icons": { "tile": "", "taskbar": "", "store": "" }
  }
}
```

- **`install_engine`**（值為 `traditional`／`msix`）——不命名為 `engine`，
  理由是設定檔其餘欄位皆為應用程式本身的資料，單獨一個 `engine` 無法看出
  所指為何。`CONTEXT.md` 所稱的「模式」即為此欄位的二選一。**此項已實作**，
  見 `install_engine.py`。
- **`msix.identity_name`**——[ADR-0007](../adr/0007-package-identity-name-is-an-explicit-required-field.md)
  的套件身分名稱。不命名為 `package_name`，理由是它對應的正是清單中的
  `Identity/@Name`，而「package name」易與顯示名稱混淆。
- **`msix.certificate_subject`**——第二輪決議第十一項的發行者。此處有一項
  取捨：該值填入清單的 `Publisher` 欄位，理應同名，但頂層已有一個
  `publisher`（VERSIONINFO 的公司名，自由文字），同名而不同義的兩個欄位置於
  同一份設定檔是後續缺陷的來源。採 `certificate_subject` 的效益是名稱本身
  即說明了規則——其值必須與憑證上記載的一致，不一致時系統拒絕安裝且錯誤
  訊息不指向此原因。代價是與 MSIX 官方文件的欄位名對不上，讀該文件者需多
  一次轉換。
- **`msix.icons`**（`tile`／`taskbar`／`store`）——第五輪決議第一項的三張
  圖示個別覆蓋，不填即沿用 `png_icon`。不採清單原名（`Square150x150Logo`
  等），理由是後者精確但要求使用者先理解 MSIX 的結構。
- **`msix.min_windows_version`**——第五輪決議第二項，預設
  `10.0.17763.0`（依據見第六輪查證結果第一項）。

### 兩截式的指令

```
mswi-cli pack-msix --config app.json                          → 未簽章的 .msix
（呼叫端自行簽章）
mswi-cli pack --config app.json --signed-msix dist/MyApp.msix → Setup_XXX.exe
```

一體式即為 `pack` 不帶 `--signed-msix`：憑證為本機檔案時，由工具串接三個
步驟一次完成（第二輪決議第三項）。

### MSIX 簽章不另立設定，共用現有的 `signing`

理由與 [ADR-0008](../adr/0008-sdk-build-tools-are-fetched-on-explicit-request-only.md)
決定四同一條：不在新的維度上重新製造剛消除的分歧。需要兩張不同憑證的情形，
走兩截式自行簽署 `.msix` 即可——該路徑本即為此設計。

## 動工前仍需先有答案的問題

第一輪所列五項中，第 1、5 項已於第二輪解決，第 2 項的技術部分已於第三輪
spike 驗證（見「已完成之待辦」）。以下為仍待解決者：

1. **簽章/信任鏈的最終方案**：是否要接上 Microsoft Store 上架（那麼
   簽章信任問題由 Store 解決），還是隻做企業側載（需要自己處理受信任的
   人憑證存放區佈署，通常要搭配群組原則批次部署，不適合個人使用者
   單機側載）。這個決定會大幅影響工程複雜度，必須先定案。細節見上方
   「簽章要求」一節——如果不走 Store，SignPath Foundation 的開源免費
   方案是個候選，但要先決定能不能接受發行者名稱顯示成
   `SignPath Foundation` 而不是自己的品牌，不能接受的話就要編列預算買
   自己的 OV 憑證。

   **第二輪更新**：SignPath Foundation 已回覆拒絕本專案的申請，此候選
   方案不再成立。現階段採自簽憑證，定位為開發與測試手段（見第二輪決議
   第一項），不作為散布方案。取得正式憑證的途徑（公開 CA 的 OV 憑證、
   Microsoft Store 上架、或其他雲端代簽服務）仍待決定，該決定不阻擋
   spike 與第一版實作的進行。
2. **WinRT 綁定套件的可行性驗證**：`winsdk`/`pywinrt` 這類套件能不能在
   PyInstaller 打包後的環境正常運作（WinRT 元件通常靠 COM 啟動，
   PyInstaller 的 `--onefile` 模式對這類原生互操作套件偶爾會有相容性
   問題），這個要先花一輪 spike 驗證，不能假設能直接用。**驗證範圍
   要包含 `AddPackageAsync` 的 `Progress` callback 拿不拿得到**（見上方
   路線 B 說明）。**第二輪更新**：進度回報的取得與否不再是本路線的存廢
   判準（見第二輪決議第六項），spike 的通過條件為「能否部署」，進度回報
   降為附帶確認項目。驗證範圍另增兩項，見第二輪決議第十六項：MSIX 在
   GitHub Actions 的伺服器版 runner 上能否部署，以及能否於降權情況下
   驗證免管理員權限安裝。

   **第三輪更新**：本項已解決。見「第三輪 spike 結果」第一至三項與
   第八項——綁定套件可用（但套件名稱與第一輪所述不同）、部署 API 可
   完整呼叫且不需管理員權限、進度回報的介面存在，且本項原本的主要
   風險 PyInstaller 相容性經實測通過（`--onefile` 打包後 COM 啟動
   正常）。仍未驗證的項目見該節第九項，皆規劃於 CI 或實作階段進行。
3. **MSIX 套件本身怎麼產生**：這個工具現在的輸入是「使用者選一個資料夾
   當 app 內容」，MSIX 需要一份 `AppxManifest.xml` + 用 `makeappx.exe`
   打包——這一步的產生邏輯要另外設計，不是把現有的檔案複製邏輯改個
   輸出格式就好。

   **第五輪更新**：清單各欄位的來源已定案，見「第五輪定案決議」——圖示、
   最低 Windows 版本、`local_appdata_files` 的處置、應用程式識別碼。
   本項尚未涵蓋的部分：清單中的語言宣告如何對應本專案既有的多語系
   設計（`eula_texts`、`lang_detect.py`）、檔案關聯與 PATH 這兩項第一類
   功能在清單中的實際宣告形式、以及清單範本的存放形式（獨立檔案或
   程式碼內組字串）。
4. **設定欄位的具體命名與形狀**：兩截式的兩個指令名稱、引擎選擇欄位、
   套件身分名稱欄位，以及 MSIX 簽章設定與現有 `signing` 欄位（供 exe 的
   Authenticode 簽章使用）之間是共用或分立。

   **已定案的部分**：SDK 路徑與快取覆蓋欄位定為 `sdk_tools_dir` 與
   `sdk_tools_cache_dir`（工具偏好層級，與 `workspace_dir` 同一層，另於
   `pack` 提供同名旗標作單次覆蓋）；SDK 工具的取得指令定為獨立子指令
   `fetch-sdk-tools`。兩者已隨 ADR-0008 的實作定案，見 `sdk_tools.py`。
5. **EULA 頁面在 MSIX 模式的行為**：推論為不受影響（EULA 由 bootstrapper
   於交付系統部署之前顯示完畢），此推論尚未驗證。
