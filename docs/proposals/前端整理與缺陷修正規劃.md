# 甲、安裝進行中／完成後仍可再次觸發安裝

## 重現方式（使用者實測，2026-08-30）

1. 拖曳圖示到資料夾，安裝開始。
2. **在切換到「安裝成功」畫面之前**，再次抓住主畫面上的應用程式圖示不放。
3. 畫面切到「安裝成功」之後，把手上的圖示拖到資料夾圖示上放開。
4. 出現錯誤，訊息提及「尚未通過密碼驗證」／找不到檔案。

## 機制

三件事疊在一起：

**一、圖示在安裝開始的那一刻就恢復可拖曳。** `absorbIntoDropTarget()` 的
收尾（`ui/index.html:1119` 一帶）把 `dragAbsorbing` 設回 `false`，**然後**
才呼叫 `triggerInstallFromDragItem()`。整段安裝期間圖示的狀態跟安裝開始前
完全相同。

**二、`pointerdown` 只有一個守門條件。** `ui/index.html:970` 只檢查
`dragAbsorbing`（吸入動畫播放中）。沒有任何「安裝進行中」或「已經裝完」的
狀態被檢查。

**三、成功彈窗擋不住已經抓在手上的拖曳。** 彈窗是不透明的全螢幕覆蓋層
（`display: flex`、`z-index: 10000`），實測 `document.elementFromPoint()`
在圖示位置回傳的是彈窗本身——所以**新的** `pointerdown` 確實碰不到圖示。
但圖示在彈窗出現前就已經 `setPointerCapture()`，捕獲中的指標事件**完全不
經過命中測試**，後續的 `pointermove`／`pointerup` 照樣送到圖示上。

而且 `showModal()` 不會隱藏 `mainView`——主畫面只是被覆蓋層蓋住，版面仍然
存在，安裝目的地圖示的 `getBoundingClientRect()` 照樣是真實座標，所以放開
時照樣算命中。

換句話說，「彈窗蓋住圖示」是目前唯一在擋第二次拖曳的東西，而它只是副作用、
不是設計，而且只擋得住其中一種情況。

## 錯誤訊息的來源

密碼保護的安裝在成功後會清掉解密出來的暫存資料夾，並把
`self._decrypted_payload_dir` 設回 `None`。第二次呼叫 `trigger_installation()`
時 `_app_contents_dir()` 走到：

```python
if self.password_protected:
    if not self._decrypted_payload_dir:
        raise RuntimeError("尚未通過密碼驗證，無法取得應用程式檔案")
```

**沒有密碼保護的安裝不會出現這個錯誤——它會安靜地再裝一次。** 同一個缺陷
比較不明顯、但不見得比較輕微的表現。

## 三段時間窗，嚴重性不同

| 時間窗 | 目前行為 | 後果 |
|---|---|---|
| 進度條進行中（還沒有任何彈窗） | 圖示完全裸露，可以正常抓起來再放一次 | **兩個 `trigger_installation()` 並行**，同時複製檔案到同一個目錄、同時寫安裝清單、各自可能觸發回滾 |
| 成功彈窗已出現，但拖曳是在彈窗出現前抓住的 | pointer capture 繞過覆蓋層 | 使用者實測到的情境 |
| 安裝失敗／被取消，退回主畫面 | 可以再拖 | **這是正確的**，修正不能把這個情境一起擋掉 |

第一段時間窗沒有被踩到，只是因為進度條跑得快、不容易在那幾秒內再抓一次。
它的後果比使用者實際遇到的更嚴重。

## Python 端沒有第二道防線

`trigger_installation()` 沒有任何重入防護。單一實例鎖
（`_acquire_single_instance_lock()`）是行程層級、在程式啟動時取得一次，
擋的是「使用者手滑開兩個安裝程式」，不是「同一個行程裡被呼叫兩次」。
pywebview 的 JS API 呼叫各自在自己的執行緒上跑，兩次呼叫會真的並行。

## 修正方向

**一、前端引入明確的安裝狀態。** 目前只有 `dragAbsorbing`（動畫中）跟
`installSucceeded`（給關閉彈窗時判斷要不要啟動程式用）。需要一個涵蓋
「安裝進行中」與「已完成」的狀態，`pointerdown` 與鍵盤觸發路徑
（`triggerInstallFromDragItem()` 同時服務滑鼠與鍵盤，見
`tests/test_ui_accessibility.py`）都要檢查它。失敗／取消時要正確清回可拖曳。

**二、彈窗出現時主動終結進行中的拖曳。** 顯示成功彈窗前呼叫
`releasePointerCapture()` 並走既有的 `endDragGesture()` 彈回路徑。只加狀態
檢查而不處理這一步的話，`pointerup` 仍然會被送到圖示上——雖然不再觸發安裝，
但視覺上會留下一個卡在半空中的圖示。

**三、Python 端補一道重入防護。** 前端狀態可以被繞過（畫面被改、或未來多
一條觸發路徑），而 `trigger_installation()` 是 JS API 的公開方法。在
`InstallerAPI` 上加一個「這次安裝已在進行中／已完成」的旗標，第二次呼叫
直接回傳明確錯誤，不要進到複製檔案的流程。這一層也涵蓋第一段時間窗的
並行問題。

## 解除安裝端目前為什麼沒事，以及為什麼這件事會變

解除安裝端目前用的是**瀏覽器內建拖放**（`draggable="true"` +
`dragstart`／`dragover`／`drop`），不是 pointer capture；而且圖示與垃圾桶
都在 `confirmView` 裡，`showView()` 切走時整個畫面被隱藏，拖放的兩端同時
消失。推論上不會踩到同型問題（**未實測**）。

**但乙一旦實作，這個保護就沒了**——解除安裝端會改用同一套 pointer capture
機制。屆時它是否安全，取決於甲有沒有先修好，以及 `showView()` 隱藏畫面之後
`getBoundingClientRect()` 回傳全零是否足以擋掉命中判定（推論上足夠，但那
同樣是副作用而不是設計，跟現在安裝端依賴覆蓋層是同一種脆弱）。

**因此甲必須先做，或與乙一起做。**

## 驗證方式

前端狀態機的部分用這個專案既有的靜態解析手法釘住契約（比照
`tests/test_ui_accessibility.py`／`tests/test_ui_config_conflicts.py`）：斷言
`pointerdown` 與鍵盤觸發都檢查了安裝狀態、斷言顯示成功彈窗的路徑上有釋放
指標捕獲。Python 端的重入防護是一般單元測試（連續呼叫兩次
`trigger_installation()`，第二次要回傳錯誤且不進到複製流程）。

實際的手勢時序（抓著不放、期間畫面切換）沒有辦法用靜態解析或單元測試涵蓋，
需要照使用者的重現步驟實機走一次。

# 乙、把安裝端的自繪拖曳搬進解除安裝端

## 動機

拖曳安裝與拖曳解除安裝是同一個核心識別動作的兩端，目前卻是兩套完全不同的
機制：

| | 安裝端 `ui/index.html` | 解除安裝端 `ui/uninstall.html` |
|---|---|---|
| 機制 | pointer 事件 + `setPointerCapture`，自繪 | 瀏覽器內建 HTML5 拖放 |
| 位移 | 自行實作的彈簧求解器 | 由作業系統繪製，網頁端無法控制 |
| 按下回饋 | 有（`PICKUP_SCALE` 放大） | 只有 CSS `:active` 的 `scale(0.95)` |
| 沒命中 | 彈回原位，速度交接給彈簧 | 無（作業系統的拖曳影像直接消失） |
| 命中 | 吸入動畫 + 目的地回應 | 無 |
| 磁吸 | 有（強度 20%） | 無 |
| 命中容差 | 25px | 由瀏覽器的命中測試決定 |
| 鍵盤操作 | **有**（`tabindex`／`role`／Enter／空白鍵） | **完全沒有** |
| 尊重 `prefers-reduced-motion` | 有 | 不適用 |

[`ADR-0002`](../adr/0002-drag-to-install-self-rendered-drag.md) 記載了安裝端
為什麼要從內建拖放改成自繪：「拖曳過程中跟著游標移動的那張影像由作業系統
繪製，網頁端無法控制它的外觀、縮放、透明度，也無法在放開時介入……整個專案
的核心識別動作，剛好卡在整份介面裡最不能調整外觀的機制上。」

**這段理由對解除安裝端一字不改地成立**——解除安裝端仍然停在那個被換掉的
機制上，等於 ADR-0002 只做了一半。

## 附帶收穫：補上完全缺席的鍵盤操作

`ui/uninstall.html:242` 的 `<div class="icon-wrapper" id="dragAppIcon"
draggable="true">` 沒有 `tabindex`、沒有 `role`、沒有任何 `keydown`
處理——**解除安裝介面目前完全無法用鍵盤操作**。而拖曳是這個畫面唯一的
觸發點（ADR-0002 決定四：不另外提供「跳過拖曳」按鈕）。

安裝端已經解決過這件事，`tests/test_ui_accessibility.py` 也把它釘成測試，
但那份測試只解析 `ui/index.html`。搬過去等於順手補上這個缺口，測試也應
比照擴充到解除安裝端。

## 要搬的東西

安裝端這套拖曳由這些部分組成（`ui/index.html`）：

- **彈簧求解器**：`makeSpring`／`stepSpring`／`springAtRest`
- **拖曳狀態與繪製**：`renderDragPosition`／`setPickedUp`／`setDropHover`／
  `ensureDragLoop`
- **命中判定**：`dragIsOverDropTarget`（重疊即命中 + `HIT_TOLERANCE` 容差）
- **手勢**：`pointerdown`／`pointermove`／`pointerup`／`pointercancel` +
  `endDragGesture`
- **命中後**：`absorbIntoDropTarget`（吸入 + 目的地回應 + 觸發動作）
- **無障礙**：`tabindex`／`role`／Enter 與空白鍵走同一個觸發函式
- **11 個具名常數**：`SPRING_BOUNCE`／`SPRING_RESPONSE`／`PICKUP_SCALE`／
  `ABSORB_MS`／`SWALLOW_MS`／`SWALLOW_SQUASH`／`HIT_TOLERANCE`／
  `MAGNET_STRENGTH`／`MAGNET_RANGE`／`EASE_OUT`／`EASE_SNAP`
- **`motionReduced()`**：`prefers-reduced-motion` 判斷

解除安裝端需要對應調整的部分：

- **目的地從資料夾換成垃圾桶**，「目的地回應」的具體動作不同：安裝端是
  資料夾很輕地吞一下（`SWALLOW_*`），解除安裝端已經有垃圾桶蓋開闔的角度
  彈簧（`createAngleSpring`／`setOpen`），要接到新拖曳的 hover 狀態上，
  取代目前的 `dragenter`／`dragleave`。
- **移除 `setupTrashDragDrop()`**（約 26 行）與 `draggable="true"`。
- **觸發的動作不同**：命中後呼叫 `onDelete()`（進反悔倒數），不是安裝。

## 兩份彈簧求解器的問題

解除安裝端已經有一份彈簧（`createAngleSpring`，給垃圾桶蓋的角度用），
安裝端有另一份（`makeSpring`／`stepSpring`，給位移用）。ADR-0002 說
「自己寫約三十行即可」，現在是兩份三十行。

搬過去之後同一個檔案裡會有兩份彈簧求解器。**建議一併收斂成一份**——這是
純粹的數學求解器，位移與角度只是拿它算不同的量，沒有理由分成兩套實作。
這件事的風險低於整個搬移本身，適合在同一輪處理。

## 作法評估

### 方案一：複製一份到 `ui/uninstall.html`

最快，也最符合「先讓解除安裝端有這個手感」的目標。但這會讓自繪拖曳變成
**兩份要手動對齊的實作**——而這正是這個專案在 Python 端反覆處理過、
`file_assoc.py` 的模組說明明確記載「這個『兩邊手動對齊』的協定已經漏改過」
的形態。ADR-0002 也載明那 11 個常數「是在互動原型上反覆拖曳調出來的觀感
值」，之後一定會再微調——微調時漏改一邊，兩端手感就會分岔，而且不會有任何
測試轉紅。**不建議。**

### 方案二：抽成 `ui/drag_to_target.js`，兩份 HTML 共用（建議）

搬移的同時就做成共用檔案，不製造第二份複本。介面上需要參數化的只有：
目的地元素、命中後要呼叫什麼、目的地的「回應」動畫（資料夾吞一下 vs
垃圾桶開蓋）。

代價是要先解決下面 F01／F02 兩個打包機制問題，否則會製造一個比複製更難
察覺的狀況——複製是「兩份會分岔」，看得到；漏覆蓋是「舊檔案靜默生效」，
看不到。

### 方案三：維持內嵌，改以建置期樣板拼接

在打包流程把共用片段插進兩份 HTML。可以完全迴避 F01／F02（產物仍然只有
HTML 檔案），但會讓「原始碼裡看到的 HTML」與「實際跑的 HTML」不一致，
增加除錯難度，也讓 `tests/test_ui_*.py` 這幾份靜態解析測試需要改成解析
拼接後的結果。**不建議**，記錄下來是為了說明為何不走這條路。

## 走方案二要先解決的兩個打包機制問題

### F01：新增的 `.js` 檔案會落進「只在缺少時才補」的分支

`packaging_core.ensure_workspace_files()` 複製 `ui/` 內容到工作目錄時，
依**檔名白名單**決定覆蓋策略：

```python
if name in ("index.html", "uninstall.html"):
    shutil.copy2(src, dest)          # 實作檔案，一律覆蓋
elif not os.path.exists(dest):
    shutil.copy2(src, dest)          # 其他靜態資源，只在缺少時才補
```

新增的 `.js` 會落進第二個分支。這代表**重複使用同一個工作目錄的使用者，
工作目錄裡卡著的舊版 `.js` 永遠不會被換掉**——不管重新編譯幾次新的打包
工具，實際被拿去打包的都還是最早那次留下的過期程式碼，而且沒有任何錯誤
訊息。

這正是該函式說明文字裡以「【重要】」標記、已經修過一次的同一個缺陷，只是
換一道門重新出現。根因不是那次修正沒做完，而是**修正的形式是一份寫死的
檔名白名單**——白名單天生無法涵蓋之後新增的檔案。

修正方向：改成**依用途判斷而非依檔名**。建議白名單反轉——除了已知的
可自訂靜態資源（目前是 `folder_icon.png`／`app_icon.png`／`trash_*.svg`）
以外一律覆蓋，新增實作檔案時不需要記得更新任何清單，跟這個專案偏好的
「新增時不用記得同步」方向一致。

### F02：新檔案要手動登記，且沒有任何測試會抓漏

新增一份 `ui/*.js` 需要同步更新：

1. `build_config_tool._REQUIRED_FILES`——編譯打包工具 exe 前的存在性檢查，
   目前逐項列出 `ui/config.html`／`ui/index.html`／`ui/uninstall.html`。
2. `packaging_core.ensure_workspace_files()` 的覆蓋白名單（見 F01）。

`--add-data=ui;ui` 是整個資料夾一起帶，不需要改動。

`tests/test_shared_module_packaging.py` 用 `ast` 解析 `installer_core.py`／
`uninstall.py` 的 import、反推應該被打包的**Python 模組**，藉此自動抓出漏
登記的模組。這個機制**不涵蓋 `ui/` 底下的資源**，所以上面兩份清單漏改不會
有任何測試轉紅——跟該測試檔案開頭描述的、當初導致 `ModuleNotFoundError` 的
情境完全相同，只是對象換成前端資源。

修正方向：補上類似的自動比對——解析兩份 HTML 實際 `<script src=>`／
`<img src=>` 引用到的相對路徑，比對 `build_config_tool._REQUIRED_FILES`
有沒有漏登記。

## 驗證方式

結構性契約沿用 ADR-0002 已經確立的做法（見
`tests/test_ui_accessibility.py`）：斷言解除安裝端確實移除了原生拖放、走
pointer 事件並使用 `setPointerCapture`、原位殘影存在、尊重
`prefers-reduced-motion`、鍵盤與滑鼠共用同一個觸發函式。那份測試目前只解析
`ui/index.html`，需要擴充成兩份都檢查。

**手感本身無法自動化驗證**——ADR-0002 已載明模擬的滑鼠與鍵盤事件送不進
pywebview 的 WebView2 內容區（`.claude/skills/run-installer-gui` 的說明也
記載同樣限制）。搬移完成後必須由人在真實的解除安裝視窗上實際拖過，並與
安裝端並排比較手感是否一致。

那 11 個常數依 ADR-0002 的決定**不寫進測試**（「把它們釘死只會擋住往後的
微調」）。

# 丙、翻譯函式的複本

`t`（取翻譯字串，含 `{{變數}}` 代換）與 `applyI18n`（把翻譯套用到帶
`data-i18n` 的元素）在三份畫面裡各有一份複本：

| 函式 | index↔uninstall | index↔config | index 版行數 |
|---|---|---|---|
| `t` | 94% | 94% | 7 |
| `applyI18n` | 84% | 51% | 7 |

（相似度為 `difflib.SequenceMatcher` 對函式本體原文的比對結果。）

`applyI18n` 只剩 51% 相似最明顯——三份畫面對「翻譯要怎麼套到元素上」已經是
三套不同的實作。

**這一項可以獨立於甲乙進行，但優先度低**：它目前造成的是維護成本，不是
使用者看得到的問題。

收斂前要先釐清一個差異（F03）：`ui/config.html` 除了 `pywebviewready` 之外
還有 `initLanguage()`／`checkEnvironmentOnLoad()`／`initWorkspaceDir()` 一串
非同步初始化，且語言偏好存在 `localStorage`（另外兩份沒有這段）。
`applyI18n` 的差異多半源自這裡，抽共用時不能把「各畫面自己的初始化順序」
一起併掉。

如果乙採方案二，`ui/drag_to_target.js` 這個共用檔案的機制（F01／F02 的
修正）已經到位，丙可以直接沿用同一條路，不需要再解決一次。
