**狀態：已勘查，尚未實作。這份文件記錄發現與作法評估，不含任何程式碼變更。**

勘查基準：`0.14.1` 之後、跨模組一致性稽核五輪修正完成的工作樹（測試 806 項
全數通過）。

這份文件涵蓋兩個獨立的主題，**甲的優先度高於乙**：

- **甲**：安裝進行中／完成後，拖曳圖示仍然可以再觸發一次安裝（缺陷，使用者

# 甲、安裝進行中／完成後仍可再次觸發安裝

## 重現方式（使用者實測，2026-08-30）

1. 拖曳圖示到資料夾，安裝開始。
2. **在切換到「安裝成功」畫面之前**，再次抓住主畫面上的應用程式圖示不放。
3. 畫面切到「安裝成功」之後，把手上的圖示拖到資料夾圖示上放開。
4. 出現錯誤，訊息提及「尚未通過密碼驗證」／找不到檔案。

## 機制

三段程式碼合起來造成這個結果：

**一、圖示在安裝開始的那一刻就恢復可拖曳。** `absorbIntoDropTarget()` 的
收尾（`ui/index.html:1119` 一帶）把 `dragAbsorbing` 設回 `false`，**然後**
才呼叫 `triggerInstallFromDragItem()`。也就是說整段安裝期間，圖示的狀態跟
安裝開始前完全相同。

**二、`pointerdown` 只有一個守門條件。** `ui/index.html:970` 的
`dragItem.addEventListener('pointerdown', ...)` 只檢查 `dragAbsorbing`
（吸入動畫播放中）。沒有任何「安裝進行中」或「已經裝完」的狀態被檢查。

**三、成功彈窗擋不住已經抓在手上的拖曳。** 彈窗是不透明的全螢幕覆蓋層
（`display: flex`、`z-index: 10000`、背景 `#f5f5f7`），實測
`document.elementFromPoint()` 在圖示位置回傳的是彈窗本身——所以**新的**
`pointerdown` 確實碰不到圖示。但圖示在彈窗出現前就已經
`setPointerCapture()`，捕獲中的指標事件**完全不經過命中測試**，後續的
`pointermove`／`pointerup` 照樣送到圖示上，放開時照樣算命中資料夾。

換句話說，「彈窗蓋住圖示」這件事目前是唯一在擋第二次拖曳的東西，而它只是
副作用、不是設計，而且只擋得住其中一種情況。

## 錯誤訊息的來源

密碼保護的安裝在成功後會清掉解密出來的暫存資料夾，並把
`self._decrypted_payload_dir` 設回 `None`。第二次呼叫
`trigger_installation()` 時 `_app_contents_dir()` 走到：

```python
if self.password_protected:
    if not self._decrypted_payload_dir:
        raise RuntimeError("尚未通過密碼驗證，無法取得應用程式檔案")
```

這就是使用者看到的訊息。**沒有密碼保護的安裝不會出現這個錯誤——它會安靜地
再裝一次**，這是同一個缺陷比較不明顯、但不見得比較輕微的表現。

## 三段時間窗，嚴重性不同

| 時間窗 | 目前行為 | 後果 |
|---|---|---|
| 進度條進行中（還沒有任何彈窗） | 圖示完全裸露，可以正常抓起來再放一次 | **兩個 `trigger_installation()` 並行**，同時複製檔案到同一個目錄、同時寫安裝清單、同時可能觸發各自的回滾 |
| 成功彈窗已出現，但拖曳是在彈窗出現前抓住的 | pointer capture 繞過覆蓋層 | 使用者實測到的情境 |
| 安裝失敗／被取消，退回主畫面 | 可以再拖 | **這是正確的**，修正不能把這個情境一起擋掉 |

第一段時間窗沒有被使用者踩到，只是因為進度條跑得快、不容易在那幾秒內再抓
一次。它的後果比使用者實際遇到的更嚴重。

## Python 端沒有第二道防線

`trigger_installation()` 沒有任何重入防護。單一實例鎖
（`_acquire_single_instance_lock()`）是行程層級、在程式啟動時取得一次，
擋的是「使用者手滑開兩個安裝程式」，不是「同一個行程裡被呼叫兩次」。
pywebview 的 JS API 呼叫各自在自己的執行緒上跑，兩次呼叫會真的並行。

## 修正方向

**一、前端引入明確的安裝狀態，取代目前的隱含狀態。** 目前只有
`dragAbsorbing`（動畫中）跟 `installSucceeded`（給關閉彈窗時判斷要不要
啟動程式用）。需要一個涵蓋「安裝進行中」與「已完成」的狀態，`pointerdown`
與鍵盤觸發路徑（`triggerInstallFromDragItem()` 同時服務滑鼠與鍵盤，見
`tests/test_ui_accessibility.py`）都要檢查它。失敗／取消時要正確地把狀態
清回可拖曳。

**二、彈窗出現時主動終結進行中的拖曳，不要只靠覆蓋層。** 顯示成功彈窗前
呼叫 `releasePointerCapture()` 並走既有的 `endDragGesture()` 彈回路徑，
讓手上的圖示回到原位。只加狀態檢查而不處理這一步的話，第二段時間窗的
`pointerup` 仍然會被送到圖示上——只是不再觸發安裝，但視覺上會留下一個
卡在半空中的圖示。

**三、Python 端補一道重入防護。** 前端狀態是可以被繞過的（畫面被改、
或未來多一條觸發路徑），而 `trigger_installation()` 是 JS API 的公開方法。
在 `InstallerAPI` 上加一個「這次安裝已經在進行中／已完成」的旗標，第二次
呼叫直接回傳明確的錯誤，不要進到複製檔案的流程。這一層也順帶涵蓋
第一段時間窗的並行問題。

**四、確認解除安裝端是否有同型問題。** 解除安裝端用的是**完全不同的拖曳
機制**——`ui/uninstall.html` 的圖示用瀏覽器原生拖放
（`draggable="true"` + `dragstart`／`dragover`／`drop`），不是 pointer
capture；而且圖示與垃圾桶都在 `confirmView` 裡，`showView()` 切走時整個
畫面會被隱藏，拖放的兩端同時消失。推論上不會踩到同一個問題，但**未實測**，
修正時應一併驗證，不要因為「機制不同」就直接假設安全。

## 驗證方式

前端狀態機的部分可以用這個專案既有的靜態解析手法釘住契約（比照
`tests/test_ui_accessibility.py`／`tests/test_ui_config_conflicts.py`）：斷言
`pointerdown` 與鍵盤觸發都檢查了安裝狀態、斷言顯示成功彈窗的路徑上有釋放
指標捕獲。Python 端的重入防護是一般的單元測試（連續呼叫兩次
`trigger_installation()`，第二次要回傳錯誤且不進到複製流程）。

實際的手勢時序（抓著不放、期間畫面切換）沒有辦法用靜態解析或單元測試涵蓋，
需要照使用者的重現步驟實機走一次。

# 乙、三份畫面共用的 JavaScript 抽出

## 動機

`ui/index.html`（安裝端）、`ui/uninstall.html`（解除安裝端）、
`ui/config.html`（打包工具）三份畫面各自內嵌一段 `<script>`，其中有四個
函式在三份檔案裡各有一份複本，而且**已經彼此不同步**：

| 函式 | 職責 | index↔uninstall | index↔config | index 版行數 |
|---|---|---|---|---|
| `t` | 取翻譯字串（含 `{{變數}}` 代換） | 94% | 94% | 7 |
| `applyI18n` | 把翻譯套用到帶 `data-i18n` 的元素 | 84% | 51% | 7 |
| `setupCustomDrag` | **無邊框視窗**的自訂拖曳 | 89% | 85% | 35 |
| `dragLoop` | 視窗拖曳的每幀位移計算 | 87% | 84% | 30 |

（相似度為 `difflib.SequenceMatcher` 對函式本體原文的比對結果。）

相似度不是 100% 代表這幾份複本各自被改過。`applyI18n` 只剩 51% 相似最明顯
——三份畫面對「翻譯要怎麼套到元素上」已經是三套不同的實作。

這正是這個專案在 Python 端反覆處理過的同一種形態，且**視窗拖曳這一項在
Python 端早就收斂完成**：`window_drag.py` 的模組說明記載
「`ConfigAPI`（製作工具視窗）跟 `InstallerAPI`（安裝端視窗）共用同一份
實作」。後端共用了，前端呼叫它的那一段卻仍是三份各寫各的——收斂只做了
一半。

**不在共用範圍內：應用程式圖示的拖曳。** `setupCustomDrag`／`dragLoop` 指的
是「按住視窗空白處搬動整個視窗」，跟「把圖示拖到資料夾／垃圾桶」是兩件事。
後者在安裝端是 pointer events 加自訂彈簧物理，在解除安裝端是瀏覽器原生
拖放，**兩套機制完全不同**，不是共用的候選（要不要統一是另一個題目，這份
規劃不涵蓋）。

## 各檔案的 JavaScript 份量

| 檔案 | 總行數 | `<script>` 內行數 | 獨有函式數 |
|---|---|---|---|
| `ui/index.html` | 1233 | 795 | 37 |
| `ui/uninstall.html` | 683 | 369 | 15 |
| `ui/config.html` | 1738 | 1323 | 未計（打包工具自己的表單邏輯，不在共用範圍） |

## 發現清單

### F01：新增的共用 `.js` 檔案會落進「只在缺少時才補」的分支

`packaging_core.ensure_workspace_files()` 複製 `ui/` 內容到工作目錄時，
依**檔名白名單**決定覆蓋策略：

```python
if name in ("index.html", "uninstall.html"):
    shutil.copy2(src, dest)          # 實作檔案，一律覆蓋
elif not os.path.exists(dest):
    shutil.copy2(src, dest)          # 其他靜態資源，只在缺少時才補
```

新增的共用 `.js` 會落進第二個分支。這代表**重複使用同一個工作目錄的
使用者，工作目錄裡卡著的舊版 `.js` 永遠不會被換掉**——不管重新編譯幾次
新的打包工具，實際被拿去打包的都還是最早那次留下的過期程式碼，而且沒有
任何錯誤訊息。

這正是該函式說明文字裡以「【重要】」標記、已經修過一次的同一個缺陷，只是
換一道門重新出現。根因不是那次修正沒做完，而是**修正的形式是一份寫死的
檔名白名單**——白名單天生無法涵蓋之後新增的檔案。

### F02：新檔案要手動登記在兩份清單裡，且沒有任何測試會抓漏

新增一份 `ui/*.js` 需要同步更新：

1. `build_config_tool._REQUIRED_FILES`——編譯打包工具 exe 前的存在性檢查，
   目前逐項列出 `ui/config.html`／`ui/index.html`／`ui/uninstall.html`。
2. `packaging_core.ensure_workspace_files()` 的覆蓋白名單（見 F01）。

`--add-data=ui;ui` 是整個資料夾一起帶，不需要改動。

`tests/test_shared_module_packaging.py` 用 `ast` 解析 `installer_core.py`／
`uninstall.py` 的 import、反推應該被打包的**Python 模組**，藉此自動抓出
漏登記的模組。這個機制**不涵蓋 `ui/` 底下的資源**，所以上面兩份清單漏改
不會有任何測試轉紅——跟該測試檔案開頭描述的、當初導致
`ModuleNotFoundError` 的情境完全相同，只是對象換成前端資源。

### F03：三份畫面的載入時機不同，共用檔案不能假設同一種初始化方式

- `ui/index.html`／`ui/uninstall.html`：由 `webview.create_window()` 載入，
  等 `pywebviewready` 事件後才能呼叫 `pywebview.api.*`。
- `ui/config.html`：同樣是 `pywebviewready`，但它額外有
  `initLanguage()`／`checkEnvironmentOnLoad()`／`initWorkspaceDir()` 一串
  非同步初始化，且語言偏好存在 `localStorage`（另外兩份沒有這段）。

`applyI18n` 相似度只有 51% 多半源自這個差異。抽共用時要先確認「哪些是
真正共用的行為、哪些是各畫面自己的初始化順序」，不能把差異一起併掉。

## 作法評估

### 方案一：抽成 `ui/shared.js`，三份 HTML 以 `<script src>` 載入

最直觀，但要先解決 F01／F02，否則會製造一個比現況更難察覺的問題——現況是
「三份複本不同步」，看得到；漏覆蓋則是「舊檔案靜默生效」，看不到。

配套修正：

- `ensure_workspace_files()` 的覆蓋策略改成**依用途判斷而非依檔名**。例如
  把「實作檔案」與「使用者可自訂的靜態資源」拆成兩份明確的清單，或改成
  「除了已知的可自訂資源（目前是 `folder_icon.png`／`app_icon.png`／
  `trash_*.svg`）以外一律覆蓋」——後者是白名單反轉，新增實作檔案時不需要
  記得更新任何清單，跟這個專案偏好的「新增時不用記得同步」方向一致。
- 為 `ui/` 資源補上類似 `test_shared_module_packaging.py` 的自動比對：解析
  三份 HTML 實際 `<script src=>`／`<img src=>` 引用到的相對路徑，比對
  `build_config_tool._REQUIRED_FILES` 有沒有漏登記。

### 方案二：維持內嵌，改以建置期樣板拼接

在打包流程把共用片段插進三份 HTML。可以完全迴避 F01／F02（產物仍然只有
三個 HTML 檔案），但會讓「原始碼裡看到的 HTML」與「實際跑的 HTML」不一致，
增加除錯難度，也讓 `tests/test_ui_*.py` 這幾份靜態解析測試需要改成解析
拼接後的結果。**不建議**，記錄下來是為了說明為何不走這條路。

### 方案三：只收斂視窗拖曳，翻譯機制暫不動

`setupCustomDrag`／`dragLoop` 三份相似度都在 84% 以上、職責單純、且後端
（`window_drag.py`）已經是共用的，收斂風險最低、收益明確。`t`／`applyI18n`
牽涉各畫面不同的初始化順序（F03），可以留到下一步。

適合作為第一刀，讓 F01／F02 的配套修正先在一個範圍較小的改動上驗證過。

## 建議順序

1. 先修 F01／F02 的機制問題（覆蓋策略與自動比對測試），這一步不搬動任何
   前端程式碼，可獨立驗證。
2. 依方案三收斂視窗拖曳，確認整條打包流程在多了一個 `ui/*.js` 之後仍然
   正確（含重複使用同一個工作目錄的情境）。
3. 再處理 `t`／`applyI18n`，並先釐清 F03 列出的初始化差異。

## 已知限制

- 甲的第一段時間窗（進度條進行中再放一次，導致兩個安裝並行）是依程式碼
  推論，**未實際重現**。使用者實測到的是第二段時間窗。動工修正時應先確認
  第一段是否真的可觸發，以及並行安裝的實際表現。
- 甲的第四點（解除安裝端是否有同型問題）同樣未實測，目前只有「機制不同、
  拖放兩端會同時被隱藏」這個推論。
- 乙的相似度數字以函式本體原文比對得出，反映的是文字差異而非語意差異；
  84% 相似也可能是行為完全等價、只有變數命名不同。實際收斂前仍需逐一閱讀
  三份實作，確認差異是「已經長歪」還是「各畫面真正需要的不同行為」。
- 乙未實際嘗試新增 `.js` 檔案跑一次完整打包流程，F01 的實際表現（舊檔案
  靜默生效）是依 `ensure_workspace_files()` 的程式碼推論，動工時應先以
  「重複使用同一個工作目錄」的情境實機重現確認。
- 未評估 `ui/config.html` 那 1323 行打包工具自身的表單邏輯。它與另外兩份
  畫面的共用面只有上述四個函式，其餘不在這份規劃範圍內。
