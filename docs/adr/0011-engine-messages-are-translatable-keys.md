# ADR-0011：引擎相容性訊息改為可翻譯的 key，且僅限 `install_engine.py`

- 狀態：已定案
- 日期：2026-09-01
- 相關：[ADR-0009](0009-msix-engine-first-version-is-per-user-scope-only.md)、
  `docs/proposals/MSIX輸出規劃.md` 第十四輪定案決議第七至九項

## 背景

`install_engine.py` 回報「這份設定與 MSIX 引擎不相容」的訊息，原本是寫死在
模組內的繁體中文句子，由 `Finding.message` 直接攜帶。CLI 與配置精靈都直接
把那些句子印出來。

第十四輪定案決議第四項要求在使用者選定引擎的當下，就地標出不相容的欄位，
而不是等到按下編譯才一次列出。該提示會出現在配置精靈的表單上，而配置精靈
是雙語的（繁體中文／英文，語言由使用者在畫面上選擇）。只有中文的訊息會使
英文介面出現一塊未翻譯的區域。

## 決定

### 一、訊息改為 key，翻譯表放在 Python 端

`Finding` 攜帶的是訊息表的鍵（`field.<欄位>`），不是現成的句子。
`Report.error_message(lang)` 於組出訊息時才查表。

翻譯表放在 `install_engine.py` 而不是 `ui/config.html` 的 i18n 表：CLI 沒有
前端可以問，訊息若只存在於前端，CLI 就沒有來源。

保留現成句子並在前端另寫一份簡短的雙語版本亦為候選方案，且改動最小；不採用
是因為兩地各有一份文字，日後分類異動而其中一處沒跟上時，症狀是某個欄位在
某個語言下沒有訊息，而那不會有任何測試以外的地方會叫。改為 key 之後，
「兩種語言的鍵集合必須相等」與「每個分類欄位都有訊息」成為可以直接斷言的
性質（見 `tests/test_install_engine_i18n.py`）。

### 二、就地提示只說類別，不說細節

配置精靈欄位旁的提示取自 `hint.<類別>`，三則、兩種語言共六則。欄位各自的
完整說明（失去什麼、有無替代方案）留在按下編譯時的清單裡。

理由：那份清單的職責是支援「切換引擎對本專案是否划算」這個判斷
（ADR-0009 決定四），需要完整資訊；表單上的提示職責是事前告知「這一格在
這個模式下不能用」，塞進一整段會把表單擠爆。

### 三、欄位分類另開一個與設定值無關的查詢

`field_categories()` 回傳 `{欄位: 類別}`，不看這次填了什麼。
`check_settings()` 維持原本的語意，只列出實際被填了的欄位。

兩者是不同的問題：就地標記的用途是事前告知，使用者還沒填就該看得到這一格
在這個模式下不能用；而建置時的清單回答的是「這份設定裡有哪些違規」。

前端因此不需要自行維護一份不相容欄位清單。前端若自行維護，該清單與
`install_engine.py` 分岔時的症狀是某個欄位悄悄不再被標記。

### 四、CLI 依系統語言，`--lang` 可覆寫

`pack` 與 `pack-msix` 接受 `--lang`。未指定時呼叫既有的
`lang_detect.detect_system_language()`，與配置精靈首次啟動時的預設值一致。

提供旗標而非僅依系統語言，是為了 CI：輸出語言跟著執行機器的區域設定跑，
會使同一份設定在兩台機器上產生不同語言的紀錄，比對即失效。

認不得的語言標籤退回預設語言，不拋例外。語言標籤來自系統設定或命令列旗標，
可能是任何值；為了一個顯示語言中止建置沒有道理。

### 五、本次範圍僅限 `install_engine.py`

`packaging_core.py` 的欄位驗證訊息維持繁體中文，不在本次改動範圍。

兩者的訊息顯示在同一個彈窗裡，因此英文介面按下編譯時，錯誤訊息會出現
MSIX 部分為英文、欄位驗證部分為中文的混雜。此代價為已知且接受。

理由：`packaging_core.py` 的訊息數量遠多於 `install_engine.py`（欄位驗證
散在整個檔案中），且多數帶參數（欄位名、路徑），改造量為另一個量級。第十四輪
的主題是表單結構與引擎連動，把整個後端的訊息層一併重寫會使該輪大到難以驗收。
兩者可以完全獨立地進行。

## 後果

- 一個未來的讀者看到 `install_engine.py` 回傳 key 而 `packaging_core.py`
  回傳現成句子，會認為那是沒做完的重構。該不一致是刻意的、分階段的，本文
  即為其記錄——在 `packaging_core.py` 一併完成之前，不要「順手修好」其中一邊。
- CLI 的輸出語言不再固定為繁體中文。既有的自動化流程若以中文字串比對 CLI
  輸出，在英文系統上會失效；`--lang zh-TW` 可恢復原行為。
- `Finding` 的第三個欄位由 `message` 更名為 `key`。該結構未在本專案之外使用。

## 決定五的後續（2026-09-02）

決定五所述的分階段已完成。`packaging_core.py`、`png_size.py`、`cert_subject.py`、`msix_settings.py` 的訊息皆已改為可翻譯的 key，英文介面下的錯誤彈窗不再中英混雜。

搬移 `packaging_core.py` 的四十六則訊息時，**中文一律以工具從原始碼逐字抽出**（AST 解析，隱式串接與 f-string 皆能正確處理），不由人手重打。先前一次嘗試憑印象重寫，改掉了十六則的措辭，並把數則「`<br>`」之後的整段解釋整段丟失——而測試多半只斷言關鍵字，全數通過。該次嘗試已退回。

過程中另修正兩項：

- `install_engine.UnknownEngine` 的訊息在第十四輪 key 化時被漏掉，仍為  寫死的中文。它是唯一不在 `check_settings()` 路徑上的使用者可見訊息，  因此未被該次的清點涵蓋。
- 取訊息的輔助函式其前兩個參數名為 `key` 與 `lang`，與訊息本身的參數名  相撞（`custom_dep.insecure_url` 帶的正是 `key=key`，  拋出 `got multiple values for argument 'key'`）。六個取訊息的函式改為  僅限位置參數（`/`），訊息的參數叫什麼都不再會撞。
