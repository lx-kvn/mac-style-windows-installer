# ADR-0010：MSIX 模式的檔案關聯圖示必須是 PNG，且此限制與最低 Windows 版本綁定

## 狀態

已接受（2026-09-01 決定）。尚未實作。決定範圍屬於 MSIX 輸出功能，規劃見
[`docs/proposals/MSIX輸出規劃.md`](../proposals/MSIX輸出規劃.md)。

## 背景

現有的檔案關聯圖示欄位 `doc_icon`（所有副檔名共用一張）與 `doc_icons`
（每個副檔名各自一張）接受的是 `.ico` 檔案——`builder.py` 會把它們複製成
`doc_icon.ico`／`doc_icon_<副檔名>.ico` 內嵌進安裝檔，安裝端寫進登錄表的
`DefaultIcon`。

MSIX 的檔案關聯宣告中，圖示由 `<uap:Logo>` 承載，而該元素接受的是 MSIX
資源系統認得的影像格式，不含 `.ico`。另有一個明確支援 `.ico` 的變體
`<desktop7:Logo>`（官方描述為「Adds support for .ico, .dll, and .exe
files」），**但它要求 Windows 10 build 19645**，遠高於
[第六輪查證](../proposals/MSIX輸出規劃.md)所定的最低版本預設值
`10.0.17763.0`（Windows 10 1809）。宣告一個高於套件最低版本的元素，會使
套件在該版本以下的系統上行為不完整。

本專案沒有影像處理能力——production 程式碼不含 Pillow 或任何轉檔、縮放
邏輯（見第五輪決議第一項），因此無法在打包階段把 `.ico` 轉成 PNG。

曾考慮的第三條路是**不宣告圖示**，倚賴系統的退回行為。該路徑因兩項理由
被放棄：官方文件對退回行為的描述是「通用的預設圖示，或關聯程式的圖示，
視 Windows 版本與設定而定」，本身即不確定；且以 CI 探針實測兩次皆未取得
量測結果（`SHGetFileInfoW` 在無人值守的 runner 上對有宣告圖示的對照組同樣
無回報，證明是量測方法無效而非取得答案）。以一個不確定的結果換取「使用者
少準備一張圖」，而該不確定的結果可能是空白的通用文件圖示——那將使使用者
設定關聯圖示的目的完全落空，且要到終端使用者安裝完畢後才顯現。

## 決定

### 一、MSIX 模式的關聯圖示必須是 PNG

`doc_icon` 與 `doc_icons` 沿用既有欄位，不新增欄位；MSIX 模式下驗證改為
「必須是 `.png`」，填入 `.ico` 於打包階段報錯，訊息說明格式限制的來源。

不新增 `msix.doc_icons` 這類平行欄位，理由是那會使同一個概念在設定檔中
有兩處來源，而兩者的取捨（哪一個生效、兩個都填怎麼辦）沒有使用者能理解
的答案。同一個欄位在不同引擎下接受不同格式，是可以用一句話說明的規則。

使用者的代價是為既有的圖示另存一份 PNG，屬一次性工作，且錯誤訊息會直接
說明要做什麼。相對於此，功能得以完整保留——每個副檔名各自的圖示不會消失。

### 二、每個副檔名各自一個關聯群組

MSIX 的 `<uap:Logo>` 掛在**關聯群組**（`uap:FileTypeAssociation`）之下，
不是掛在個別副檔名之下；一個群組可含多個副檔名，但只有一個圖示。

現有的 `doc_icons` 允許每個副檔名各有圖示，要保留該能力，就必須讓每個
副檔名各自成為一個群組。群組名稱有格式限制（1 至 64 字元、全小寫、無
空白），由副檔名推導（`.locked` → `locked`）。

不採用「所有副檔名共用一個群組」，理由是那會使 `doc_icons` 這個既有欄位
在 MSIX 模式失去意義，而該欄位的存在本身就來自「不同副檔名需要不同圖示」
這個真實需求（其加入時的理由記於 `builder.py` 的說明）。

### 三、此限制與最低 Windows 版本綁定，版本提高時應重新評估

本決定成立的唯一原因是 `desktop7:Logo` 的最低版本（build 19645）高於本
工具宣告的最低版本（`10.0.17763.0`）。**若日後最低版本預設值提高至 19645
以上，此限制即自動消失**，屆時可改為直接宣告 `.ico`，使用者不需要再另外
準備 PNG。

此項獨立列為決定而非寫在後果裡，是因為兩個決定之間的相依關係不會從程式碼
看出來：讀到「MSIX 模式要 PNG」的人不會知道它取決於另一個檔案裡的一個
版本號常數。最低版本預設值的變更（`msix_settings.DEFAULT_MIN_WINDOWS_VERSION`）
須一併回頭檢視本決定。

## 後果

- 既有下游專案切換到 MSIX 引擎時，若使用了檔案關聯圖示，需要多準備 PNG。
  該需求於打包階段以明確訊息提出，不會延後至終端使用者端。
- 檔案關聯的清單結構為「一個副檔名一個群組」，群組數量隨副檔名數量成長。
  群組名稱由副檔名推導，因此副檔名的字元集連帶受到群組名稱格式的約束，
  需於驗證階段檢查。
- 最低 Windows 版本的預設值成為一個牽動其他決定的常數，變更時的檢視範圍
  大於該值本身。

## 已知限制

- 「不宣告圖示時系統實際使用哪個圖示」這個事實仍然未知。以 CI 探針量測
  兩次皆未取得結果（第一次使用 `SHGetFileInfoW`，對照組同樣無回報）。本
  決定不依賴該事實，因此不阻擋實作；但若日後要重新評估決定一，需要先取得
  該答案，建議的下一個量測方式是部署後直接讀取
  `HKCU\Software\Classes` 底下的 ProgID 與 `DefaultIcon`。
- 本決定未涵蓋 `.ico` 內含多張不同尺寸影像這件事。PNG 是單一尺寸，使用者
  由 `.ico` 另存 PNG 時需自行決定取哪一個尺寸，本工具不提供指引。

## 已完成之待辦

1. **MSIX 模式下 `doc_icon`／`doc_icons` 的 PNG 驗證與 `.ico` 的報錯訊息**
   ——已實作於 `packaging_core.py`。訊息鍵為 `doc_icon.format` 與
   `doc_icon.ext_bad_format`，MSIX 模式下額外附上 `doc_icon.msix_png_reason`
   說明為何只能是 PNG。
2. **副檔名到群組名稱的推導與格式驗證**——已實作於
   `msix_manifest.association_group_name()`。
3. **`msix_settings.DEFAULT_MIN_WINDOWS_VERSION` 一帶的註記**——已補上，
   指出調高該值時本 ADR 決定三的前提可能不再成立，須重新評估。
