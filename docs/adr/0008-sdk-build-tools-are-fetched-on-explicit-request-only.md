# ADR-0008：Windows SDK 工具由使用者明確要求才下載，打包流程不自動取得

## 狀態

已接受（2026-08-31 決定）。決定範圍屬於尚未實作的 MSIX 輸出功能，
規劃見 [`docs/proposals/MSIX輸出規劃.md`](../proposals/MSIX輸出規劃.md)。

## 背景

MSIX 模式需要 `makeappx.exe`（打包）與 `signtool.exe`（簽章），兩者屬於
Windows SDK。第三輪 spike 實測確認
（見規劃文件「第三輪 spike 結果」第五項）：
`Microsoft.Windows.SDK.BuildTools` 這個 22 MB 的 NuGet 套件為一般 zip
檔案，可自 nuget.org 直接下載，解壓後即可執行這兩支工具，不需安裝程序、
不需註冊、不需系統管理員權限。

此發現使一個設計成為可能：打包流程在找不到 SDK 工具時自行下載，使用者
無感。其吸引力有實據支撐——本專案開發者自己的機器上即未安裝 Windows
SDK，顯示「要求使用者先安裝數 GB 的 SDK」這道門檻對下游專案開發者而言
並非罕見障礙。

本專案的打包流程亦已存在打包當下的網路存取：`bundle_dependencies` 會在
打包時下載相依元件安裝檔並內嵌進 `Setup.exe`（`builder.py` 的
`_download_file()`）。若僅以「打包時是否連網」為判準，自動下載並未跨越
任何新的界線。

## 決定

### 一、不自動下載；偵測不到時輸出取得指令

打包流程不自行下載 SDK 工具。找不到可用的工具時中止並報錯，錯誤訊息
包含使用者可直接複製執行的取得指令。

判斷的依據不是「打包時是否連網」，而是**下載物在打包機器上的處置方式**：

- 既有的 `bundle_dependencies`：下載一個檔案，將其**內嵌**進產出的
  `Setup.exe`。該檔案在打包機器上不被執行。最壞情況是產出一顆內容有誤
  的安裝檔。
- SDK 工具：下載一個執行檔，並在打包機器上**執行**它。最壞情況是打包
  機器遭入侵——而打包機器通常存放簽章憑證。

既有先例只涵蓋前者。以「本專案已經會在打包時下載東西」推導出「因此可以
自動下載並執行」，是把兩種不同性質的行為視為同一件事。

在打包機器上執行一個剛從網路取得的執行檔，屬於應由使用者知情並同意的
行為，不由工具代為決定。

此決定同時避免另一個實務問題：打包過程進行未預期的網路存取，在 CI 或
無外網環境中會表現為難以診斷的失敗。

**此決定保留了自動下載的絕大部分效益**：原本的門檻是「使用者需自行得知
要安裝 Windows SDK、找到它、完成數 GB 的安裝」；本決定將其降為「照著
錯誤訊息複製一行指令」。門檻中屬於「使用者需自行研究」的部分已被消除，
剩餘的是一次明確的確認動作。

### 二、版本固定並驗證雜湊

下載的 NuGet 套件版本與其 SHA-256 雜湊皆寫死於程式碼中。

理由有二。其一與決定一同源：既然判定「下載來執行」的風險高於「下載來
內嵌」，就不應套用內嵌情境的驗證強度。其二為可重現性——版本未固定時，
不同時間執行的兩次打包會使用不同版本的 `makeappx`，產出的 `.msix` 因此
不同；對一個打包工具而言，無法確定使用者的工具鏈版本會使問題回報難以
處置。

此處與既有的內建相依元件（`dependency_defs.py` 的
`BUILT_IN_DEPENDENCIES`）採取不同做法，兩者並不矛盾：那些項目的下載
網址是 `https://aka.ms/vc14/...` 這類**指向最新版**的形式，該設計對
VC++ 執行階段是正確的（使用者應取得最新版），而網址內容既然會變動，
就無法釘住雜湊——未驗證雜湊是該設計選擇的必然結果。SDK 工具的需求相反：
需要一組已知且穩定的工具鏈。NuGet 套件發布後內容不可變更，因此固定版本
即等同固定內容，雜湊值取得一次後永久有效。

`_download_file()` 已支援 `expected_sha256` 參數，此決定不需要新的機制。

代價：版本需要人工維護。寫死版本號與雜湊值之處須加註說明固定的理由，
以及更換版本時兩個常數必須同時更新。

### 三、快取位置為獨立且持久，路徑含版本號

下載的工具存放於使用者層級的持久位置（比照
`packaging_core.default_workspace_dir()` 所使用的 `%LOCALAPPDATA%`
慣例），路徑中含版本號，並提供設定欄位供覆蓋（供 CI 將該目錄納入其
快取機制，需求性質同既有的 `--workspace-dir`）。

不放置於編譯工作目錄，因為該目錄是每次建置開頭即清空的暫存區；將「取得
一次即長期有效」與「每次重新產生」的資料置於同一區域，會導致快取在某次
清理中消失，使用者需重新下載。此點亦與決定一相關：決定一之所以成立，
前提是「取得一次即持續有效」；快取若不持久，該前提不成立。

路徑含版本號是為了配合決定二的版本更換：新版本落於新目錄，不覆寫舊版，
亦不會產生新舊混雜的中間狀態。

### 四、既有的 exe 簽章功能共用同一套取得機制

`signtool` 同時為 MSIX 模式與既有的 `signing` 功能所使用。取得機制兩者
共用，不因功能而分歧。

理由為一致性：規劃文件第二輪決議第十三項已決定統一 `signtool` 與
`makeappx` 的檢索邏輯，理由是「同一目錄下的兩支工具採用兩套檢索方式，
是後續缺陷的來源」。若在「是否可下載」這個維度上重新分開，等同於在另一
個位置重建剛被消除的不一致。

對既有功能而言此非風險方向的變更：未主動要求下載時，簽章仍然失敗，差別
僅在錯誤訊息由死路變為可執行的指引。此變更並修正既有錯誤訊息的誤導性
——現行訊息為「需要安裝 Windows SDK 或 Visual Studio，並確認它在 PATH
裡」（`builder.py:141`），而 Windows SDK 安裝後不會將這些工具加入 PATH，
依該訊息操作不會成功。

### 五、來源優先序依使用者意圖的明確程度排列

1. 使用者手動指定的路徑
2. 下載的快取
3. 系統上偵測到的 SDK 安裝

排序依據為「使用者表達該意圖的明確程度」，而非來源的技術特性。此依據
使順序可被推導而不需記憶，並在未來新增來源時提供插入位置的判準。

快取優先於系統 SDK 的理由有二：快取是經決定二固定版本並驗證雜湊的
版本，系統上的安裝則是使用者碰巧具備的，版本不一且可能為殘缺安裝——
而具備 SDK 的使用者正是版本差異最大的一群，決定二的可重現性目標若讓
系統安裝優先，對這群使用者即失效。其二，依決定一，快取不會自動產生，
其存在即代表使用者曾主動執行取得指令；此時採用其他來源等同忽略使用者
已明確表達的選擇。

建置過程須輸出本次實際採用的來源與版本。三個來源並存時，「兩台機器
打包結果不同」的問題若無此資訊將難以診斷。

## 後果

- MSIX 模式的首次使用需要一次額外的明確操作。
- 既有 `signing` 功能的使用者取得一條先前不存在的解決路徑，且錯誤訊息
  的誤導性被移除。
- 版本號與雜湊值成為需要人工維護的項目。

## 已知限制

- 決定一無法防止使用者在不理解後果的情況下執行取得指令。該指令的作用
  是取得並執行一個外部執行檔，工具能做的是使其成為一次明確的動作，而
  非確保使用者理解該動作。
- 決定二的版本固定沒有自動更新機制。工具鏈過時的偵測與更換依賴維護者
  主動處理。
- 決定五的優先序無法處理「使用者手動指定的路徑指向一個殘缺或版本不符
  的 SDK」。該情形下工具應在使用前驗證所指定路徑確實含有可執行的
  `makeappx`／`signtool`，但無法驗證其版本是否適用。

## 待辦事項

1. 決定取得指令的具體形式（獨立子指令或既有指令的旗標）與設定欄位名稱。
2. 取得並寫入固定版本的 SHA-256 雜湊值，並加註更換版本的維護說明。
3. 實作路徑驗證：使用任何來源之前確認該路徑確實含可執行的所需工具。
