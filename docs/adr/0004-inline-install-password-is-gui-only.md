# ADR-0004：直接輸入的安裝密碼只存在於配置精靈，設定檔一律拒絕

## 狀態

已接受（2026-08-29 決定）。

## 背景

安裝密碼保護（見 [`CONTEXT.md`](../../CONTEXT.md)「安裝密碼保護」一節）在
[ADR 之前的設計](../../CONTEXT.md)裡只有一種指定密碼的方式：設定欄位
`install_password_env` 填一個**環境變數名稱**，密碼本身放在該環境變數裡，
打包當下才讀出來。理由是設定檔是一份普通的 JSON 文字檔，會被存進專案、
傳給同事、上傳到版本控制——密碼寫在裡面等於整個保護失效。這個做法比照
既有的 `signing.cert_password_env`。

這個功能在 CLI、打包驗證、`builder.py` 加密、安裝端密碼關卡、靜默安裝
`/PASSWORD=` 參數都已完成，唯獨 `ui/config.html` 沒有對應欄位，GUI 使用者
無法使用（跨模組一致性稽核 F14）。補這個欄位時浮現一個取捨。

環境變數這條路對 GUI 使用者的門檻明顯高於其他欄位：其他欄位都是打字或
選檔案，這一個要先離開工具、到作業系統設定裡建立一個環境變數、而且設定
完還得重新啟動工具才讀得到（環境變數不會即時傳播到已經在執行的行程）。
配置精靈的定位是「點一點就把安裝檔做出來」，這道門檻與定位不符。

但如果讓「直接輸入密碼」變成一個一般欄位，它就會落進
`validate_and_build_pack_data()` 收的那包 `data` 裡——**而 GUI 與 CLI 共用
同一個驗證函式，`data` 的欄位集合就是設定檔的格式**。等於同時讓設定檔
也能寫明文密碼，把當初繞環境變數要避開的風險原封不動放回來。

## 決定

### 一、配置精靈提供兩種填法，設定檔只支援其中一種

配置精靈的「啟用安裝密碼保護」區塊提供二選一：

| 填法 | 配置精靈 | 設定檔（CLI） |
|---|---|---|
| 直接輸入密碼 | ✅ 預設 | ❌ 拒絕 |
| 填環境變數名稱（`install_password_env`） | ✅ | ✅ |

兩條路的能力不對等是這個決定的核心，不是遺漏。

### 二、直接輸入的密碼不進入 `data`，也不進入 `pack_data`

密碼以獨立參數往下傳：`ConfigAPI.start_pack(data, install_password)` →
`builder.build_all(..., install_password=...)`。它不是 `data` 的一個 key，
因此不在設定檔格式裡；也不寫回 `pack_data`，因此不會出現在任何可能被
序列化的結構中。

`validate_and_build_pack_data()` 只收到一個布林值
（`has_inline_password`），知道「這次有沒有用直接輸入」就足以做驗證，
不需要看到密碼本身。這個純函式因此維持「只處理設定值」的性質。

不採用「配置精靈自己在背後建立一個臨時環境變數、再走原本那條路」的方案。
那個做法完全不用改打包端，看起來更省事，但打包過程會叫起 PyInstaller 等
子行程，子行程會繼承整個環境變數區塊，等於把明文密碼交給每一個子行程；
而且「畫面上寫著 A、底下偷偷變成 B」這種轉換，下一個讀程式碼的人沒有線索
可以理解為什麼。

### 三、設定檔裡出現直接寫密碼的欄位時明白報錯

`validate_and_build_pack_data()` 偵測到 `data` 裡有 `install_password`
這個 key 就回傳明確的錯誤訊息，指向 `install_password_env`。

不採用「不認得的欄位本來就會被忽略」的處理方式。這個專案已經修過好幾次
「使用者以為設定生效了、其實被默默忽略」的缺陷（`dependencies_min_version`
沒跟 `dependencies` 交叉比對、`doc_icons` 沒跟 `file_associations` 交叉
比對），而這一項被忽略的後果特別嚴重：使用者以為自己的安裝檔有密碼保護，
實際上完全沒有，而且要等到把安裝檔發出去才可能發現。

### 四、加密所需的第三方套件在產生任何副作用之前檢查

加密實作（`install_encryption.py`）依賴 `cryptography`，該 import 位於
函式內部而非檔案頂端。`build_all()` 的執行順序是「清空 `dist/`／`build/`
→ 編譯 `uninstall.exe`（數十秒）→ 加密」，套件缺少時使用者會白等完整段
編譯、產物也已被清空，最後才收到一個 ImportError。

改為在 `validate_and_build_pack_data()` 內檢查：只有在這次真的要用密碼
保護時才視為缺少。這與 ADR-0003 第三點（版本號格式驗證前移）是同一個
原則——純函式的職責就是在任何檔案系統副作用發生之前攔截設定錯誤。

## 後果

- 配置精靈使用者不需要碰環境變數就能用這個功能，預設就是直接輸入。
- 設定檔永遠不可能含有明文的安裝密碼，不論使用者從哪一條路進來。
- 兩條路的能力不對等，需要在說明文字、`CLI_USAGE.md`、以及本 ADR 三處
  說明理由，否則會被誤判成漏做。
- 「直接輸入」這條路無法被寫進設定檔，也就無法納入可重複執行的自動化
  流程（CI／批次打包）。需要自動化的使用者只能用環境變數那條路——這正是
  環境變數那條路存在的情境，兩者的適用場合本來就不同。
- `build_all()` 取得密碼的來源從一種變成兩種（參數或環境變數），多一行
  判斷。

## 已知限制

- 直接輸入的密碼在打包期間以字串形式存在於工具行程的記憶體中，沒有做
  任何抹除。這與本功能的定位一致（存取控制，不是防範有心人的資安機制，
  見 `CONTEXT.md`）——能讀取這個行程記憶體的人，本來就能讀到更多東西。
- 工具無法驗證使用者輸入的密碼是不是打錯了（沒有可以比對的來源），打錯
  的後果是產出一顆沒有人打得開的安裝檔，而且通常要到發布之後才會發現。
  緩解措施只有輸入框旁邊的「顯示」切換，讓使用者自己確認。不採用「再
  輸入一次」的二次確認欄位：兩次都貼上同一個打錯的內容並不罕見，防護
  效果有限，卻要多一個欄位與一條驗證規則。
