# ADR-0006：MSIX 模式不提供自訂解除安裝介面

## 狀態

已接受（2026-08-31 決定）。決定範圍屬於尚未實作的 MSIX 輸出功能，
規劃見 [`docs/proposals/MSIX輸出規劃.md`](../proposals/MSIX輸出規劃.md)。

## 背景

本專案的識別由兩個對稱的手勢構成，兩者皆記錄於
[`CONTEXT.md`](../../CONTEXT.md)：安裝端把應用程式圖示拖曳至資料夾圖示
（拖曳安裝），解除安裝端把應用程式圖示拖曳至垃圾桶圖示（比照 macOS 將
應用程式拖入 Dock 垃圾桶的原生手勢，見 `ui/uninstall.html`）。

傳統引擎下，解除安裝介面之所以能夠存在，是因為安裝流程在
`SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall\<app_name>` 寫入
`UninstallString`，指向本專案產出的 `uninstall.exe`
（`installer_core.py:509`）。使用者於 Windows 的應用程式清單點選解除安裝
時，系統呼叫的即是該 exe，控制權因此回到本專案手中。

MSIX 套件的解除安裝由系統的套件引擎全權接管。套件清單不提供等同於
`UninstallString` 的欄位，無法將解除安裝動作重新導向至自訂程式；使用者在
系統介面點選解除安裝時，執行的是系統自身的套件移除流程。

此處存在一項不對稱，且該不對稱不可經由設計消除：安裝端的介面之所以得以
保留，是因為使用者雙擊的是本專案產出的 `Setup.exe`，本專案先取得控制權、
顯示完整介面之後才將部署工作交付系統；解除安裝端沒有對應的進入點，動作
由 Windows 自身的介面發起，本專案的程式碼不在執行路徑上。

## 決定

### 一、MSIX 模式不提供自訂解除安裝介面

MSIX 模式的解除安裝完全交由 Windows 處理，不產生 `uninstall.exe`，不寫入
解除安裝登錄表項目（該項目由套件清單自動產生）。垃圾桶拖曳手勢僅存在於
傳統引擎模式。

考慮過但未採用的替代方案有二：

**方案甲：將自訂解除安裝程式包入套件，保留垃圾桶手勢，由其請求系統移除
自身套件。** 不採用，因為它產生兩條並存且體驗不同的解除安裝路徑——使用者
亦可直接由 Windows 的應用程式清單發起移除，該路徑無法被攔截。同一操作
出現兩種不同介面，較諸單一的系統介面更不一致。此外，執行中的程式請求
系統移除自身所在套件，在套件模型下屬於邊界情況，可靠度低於本專案其他
部分。

**方案乙：於開始選單放置捷徑，指向 Windows 的應用程式清單頁面。** 不採用，
因為它所節省的僅為使用者開啟系統設定的數次點擊，而需長期維護一個開始
選單項目，效益與成本不相稱。

### 二、此決定的代價已被明確接受

MSIX 模式下，本專案的識別僅存在於安裝端。此代價在決策當下已被完整陳述並
接受，不屬於實作過程中被忽略或延後處理的事項。記錄此點的目的，是避免
後續維護者將「MSIX 模式沒有垃圾桶畫面」誤判為未完成的功能缺口而著手補上。

## 後果

- 使用者在 MSIX 模式下體驗到的流程為：安裝時是 macOS 風格的拖曳介面，
  解除安裝時是 Windows 的標準介面。
- `ui/uninstall.html`、`uninstall.py`、`self_delete.py` 等解除安裝端模組
  在 MSIX 模式的建置流程中不參與，該模式的產出物不含 `uninstall.exe`。
- 傳統引擎模式不受本決定影響，維持現狀。

## 已知限制

- 本決定使 MSIX 模式與傳統模式在使用者體驗上不對等。若後續判定該不對等
  不可接受，可行的處置是重新評估 MSIX 輸出功能整體是否值得保留，而非
  在此決定上尋求折衷——方案甲與方案乙已於決定一評估並排除。
