# ADR-0012：WebView2 Runtime 在建立視窗之前偵測，三個進入點的處置刻意不同

- 狀態：已定案
- 日期：2026-09-04
- 相關：`docs/investigations/CI與本機虛擬機的能力對比.md`（實測結果）、
  [ADR-0011](0011-engine-messages-are-translatable-keys.md)（訊息表的慣例）

## 背景

安裝介面、解除安裝介面與配置精靈都是 pywebview 程式，三者都依賴 Windows 的
Microsoft Edge WebView2 Runtime 渲染畫面。該元件在 Windows 11 與近期更新過的
Windows 10 上內建，較舊、未更新的 Windows 10 可能沒有。

2026-09-03 於 Windows 10 Enterprise LTSC 2019（組建 17763.316，未安裝該元件）
實測，實際行為與文件原先的推論不同：

- 視窗**會**開啟，但 CSS 與 JavaScript 都不生效——原本左右並排的應用程式圖示
  與安裝目的地塌成由上而下堆疊並溢出視窗，箭頭、核取方塊與關閉鈕皆不可見，
  應用程式名稱停在 `ui/index.html` 的預設佔位文字「載入中...」。
- **全程不顯示任何錯誤訊息，行程也不結束。**

使用者看到的是一個像是還在載入的畫面，會一直等下去。這比空白視窗更不利：
空白至少看得出壞了。同一顆安裝檔在已安裝該元件的 Windows 11 上畫面完整可
操作，因此差異確定來自這個系統元件。

原先的文件記載為「畫面會直接空白或報錯」，該敘述來自推論，已依實測更正。

## 決定

### 一、偵測放在建立視窗之前，且不使用既有的相依元件機制

`dependency_install.py` 已有一套「偵測使用者缺什麼 → 下載 → 驗證 → 靜默安裝」
的機制，WebView2 Runtime 的形狀與它處理的 VC++／.NET 相同。**但不能沿用。**

那套機制的偵測結果、詢問畫面與安裝進度全都呈現在 `ui/index.html`（見該檔的
「相依元件自動安裝頁」），而 `get_dependency_warnings()` 是 `js_api` 方法
——由網頁呼叫 Python，不是 Python 主動顯示。缺少 WebView2 時打不開的正是那個
頁面：雞生蛋。

因此偵測與處置全程在 Python 內完成，不碰 HTML，只重用那套機制的概念（登錄表
偵測、下載後執行），實作獨立於 `webview2_runtime.py`。

判斷依微軟文件，讀 `EdgeUpdate\Clients\{F3017226-FE2A-4295-8BDF-00C3A9A7E4C5}`
的 `pv`，**三個位置都查**：64 位元的 `WOW6432Node`、32 位元的原生路徑，以及
`HKCU`（使用者層級安裝）。只查 `HKLM` 會把使用者層級的安裝誤判成沒裝，然後
對著一台已經有 WebView2 的機器要求重裝。`pv` 為空或 `0.0.0.0` 視為未安裝
——EdgeUpdate 會留下後者那種空殼機碼。

### 二、三個進入點的處置不同，這是刻度差異而非遺漏

| 進入點 | 處置 | 為什麼 |
|---|---|---|
| `Setup_XXX.exe` | 詢問後代為下載安裝 | 使用者要靠這個畫面決定裝到哪、要不要捷徑，沒有它就無法完成安裝 |
| `uninstall.exe` | 確認後改走既有的 `--silent` 路徑 | 為了移除一個軟體而先叫使用者裝一個執行階段並不合理；解除安裝沒有非問不可的選擇，原生對話框足夠 |
| `InstallerBuilder.exe` | 只告知，不代勞 | 使用者是開發者，本來就被要求自行安裝 Python 與 PyInstaller；與該工具既有的環境檢查哲學一致 |

**不要「順手改成一致」。** 三者的差異來自使用者是誰、以及那個畫面對他而言是
不是必要的。

解除安裝這條路真的走得到：靜默安裝不建立視窗，因此一台沒有 WebView2 的機器
可以合法地裝好程式，而「設定 → 應用程式」的解除安裝按鈕用的是
`UninstallString`（有畫面的那個），不是 `QuietUninstallString`。

### 三、取得方式為 Evergreen 載入器，且不傳 `/silent`

微軟的 Evergreen 載入器實測 1.7 MB，由它負責下載並安裝真正的執行階段。
執行時**不傳 `/silent`**：安裝端沒有可用的畫面能自行顯示進度——HTML 打不開
（那正是缺少這個元件的後果），Tkinter 不在安裝檔裡
（`installer_core._show_starting_cursor()` 記載了「使用者要求安裝檔本身盡量
簡潔」這個決定，當初連 splash 視窗都因此拿掉）。讓微軟的安裝程式顯示它自己的
進度介面，是唯一不必自行實作進度視窗的做法。

### 四、不做離線內嵌

微軟另有離線的獨立安裝程式，實測 **246.5 MB**。內嵌會讓每一顆安裝檔膨脹約
六倍（目前約 44 MB）去換極少數環境，而真正需要離線部署的人走的是靜默安裝
——那條路不建立視窗，這個問題對他們不存在。

此項不列為待辦：不是「還沒做」，是評估後決定不做。日後若要加，接縫在
`webview2_runtime.acquire()`，把「從網路下載載入器」換成「從內嵌資源取出獨立
安裝程式」即可，不需要重新設計。

### 五、不提供設定欄位

不新增 `installer_config.json` 欄位讓打包者關閉此行為。關閉之後的行為與保底
路徑相同（跳一個「缺這個元件，請自行安裝」的對話框），因此該欄位省下的只有
「要不要問使用者一句」；而新增一個欄位的代價是 GUI 表單、CLI 文件、欄位驗證、
MSIX 的四類分類與使用說明書都要跟著動。

行為本身不會偷偷進行：它是跳對話框徵詢使用者，使用者可以拒絕。真正在意
「不要連外」的是使用者，而使用者已經有否決權。

### 六、不做備用介面

評估過兩種備用介面，兩者皆不採用：

- **Tkinter 表單**：Tkinter 目前不在安裝檔裡，加入會讓**每一顆**安裝檔變大去
  換極少數環境；而且做不出拖曳安裝，那是這個專案的核心識別。
- **為舊引擎另寫一份簡化 HTML**：等於維護第二套前端，且兩套必須同步。第二套
  平常沒有人使用、沒有人測試，改第一套時很容易忘記，等到真的需要它時才會發現
  它早已不能用。

## 後果

- 缺少該元件時，使用者得到的是一段說明與一個選擇，而不是一個永遠停在載入中的
  畫面。
- 安裝端多一個對外的網路行為（下載 1.7 MB 的載入器），且該行為需要使用者同意。
- 三個進入點的處置不一致，維護者若不讀本 ADR 會傾向把它們統一。
- `webview2_runtime.py` 與 `messages.py` 加入 `SHARED_DEEP_MODULES`：偵測必須
  在建立視窗之前完成，這兩支不能只存在於打包端。

## 已知限制

- 對話框以 `MessageBoxW` 顯示，其中的網址不可點選，使用者只能照著輸入。緩解
  方式是同時以預設瀏覽器開啟下載頁面，但該動作失敗時沒有補救。
- 靜默安裝（`/S`）不受此機制影響——它在建立視窗之前就結束了。一台沒有
  WebView2 的機器仍然可以靜默安裝成功，隨後才在互動式解除安裝時遇到本 ADR
  決定二的處置。
- 偵測依賴登錄表。若某種安裝方式沒有寫入 `EdgeUpdate\Clients` 的 `pv`，會被
  誤判為未安裝；目前沒有已知的這種情況。

## 已完成之待辦

- 於 Windows 10 1809 虛擬機驗證「安裝執行階段之後，同一個行程直接呼叫
  `webview.start()` 能否成功」。**實測成立**（2026-09-04，Windows 10
  Enterprise LTSC 2019 17763.316 en-US，事前確認機器上無 WebView2）：於對話框
  按下確認後，Microsoft 的載入器完成安裝並自行結束，同一個安裝檔行程隨即開出
  拖曳安裝視窗，未經重新執行，其後的安裝流程亦正常完成。此結果確認 pywebview
  於 `webview.start()` 當下才載入 WebView2 的 loader，自動繼續的前提成立。
