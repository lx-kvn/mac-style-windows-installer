# ADR-0015：MSIX 模式的降版須經使用者同意，靜默安裝除外

## 狀態

已接受（2026-09-05 決定）。尚未實作。決定所依據的行為事實取自同日於
Windows 11 25H2（26200、zh-TW）的實機量測，量測經過見
[`docs/investigations/MSIX稽核與缺陷修正.md`](../investigations/MSIX稽核與缺陷修正.md)
的 D3。

## 背景

MSIX 引擎的安裝流程原本只偵測**傳統模式**的既有安裝（讀取解除安裝登錄表），
對「同一個套件身分已經以 MSIX 裝過」的情形完全沒有分支。

實機量測取得以下事實，其中第二項推翻了稽核當時的推測：

| 情境 | 結果 | 錯誤碼 |
| --- | --- | --- |
| 乾淨機器安裝 | 成功 | — |
| 同版本重新安裝 | **成功**（系統重新註冊） | — |
| **降版安裝** | **失敗** | `0x80073D06` |
| 升版安裝 | 成功（就地更新） | — |
| 憑證不受信任（對照組） | 失敗 | `0x800B0109` |

唯一的失敗情境為降版，其錯誤碼明確且與其他失敗原因可區分。因此「部署失敗
即移除舊套件再重試一次」在技術上不會誤傷憑證或磁碟空間造成的失敗——判準
成立，剩下的是產品決定。

該產品決定的核心在於一件 MSIX 特有的事：**系統移除套件時會連同該應用程式
的資料一併清除**，那正是採用 MSIX 的理由（保證乾淨解除安裝）本身。傳統
引擎的降版覆蓋不具此後果。

傳統引擎對降版已有既定處置：`upgrade.check_existing()` 將比較結果分為
「較新／相同／較舊」三種互斥情形，其中「較舊」由前端以警示樣式呈現，其
註釋載明「明確告知使用者要裝的版本比較舊，讓使用者自己決定要不要繼續」。
降版本身是允許的，但須經使用者確認。

## 決定

### 一、部署前先偵測並比較版本，比照傳統引擎的三分法

MSIX 引擎在交付系統部署之前，先查詢同一套件身分是否已安裝，並將已安裝
版本與本次版本比較，得出與 `upgrade.check_existing()` 相同的三種結果。

不沿用「先部署，失敗再處理」：那使「要不要降版」這個決定發生在一次已經
失敗的操作之後，而使用者此時看到的是系統的錯誤訊息，不是一個他可以回答的
問題。

### 二、降版須經使用者同意，且警示須說明資料會被清除

偵測到本次版本較舊時，前端以警示樣式告知，使用者確認後才移除既有套件並
安裝。警示文字須包含一項傳統引擎不需要說明的事：移除將連同該應用程式的
資料一併清除。

不採用「一律拒絕降版」：傳統引擎允許降版，兩種引擎在同一件事上行為不同會
使下游專案難以預期。亦不採用「自動移除不詢問」：那使使用者的資料在其未
同意的情況下被清除。

### 三、靜默安裝直接覆蓋，不另設旗標

靜默安裝（`/S`）偵測到降版時直接移除並安裝，不中止、不要求額外旗標，並將
「偵測到已安裝版本 X、本次安裝 Y、舊版連同其資料將被移除」寫入靜默安裝
紀錄檔。

曾考慮新增 `/ALLOWDOWNGRADE` 旗標，缺少該旗標即中止。未採用的理由是兩種
引擎的靜默行為將因此分岔：同一份部署腳本自傳統引擎改用 MSIX 引擎會突然
失敗，而靜默安裝的呼叫端本就以「不要詢問」為前提。此取捨接受一項代價：
資料被清除一事僅能於事後自紀錄檔得知。

### 四、發行者不同的同名套件只警示，不自動移除

套件身分由「名稱 + 發行者」共同構成。打包者更換簽章憑證（例如自簽換發為
公開 CA 簽發）時名稱不變而發行者改變，系統將兩者視為互不相關的應用程式並
存安裝。

偵測到同名但發行者不同的既有套件時，告知使用者兩者將並存，但不自動移除：
該套件確有可能屬於另一個開發者的應用程式，工具不代使用者判定兩者為同一個
應用程式。

此項與決定二的差別在於系統的判定：降版的兩者在系統眼中是同一個應用程式，
發行者不同的兩者不是。

## 已知限制

- 決定四僅止於告知。使用者若確實要移除舊發行者的套件，須自行至
  「設定 → 應用程式」處理。
- 版本比較所需的本次套件版本由打包端寫入 `installer_config.json`，比照
  `msix_identity_name` 的作法。修正之前編出的安裝檔沒有該欄位，其行為維持
  修正前的樣子（不比較版本，僅於失敗時說明）。
