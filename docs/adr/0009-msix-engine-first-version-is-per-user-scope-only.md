# ADR-0009：MSIX 引擎第一版只提供「當前使用者」使用者範圍，不提供「全機器」

## 狀態

已接受（2026-08-31 決定），**部分經 [ADR-0013](0013-msix-all-users-scope-is-an-opt-in-field.md)
取代**（2026-09-04）：決定一由該 ADR 取代，決定三的適用範圍由該 ADR 決定四
限縮，決定二隨決定一失效，決定四維持有效。本文件保留為第一版範圍的紀錄。

決定二與決定四的欄位分類已實作於 `install_engine.py`（見「已完成之待辦」），
決定一與決定三未進入實作即被取代。決定範圍屬於 MSIX 輸出功能，規劃見
[`docs/proposals/MSIX輸出規劃.md`](../proposals/MSIX輸出規劃.md)。

## 背景

「應用程式的檔案落在哪裡」與「這台電腦上哪些使用者用得到它」是兩件不同的
事，詞彙見 [`CONTEXT.md`](../../CONTEXT.md)「安裝路徑與使用者範圍」一節。
傳統引擎把兩者綁在同一個選擇上——打包時的「安裝位置三選一」
（`ui/config.html` 的 `isNoAdminInstall()`，對外是 `no_admin_install` 欄位）
同時決定安裝路徑與使用者範圍，無法分開設定。

MSIX 打斷這個焊點：安裝路徑由系統決定、不可選擇（此點無爭議）；使用者範圍
仍然可選，但改由部署時採用哪一個系統 API 決定。

規劃文件第二輪決議第七項將 `no_admin_install` 整項列為第一類（無阻礙），
第五輪修正並確認「該欄位確實成為 MSIX 的預設行為」。第七輪的逐項重新檢查
發現該判斷只涵蓋一側：

- `no_admin_install=true`（當前使用者範圍）——第一類成立，MSIX 的預設行為
  即是。
- `no_admin_install=false`（**預設值**；全機器範圍）——第二類。
  `PackageManager.AddPackageAsync` 僅為當前使用者安裝；要讓機器上所有使用者
  都能使用，須改用 `ProvisionPackageForAllUsersAsync`。

`ProvisionPackageForAllUsersAsync` 有三項前置條件，皆經官方文件確認：**呼叫端
須具備系統管理員權限**、**套件須先經過 stage**、**套件須位於系統磁碟區**。
部署動作因此從一次呼叫變成兩段流程。其中的管理員權限一項不構成新的能力
需求——bootstrapper 已具備完整的跨 UAC 提權機制（`upgrade.py` 的
`ShellExecuteExW` 搭配 `runas` 動詞），第二輪決議第九項的「安裝前偵測並移除
傳統模式的既有安裝」即會使用它。

此發現的份量不在單一欄位的歸類，而在於**第二輪決議第八項的適用範圍**。第八項
規定第一版限於第一類、第二類一律報錯，其成立前提是「第二類為少數人使用的
進階功能」。但全機器範圍對應的是 `no_admin_install` 的**預設值**，代表未主動
變更該設定的下游專案在 MSIX 模式下都會直接撞上報錯——第二類在此不是進階功能
的分支，而是預設路徑。

## 決定

### 一、第一版的 MSIX 引擎只提供「當前使用者」範圍

**本項已由 ADR-0013 決定一取代。** 全機器範圍改以明確欄位 `msix.all_users`
啟用，預設仍為當前使用者範圍。以下敘述保留為第一版範圍的紀錄。

不於第一版實作 `ProvisionPackageForAllUsersAsync` 這條路徑。

理由是代價與第一版的目的不相稱：實作它需要一套兩段部署流程（stage 後再
provision）、需要在部署階段提權、需要處理「套件須位於系統磁碟區」這項前置
條件，且第三輪 spike 未驗證 `winrt-*` 綁定套件是否暴露該方法。這些工作與
採用 MSIX 的目的（由系統保證解除安裝乾淨）無關，屬於為了覆蓋既有功能面而
增加的工程量。

此決定使兩個引擎的取捨對下游專案成為一句可判斷的話：**需要系統保證解除安裝
乾淨，選 MSIX 引擎，代價是只安裝給當前使用者；需要機器上所有使用者共用，選
傳統引擎，代價是解除安裝的乾淨程度取決於安裝清單記得夠不夠完整。**

### 二、設定要求全機器範圍時報錯，語氣為第二類並附替代方案

錯誤訊息採第二輪決議第八項的第二類語氣（「目前尚未支援」），並附加一句指向
傳統引擎。

不將其歸為第三類（格式限制），理由是那不誠實：MSIX 做得到全機器，
`ProvisionPackageForAllUsersAsync` 就在那裡，本決定只是不於第一版實作。以
「格式限制」描述一個暫時的實作範圍，會使後續維護者認定此路不通而不再考慮。

不為此新增第三種訊息語氣（「本引擎不提供，另一引擎可以」）。第八項的兩種
語氣分的是「等待本工具補上」與「立即重新設計」，本項仍屬前者——附加的替代
方案只是告知等待期間有路可走，不改變其性質。目前僅此一例，為單一案例新增
類別過早；日後若出現第二個「兩個引擎能力不同」的欄位，屆時再立規則。

### 三、不採用靜默降級為當前使用者範圍

**本項的適用範圍已由 ADR-0013 決定四限縮為「設定層面的降級」**——即工具在
設定要求全機器時，自行改以當前使用者範圍產出。安裝階段因該台機器無法取得
管理員權限而降級、並於完成畫面向終端使用者說明實際發生的事，不在本項的否決
範圍內；該情形的理由見 ADR-0013 決定四。

不採用「設定為全機器時仍然部署，僅降級為當前使用者」的作法，即使搭配建置
訊息說明亦然。

此作法曾被考慮，理由是它避免把預設設定的下游專案擋在門外。否決的理由是它
不符合第五輪所立的第四類判準：第四類要求「指令無法執行」與「使用者的目的
已達成」兩個條件同時成立，而此處後者不成立——「機器上所有使用者共用同一份
安裝」這個目的並未達成。後果會落在終端使用者身上：第二位使用者登入時應用
程式不存在，而該現象要到那個時點才顯現，正是第二輪決議第八項所述「功能被
無聲移除，後果要到終端使用者安裝完畢後才顯現」的情形。

此處記錄否決的理由，是因為該作法在成本上明顯優於報錯，日後極可能被重新
提出。

### 四、MSIX 的類別檢查一次列出全部違規項

不沿用 `validate_and_build_pack_data()` 既有的「第一個錯誤即回傳」慣例
（`packaging_core.py` 現行所有欄位驗證皆如此）。

理由是兩種錯誤的性質不同。既有的欄位驗證回報的是「這個值填錯了」，逐項修正
即可，一次一條沒有問題。MSIX 的類別檢查回報的是「這份設定與這個引擎不相容」，
而下游專案需要判斷的是「切換引擎對本專案是否划算」——該判斷需要完整清單。
逐條回報會使對方每修正一項就重跑一次建置，且在看到最後一項之前無從得知總
代價，存在「修正四項後發現第五項無解、整個決定作廢」的情形。

實作方式為在 MSIX 的類別檢查區段內部累積違規項，組成一則多行訊息後回傳，
不變更 `validate_and_build_pack_data()` 的回傳形狀——該函式為 GUI 與 CLI
共用，變更簽章會波及兩個呼叫端。

## 後果

- MSIX 引擎第一版的服務對象限於「當前使用者範圍即可滿足」的下游專案。由於
  `no_admin_install` 的預設值為 `false`，多數既有設定需要一次明確的變更才能
  使用 MSIX 引擎。
- 兩個引擎的差異不再限於實作機制，而包含一項終端使用者可察覺的行為差異
  （見「已知限制」）。`CONTEXT.md` 對兩者差異的既有敘述須隨之修正。
- 全機器範圍成為第一版之後的候選項目，其實作路徑與前置條件已於本文件記錄，
  屆時不需重新調查。

## 已知限制

- 本決定使 `CONTEXT.md`「傳統引擎與 MSIX 引擎」一節原有的兩項敘述失效：
  「終端使用者不需要知道自己拿到的是哪一種」與「使用者介面上的可見差異只有
  兩處」。在多人共用的電腦上，第二位使用者登入後應用程式是否存在，是終端
  使用者直接察覺的差異，且該差異不在介面上，而在安裝完成之後。
- 決定一未經實測驗證的部分：`winrt-*` 綁定套件是否暴露
  `ProvisionPackageForAllUsersAsync`。**此項已於 2026-09-04 確認**：該方法
  與 `stage_package_async`、`deprovision_package_for_all_users_async`、
  `find_provisioned_packages` 皆存在於綁定套件中（見 ADR-0013 背景第一項）。
- 決定四的「一次列出全部」僅涵蓋 MSIX 的類別檢查。同一次建置若另有既有欄位
  驗證失敗，仍依既有慣例於第一個錯誤即回傳，兩種呈現方式並存。此不一致為
  刻意保留的範圍界線，理由是既有驗證的逐項回報並無問題，變更它屬於不相關的
  改動。
