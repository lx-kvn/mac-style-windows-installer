# 安裝軟體生成器 — 使用說明書

把任何應用程式打包成一個 macOS 風格拖曳安裝視窗的 Windows 安裝檔工具。

> 這份文件講的是**圖形介面**（`InstallerBuilder.exe`/`gui_config.py`）的用法。
> 如果你想用**命令列**操作打包（例如寫在 CI 腳本裡、不想開視窗），改看
> [`CLI_USAGE.md`](CLI_USAGE.md)——核心邏輯完全共用，只是介面跟操作方式不同。

---

## 1. 整個工具鏈長什麼樣子

這套工具會產出**三顆獨立的 exe**，職責完全不同，先分清楚：

| exe | 誰在用 | 由哪支原始碼編譯 | 有沒有 loading 回饋 |
|---|---|---|---|
| `InstallerBuilder.exe` | **你自己**，拿來製作安裝檔的工具本體 | `gui_config.py` | 有，開啟時跳出一個持續轉動的 Tkinter 小視窗 |
| `Setup_XXX.exe`（你自訂檔名） | **終端使用者**，雙擊這個來裝軟體 | `installer_core.py` | 有，游標會先顯示 Windows 內建的「載入中」小圈圈，直到視窗跳出來 |
| `uninstall.exe` | 使用者要移除軟體時用，安裝時自動放進安裝目錄 | `uninstall.py` | 有，跟 `Setup_XXX.exe` 同一套 macOS 風格拖曳視窗介面（拖曳應用程式圖示到垃圾桶＝解除安裝），不再是純文字的主控台視窗 |

`InstallerBuilder.exe` 執行「開始編譯安裝檔」時，會**再呼叫一次系統上的 `pyinstaller` 指令**去現場編譯出 `Setup_XXX.exe` 和 `uninstall.exe`。這代表：**操作 `InstallerBuilder.exe` 的這台電腦，本身要先裝好 Python + PyInstaller**，即使 `InstallerBuilder.exe` 本身已經是一顆獨立 exe 也一樣——它只是把自己的操作介面包成 exe，不是把「編譯」這件事也內建進去。

而你**編譯出來、發給使用者的東西**（`Setup_XXX.exe`、`uninstall.exe`）才是完全獨立的，使用者的電腦不需要裝任何 Python 環境。唯一的例外是 **WebView2 Runtime**（Windows 系統元件，不是 Python 套件）：Windows 11 跟近期更新過的 Windows 10 通常已經內建，比較舊、沒更新過的 Windows 10 可能會缺。

缺少時的實際行為已於 2026-09-03 實測（Windows 10 Enterprise LTSC 2019，組建 17763.316，未安裝 WebView2 Runtime）：**安裝視窗會開啟，但版面沒有正確套用**——原本左右並排的應用程式圖示與安裝目的地變成由上而下堆疊並超出視窗範圍，中間的箭頭、底部的核取方塊與關閉鈕都看不到；應用程式名稱那一格停在預設佔位文字「載入中...」，不會被填入實際名稱。全程不顯示任何錯誤訊息，行程也不會結束。

也就是說 CSS 與 JavaScript 都沒有正常運作。畫面看起來像是還在載入，使用者無從得知缺少的是什麼。同一顆安裝檔在 Windows 11（已安裝 WebView2 Runtime）上畫面完整可操作，因此差異確定來自這個系統元件。

散布給不特定使用者前，建議在說明文件裡提醒對方視情況安裝 [WebView2 Runtime](https://developer.microsoft.com/microsoft-edge/webview2/)。

## 2. 環境需求

操作 `gui_config.py` / `InstallerBuilder.exe` 這台電腦上要有：

```
pip install pyinstaller pywebview pywin32 cryptography
```

- `pyinstaller`、`pywebview` 是硬性需求，缺少會被 `InstallerBuilder.exe` 開啟時的環境檢查擋下來，並跳出提示視窗附安裝指令。
- `pywin32` 是選用，只影響「建立開始功能表 / 桌面捷徑」這個功能，缺少不會擋住編譯，只是裝出來的軟體會少了捷徑。

### 終端使用者那端需要什麼

傳統引擎沒有額外要求，安裝檔是自足的。

**MSIX 引擎有兩項要求**，而且是使用者那台電腦要滿足，不是你這台：

1. **憑證要被信任。** 未簽章、或簽章憑證不被那台電腦信任的套件，系統直接
   拒絕安裝。自簽憑證是開發測試用的，不是散布方案——真的要發給別人，需要
   公開憑證機構的程式碼簽署憑證、或走 Microsoft Store。**這個工具不會、也
   不應該幫使用者把憑證裝進信任存放區**（見 `docs/adr/0005`）：那等於安裝檔
   自己決定「我值得被信任」，那個決定必須由使用者做。
2. **Windows 10 2004 之前的企業版／教育版／LTSC 需要先開啟側載。** 那幾個
   版本預設關閉側載，使用者要到「設定 → 更新與安全性 → 開發人員專用」開啟
   之後才裝得起來。2004 之後的版本、以及一般的家用版／專業版預設就是開的。
   最低支援版本本身是 `10.0.17763.0`（Windows 10 1809）。

   > 這一項的依據是微軟的官方文件，**尚未實機驗證**——本專案目前沒有
   > Windows 10 1809 的測試環境。

## 3. 檔案結構

```
你的工作資料夾/
├── gui_config.py          製作工具本體（後端 API）
├── builder.py              實際執行編譯流程的模組
├── splash.py                載入畫面的統一介面
├── splash_helper.py         獨立的載入畫面小程式（splash.py 會呼叫它）
├── installer_core.py       安裝端邏輯（會被編譯進 Setup_XXX.exe）
├── uninstall.py             解除安裝邏輯（會被編譯進 uninstall.exe）
├── build_config_tool.py     把 gui_config.py 打包成 InstallerBuilder.exe 的建置小工具
├── ui/
│   ├── config.html           製作工具的操作介面
│   ├── index.html            安裝視窗的介面（會被打包進 Setup_XXX.exe）
│   └── folder_icon.png       安裝視窗右側的資料夾圖示（原創設計，非商標）
└── splash.png                （已不再使用，可留可刪，載入畫面改用 splash_helper.py）
```

`InstallerBuilder.exe` 打包時（`build_config_tool.py`）會把 `installer_core.py`、`uninstall.py`、`splash_helper.py`、整個 `ui/` 資料夾都內嵌進去。**第一次執行 `InstallerBuilder.exe` 時，如果它所在的資料夾缺這些檔案，會自動從內嵌資源解壓出來**，不需要手動複製。

---

## 4. 怎麼打包 `InstallerBuilder.exe`

```
python build_config_tool.py
```

會跳出一個 GUI（不是純指令稿），可以選 `.ico` 自訂輸出圖示，有即時打包進度與 log。打包完的 `InstallerBuilder.exe` 在 `dist/` 資料夾底下。

**把這顆 exe 放到你自己有完整寫入權限的資料夾**（例如 `D:\my-installer-workspace\`），不要放在 `C:\Program Files` 這類系統保護路徑底下，因為它執行時要在自己所在的資料夾寫入解壓出來的檔案跟編譯產物。

## 5. 怎麼用 `InstallerBuilder.exe`（或直接 `python gui_config.py`）製作安裝檔

開啟後填寫以下欄位：

| 欄位 | 說明 |
|---|---|
| 安裝引擎 | 決定安裝檔內部用哪一種方式把檔案放到使用者電腦上：**傳統引擎**（預設）由 `Setup_XXX.exe` 自己複製檔案、寫登錄表，並附一支解除安裝程式；**MSIX 引擎**改交給 Windows 的套件引擎，由系統保證解除安裝乾淨。兩者的完整差異、MSIX 專屬欄位、以及哪些設定在 MSIX 下不能用，見第 6 節 |
| 應用程式名稱 | 顯示給使用者看的名字，**可以是中文**，會出現在安裝介面、登錄表的顯示名稱 |
| 安裝資料夾名稱 | 只用來組安裝路徑（`C:\Program Files\<這裡>`），**建議英數字**，避免路徑含中文在少數環境下出問題；留空自動沿用應用程式名稱 |
| 應用程式版本號 | 例如 `1.0.0`。除了寫進登錄表跟安裝介面外，也會嵌進 `Setup_XXX.exe`/`uninstall.exe` 的 Win32 VERSIONINFO 資源（`FileVersion`/`ProductVersion`），在檔案總管「內容 → 詳細資料」頁籤看得到 |
| 軟體發行者 / 開發商 | 寫進登錄表 Publisher 欄位，同時也是 VERSIONINFO 的 `CompanyName`，並用來自動組成 `LegalCopyright`（`Copyright © <打包當下年份> <這裡填的名稱>`） |
| 最終輸出的安裝檔名稱 | 純粹是編譯出來那顆 `.exe` 的檔名，跟上面兩個名稱無關 |
| 應用程式內容資料夾 | 放你要安裝的軟體本體，不能是空資料夾 |
| 主要執行檔 | 選完資料夾後從下拉選單挑，供建立捷徑、偵測執行中狀態、安裝完成後立即執行使用 |
| 應用程式圖標（PNG） | 安裝視窗內顯示用 |
| 執行檔封面圖示（ICO） | 輸出 exe 在檔案總管顯示的圖示 |
| 使用者授權合約（EULA） | 選填，留空安裝端不會顯示同意頁 |
| 相依元件偵測 | 勾選 VC++ Redistributable / .NET Desktop Runtime，安裝時偵測到缺少會**自動下載＋靜默安裝**（不是只給提示連結了，見下方第 7 節） |
| 自訂相依元件 | 除了內建的兩個，可以自己定義任意相依元件（登錄表偵測鍵值 + 下載連結），安裝時走跟內建元件一樣的偵測/自動安裝流程 |
| 相依元件內嵌打包 | 前面兩種相依元件，預設是安裝時才即時下載；勾選內嵌後改成打包當下就把相依元件的安裝檔下載下來、直接包進 `Setup_XXX.exe` 裡，安裝時不用連網路，適合離線環境部署，代價是輸出的安裝檔體積會變大 |
| 檔案關聯 | 勾選後填副檔名（逗號分隔），安裝時寫入 `HKCR`；每個副檔名還可以**各自指定不同的圖示**（不填就統一用主程式圖示） |
| 加入 PATH | 安裝後把安裝路徑加進系統環境變數；預設加整個安裝目錄，如果應用程式裡有一支獨立的命令列工具放在子資料夾，可以另外指定只把那支執行檔所在的目錄加進 PATH |
| 改裝到使用者目錄的檔案 | 選填，勾選「需要」之後會顯示應用程式內容資料夾的巢狀檔案樹（跟檔案總管的展開/收合體驗一樣），逐一勾選要改裝的檔案；勾資料夾等於連同底下所有檔案一起勾。預設整個應用程式裝在你選擇的安裝位置；被勾選的檔案會改成裝到 `%LOCALAPPDATA%\Programs\<安裝資料夾名稱>` 底下，不需要額外提權，適合「主程式要系統管理員權限、但附帶的命令列工具想讓使用者自己直接在 CMD 裡呼叫」這種情境 |
| 安裝位置 | 三選一：**Program Files**（預設，需要系統管理員權限，雙擊安裝檔會跳 UAC 提示）／**使用者目錄**（`%LOCALAPPDATA%\Programs\<安裝資料夾名稱>`，完全不需要提權，適合單一使用者自己安裝的情境）／**自訂路徑**（自己填一個絕對路徑；如果這個路徑本身在系統層級、需要提權才能寫入，額外勾選旁邊的「這個路徑需要系統管理員權限」） |
| 安裝前置腳本 | 選填，填相對於應用程式資料夾的路徑（例如 `scripts\pre_install.bat`），複製檔案之前自動靜默執行；執行失敗會中止整個安裝並回報錯誤 |
| 安裝後置腳本 | 選填，登錄表/捷徑都寫完後自動靜默執行；執行失敗只記錄警告，不影響安裝結果 |
| 數位簽章憑證 | 選填，指定 `.pfx` 憑證檔（另外填密碼所在的環境變數名稱、時間戳記伺服器網址）。有設定的話，打包完成後會自動用 `signtool` 幫 `Setup_XXX.exe`、`uninstall.exe` 簽章；找不到 `signtool` 或簽章失敗會讓整個打包流程失敗，不會悄悄放行一份沒簽到的安裝檔。**這個工具本身不提供、也無法幫你生成憑證**，要先自己去採購。**選了 MSIX 引擎時這一項的份量不同**：未簽章的套件系統不收，因此它決定你拿到的是一顆安裝檔還是一份還沒簽的 `.msix`（見第 6 節） |

填完按「開始編譯安裝檔」，跳出的進度條會分兩個階段（解除安裝助手編譯、主安裝檔編譯），完成後告訴你輸出的絕對路徑。

### 畫面怎麼排的

表單依「後面的欄位會不會被前面的決定影響」排列。**安裝引擎排在最前面**，因為
它決定後面好幾組欄位有沒有意義（安裝位置、安裝資料夾名稱、相依元件、服務、
排程、前後置腳本在 MSIX 模式下全部失效或被擋）。編譯工作目錄排在最後：它是
「這台機器上的東西放哪」的偏好，不描述你要做出什麼產品，而且設定一次就不會
再改。

**必填的、以及會改變「產出物是什麼」的欄位攤開；不填只是少一個功能的收進四個
可收合的大區**：

| 區 | 裡面有什麼 |
|---|---|
| 安裝過程 | EULA、安裝密碼保護 |
| 系統整合 | 檔案關聯、加入 PATH、Windows 服務、排程工作 |
| 安裝行為 | 相依元件、自訂相依元件、前置／後置腳本、個別檔案改裝、系統還原點 |
| 發布 | 數位簽章 |

三種情況下這些區會自己展開，不用你去點：

- **裡面已經有填過東西**——例如載入舊設定之後。沒有這條的話，你會看不到自己
  設了什麼，而那些設定會真的進到安裝檔裡。
- **選了 MSIX 引擎時的「發布」區**——那個模式下數位簽章決定你拿到的是一顆安裝檔
  還是一份 `.msix`，不再只是選填。
- **按下編譯被驗證擋下，而問題在那一區**——錯誤是用彈窗說的，關掉彈窗之後你還
  要自己找是哪一格，那一格如果還收著就根本看不到。

收合狀態不會記到下次開啟，每次都依「裡面有沒有內容」重新決定。

### 選了 MSIX 引擎之後，表單會就地反應

不用等到按下編譯才知道哪些設定不能用。選定引擎的當下，受影響的欄位就會標出來，
而且**三種情況長得不一樣**：

| 樣子 | 意思 | 例子 |
|---|---|---|
| 整組淡掉、不能操作 | 這個設定在 MSIX 下不會有作用，也不需要 | 安裝資料夾名稱、個別檔案改裝 |
| 左側加一條線 + 一行原因 | 會擋下建置，但**控制項還是可以點** | 相依元件、Windows 服務、排程工作、前後置腳本 |
| 整組換成一段說明 | 這個模式根本沒有這個選擇 | 安裝位置 |

**會擋建置的那些為什麼不直接停用**：你可能是先勾了「安裝為 Windows 服務」才切到
MSIX 的。停用之後你就沒辦法把它取消了，只能切回傳統引擎、取消勾選、再切回來。

按下編譯時仍然會**一次列出全部**不相容的項目——那份清單是給你判斷「切換引擎對
我的專案划不划算」用的，需要完整資訊；表單上的提示只負責讓你更早知道。

## 6. 兩種安裝引擎

「安裝引擎」決定安裝檔內部**用哪一種方式把你的檔案放到使用者的電腦上**。這是
二選一，不是可以同時開啟的選項。

| | 傳統引擎（預設） | MSIX 引擎 |
|---|---|---|
| 誰把檔案放下去 | `Setup_XXX.exe` 自己複製、自己寫登錄表 | 交給 Windows 的套件引擎 |
| 解除安裝 | 附一支 `uninstall.exe`，本工具自己做的介面 | 由系統接管，**沒有**自訂介面 |
| 殘檔 | 靠本工具的移除邏輯，盡力清乾淨 | 系統保證清乾淨 |
| 安裝位置 | 使用者可以選（三種） | **由系統決定，使用者選不了** |
| 裝給誰 | 可以裝給全機器，或只裝給自己 | **第一版只裝給執行安裝的那一位使用者** |
| 需要憑證嗎 | 不用（但沒簽章會跳 SmartScreen 警告） | **一定要**，未簽章的套件系統不收 |
| 需要額外工具嗎 | 不用 | 需要 `makeappx`／`makepri`／`signtool`（見下方） |

拖曳安裝的畫面兩種引擎都一樣，差別只在右邊的目的地：MSIX 模式下它不是可以點的
資料夾，而是一句「由 Windows 管理位置」。

### MSIX 模式一定要填的欄位

| 欄位 | 說明 |
|---|---|
| 套件身分名稱 | **一經發布即不可變更。** 改了之後系統會把它當成另一個不相關的應用程式並存安裝，而且不會有任何警告——使用者的電腦上會同時存在新舊兩份。3 到 50 個字元，只能用英文字母、數字、句點、連字號。不由應用程式名稱推導，要自己想一個並且記住 |
| 發行者 | 必須與你的簽章憑證上記載的名稱**完全一致**，不一致時系統直接拒絕安裝，而且錯誤訊息不會指向這個原因。**在「數位簽章」區塊選好憑證之後留空即可**，工具會自己讀出來填進去。只有憑證不在本機（例如雲端代簽）時才需要自己填——注意那個字串的形式不直覺：順序是反的、分隔符是逗號加空格、值裡有逗號時要用雙引號包起來，例如 `C=TW, CN="Foo, Inc."` |
| 最低支援的 Windows 版本 | 選填，留空即 `10.0.17763.0`（Windows 10 1809） |
| 圖示個別覆蓋 | 選填，三個位置（磚塊／工作列／商店）可以各自指定。留空就沿用上面那張 PNG。**必須是正方形的 PNG**，三個位置的邊長分別至少 150／44／50 像素 |

### 憑證在不在這台機器上，決定按下編譯之後會發生什麼事

**憑證在本機**（也就是你在「數位簽章」區塊選了 `.pfx`）：按一次「開始編譯安裝檔」
就跑完全部——組裝套件、簽章、編出內嵌它的 `Setup_XXX.exe`，體驗跟傳統引擎完全
一樣。

**憑證不在本機**（例如交給雲端代簽）：編到 `.msix` 為止就停下來，畫面會告訴你
套件在哪裡。你自己拿去簽，簽好之後用命令列工具接完後半段：

```
python builder_cli.py pack --config <你的設定>.json --signed-msix <簽好的>.msix
```

這個斷點消除不掉：已簽章的 `.msix` 必須在編 `Setup_XXX.exe` 之前備妥（它是被塞
進 exe 裡的，塞進去之後要換成簽過的版本等於整個重編一次），而簽章不一定當場
完成。你不需要理解這件事——只有真的走到雲端代簽才會遇到它。

### 哪些設定在 MSIX 模式下不能用

選了 MSIX 之後表單會就地標出來（見上一節），按下編譯時也會一次列出全部。分成
三種，**語氣不一樣是刻意的**：

- **「目前尚未支援」**——MSIX 做得到，只是這個工具還沒做。可以等：相依元件、
  Windows 服務、排程工作、裝給全機器所有使用者。
- **「MSIX 無法做到，此為格式本身的限制」**——別等了，要重新設計安裝流程：
  自訂安裝路徑、安裝前置／後置腳本、內嵌相依元件的安裝檔。
- **「不會有作用，也不需要」**——不擋建置：安裝資料夾名稱、個別檔案改裝到其他
  位置。套件的位置由系統決定，本來就沒有使用者會操作的安裝資料夾；而個別檔案
  改裝原本的目的（讓命令列工具不必提權就能執行）在 MSIX 下本來就成立。

EULA、檔案關聯、加入 PATH、安裝密碼保護在兩種引擎下都正常運作。

### 需要的額外工具

MSIX 打包需要 `makeappx`、`makepri`、`signtool`，三者都屬於 Windows SDK。
**Windows SDK 裝完不會把這些工具加進 PATH**，而且也不需要為此裝好幾 GB 的 SDK：

```
python builder_cli.py fetch-sdk-tools
```

這個指令會下載一份固定版本的 `Microsoft.Windows.SDK.BuildTools`（約 22 MB）、
驗證 SHA-256、解壓到使用者層級的持久位置，之後打包流程自己找得到。**打包流程
不會自己執行它**——那等於在你沒明確要求的情況下，把一個剛從網路取得的執行檔跑
在你的機器上。

## 7. 安裝端（`Setup_XXX.exe`）實際會做的事

雙擊執行後：

1. 單一實例鎖（避免重複開啟）
2. 游標顯示「載入中」動畫，直到視窗出現
3. 有設定 EULA 的話先顯示同意頁
4. 偵測是否已安裝過舊版本，有的話問「更新覆蓋 / 取消」；如果偵測到主程式（或其他鎖定安裝目錄檔案的程序）正在執行中，會用互動式畫面問使用者要「關閉程序後繼續」還是「取消」，不是直接擋死
5. 相依元件缺少的話：預設會**自動下載＋靜默安裝**，畫面上有非阻擋式進度提示；如果打包時選了「內嵌」，這一步不用連網路，直接從安裝檔裡解出來裝
6. 有設定「安裝前置腳本」的話，這裡自動靜默執行一次；失敗會中止整個安裝並顯示錯誤
7. 使用者把左邊圖示拖到右邊資料夾（或點資料夾自訂路徑）觸發安裝：
   - 磁碟空間檢查
   - 主程式執行中偵測；如果偵測本身卡死（極少數殭屍行程的邊緣情況），互動畫面上也有一個「略過偵測，強制繼續」的保底選項
   - 複製檔案（真實進度）
   - **完整性驗證**：每個檔案先比大小，大小一致再比對 CRC32 checksum，比單純比大小更可靠
   - **檔案被其他程式鎖住時**：如果複製途中某個檔案正被其他程式使用中（例如應用程式註冊的檔案總管殼層擴充功能），會跳出互動畫面告訴你是哪個程式鎖住的，按「關閉此程式」會自動嘗試釋放（先試著只關掉相關的檔案總管視窗，不夠才會暫時關閉檔案總管本身再自動重啟）後直接重試，不用自己去工作管理員手動處理；如果這個畫面按了「關閉此程式」還是持續出現，很可能是防毒/安全軟體攔截了終止該程式的動作，請確認防毒軟體的相關防護設定（見第 12 節疑難排解）
   - **失敗自動回滾**：驗證失敗或任何步驟中途出錯，會自動刪掉這次已經複製出去的檔案，不留下裝到一半的殘骸；失敗訊息會依實際的 Windows 錯誤碼分類顯示（例如「磁碟空間不足」「權限不足」「路徑過長」各自有對應的說明，不會一律歸類成「權限不足」）
   - 寫入登錄表（含 `EstimatedSize`、`InstallDate`、`QuietUninstallString`）、捷徑、檔案關聯（含各自指定的圖示）、PATH
   - 寫入 `install_manifest.json`、`install_log.txt`
8. 有設定「安裝後置腳本」的話，這裡自動靜默執行一次；失敗只記錄警告，不影響安裝結果
9. 安裝完成可勾選「立即執行程式」

## 8. 靜默 / 命令列安裝模式

給企業批次部署（登入腳本、MDM、群組原則）用，不需要修改任何程式碼，直接對編譯出來的 `Setup_XXX.exe` 帶參數：

```bat
Setup_XXX.exe /S
Setup_XXX.exe /S /D=D:\Apps\MyApp
Setup_XXX.exe /S /NODESKTOPSHORTCUT
```

| 參數 | 作用 |
|---|---|
| `/S`、`/SILENT`、`/QUIET`、`/VERYSILENT` | 靜默安裝，不開任何視窗 |
| `/D=路徑` 或 `/DIR=路徑` | 指定安裝路徑，覆蓋預設的 Program Files 路徑 |
| `/NODESKTOPSHORTCUT` | 不建立桌面捷徑（預設會建立） |

**行為慣例**（跟業界靜默安裝工具一致）：
- 執行 `/S` 視同已同意 EULA，不會跳同意頁。
- 偵測到舊版本會自動靜默更新覆蓋，不會跳選擇視窗。
- 缺少相依元件只會印出警告文字，不阻擋安裝（畢竟沒視窗可以顯示提示）。
- **exit code 可以直接拿來判斷結果**：`0` = 成功，非 `0` = 失敗，部署腳本檢查 `%errorlevel%` 就知道有沒有裝成功。
- `Setup_XXX.exe` 是用 `--noconsole` 編譯的（GUI 拖曳安裝模式需要這樣），即使命令列帶 `/S` 執行也不會有主控台視窗可以顯示文字，**exit code 不會自己顯示出來**，要在同一個命令視窗裡緊接著查（cmd：`echo %errorlevel%`；PowerShell：`$LASTEXITCODE`）。詳細訊息會寫進 `%TEMP%\<應用程式名稱>_silent_install_log.txt`，這是實際能查到細節的管道。

`uninstall.exe` 也支援 `--silent`，而且已經寫進登錄表的 `QuietUninstallString` 欄位——代表 Windows「設定 > 已安裝的應用程式」自己的批次移除功能，也認得出來要用靜默模式呼叫。

## 9. 解除安裝行為

`uninstall.exe` 開啟後是跟 `Setup_XXX.exe` 同一套 macOS 風格拖曳視窗介面：把應用程式圖示拖到垃圾桶圖示上放開＝觸發解除安裝（也可以直接用右上角關閉鈕取消，不強迫一定要用拖曳）。如果偵測到主程式正在執行中，會跳出「關閉應用程式並繼續解除安裝／取消」的互動畫面；如果偵測到有其他程序鎖定安裝目錄裡的檔案，也會先跳互動畫面問是否要先關閉這些程序——實際釋放邏輯跟安裝端共用同一套分層策略（先試著只關掉相關的檔案總管視窗，不夠才暫時終止並自動重啟檔案總管本身）。這兩種偵測都有「略過偵測，強制繼續」的保底選項，因應偵測本身卡死的邊緣情況。

`uninstall.exe` 讀取安裝時寫的 `install_manifest.json`，**只刪清單記錄的檔案**，不會動到使用者事後在安裝目錄裡自己產生的檔案。刪完清單內的檔案後，會確認資料夾是不是真的清空了：

- 清空了 → 連資料夾一起刪掉
- 還有其他東西（使用者自己的資料，或找不到清單而退回整個清除的情況除外）→ 只刪 `uninstall.exe` 自己，資料夾跟裡面剩下的東西保留

同時會清掉登錄表項目、開始功能表/桌面捷徑、檔案關聯、PATH 裡的安裝路徑。

## 10. 已知限制 / 還沒做的事

- **數位簽章需要你自己準備憑證**：這個工具本身不販售、也無法幫你生成程式碼簽署憑證，但如果你已經有 `.pfx` 憑證，可以在製作工具裡填上（見第 5 節「數位簽章憑證」），打包流程會自動幫你簽好 `Setup_XXX.exe`／`uninstall.exe`，不用另外手動跑 `signtool`。沒有憑證的話，使用者第一次執行你編譯出來的 exe，Windows SmartScreen 大概率還是會跳警告。
- **多語言只涵蓋一部分的後端訊息**：製作工具本身、安裝/解除安裝介面（含 EULA）已經支援繁體中文/英文自動偵測系統語言。後端訊息目前只有「MSIX 引擎的設定相容性清單」支援兩種語言（CLI 用 `--lang` 指定，未指定時依系統語言）；其餘的欄位驗證訊息、打包流程的進度文字、以及 `uninstall.exe` 靜默模式的輸出仍固定是繁體中文。因此**英文介面下按編譯，錯誤彈窗可能中英混雜**——這是分階段的結果，理由見`docs/adr/0011`。
- **MSIX 引擎第一版只裝給執行安裝的那一位使用者**：需要裝給整台電腦所有使用者時請改用傳統引擎。這是「暫時不做」而不是「做不到」，見 `docs/adr/0009`。
- **MSIX 模式沒有自訂的解除安裝介面**：由系統接管，使用者到「設定 → 應用程式」或在開始功能表項目上按右鍵解除安裝。這一項不會改變，見 `docs/adr/0006`。
- **相依元件內嵌打包會讓安裝檔變大**：勾選內嵌後相依元件的安裝檔會整包塞進 `Setup_XXX.exe`，換取離線也能裝，體積上的取捨要自己衡量。
- **WebView2 依賴**：極少數沒更新的舊 Windows 10 可能缺這個系統元件，需要另外提醒使用者安裝。缺少時安裝畫面會停在「載入中...」且不顯示原因（實測結果見 §1），安裝程式目前不偵測這個元件是否存在。

## 11. 在 CI（例如 GitHub Actions）裡自動打包

如果你想在自己的 CI 流程裡自動跑打包（而不是每次手動開 `InstallerBuilder.exe`
點按鈕），**不需要**先編出、再上傳 `CLI_exe` 這個中間產物。這個工具的核心
（`builder_cli.py`、`builder.py`）本來就是公開的 Python 原始碼，CI 環境
裝一個 Python 是很輕量的事，直接照這個順序做就好：

1. CI 裡把這個 repo（或你自己 vendor 進去的一份）跟你的應用程式內容一起
   準備好。
2. 裝 Python + 相依套件：`pip install pyinstaller pywebview cryptography`。
3. 直接呼叫 `python builder_cli.py pack --app-dir ... --png-icon ... --ico-icon ... --app-name ... --version ... --exe-name ...`（完整參數見
   [`CLI_USAGE.md`](CLI_USAGE.md)），跟在自己電腦上手動下指令是同一套
   用法，只是換一台機器執行。
4. 打包出來的 `Setup_XXX.exe` 當成 workflow 的建置產物上傳/發布。

這個 repo 自己也是這樣用的（`.github/workflows/build.yml`），可以直接參考
裡面的步驟。

**關於數位簽章**：如果你想要「這個安裝檔確實是從我的 CI 建置出來的」這種
可公開驗證的簽章保證（例如透過 [SignPath](https://signpath.org/) 的開源
免費方案），前提是**你自己的專案**要有自己的 CI 流程、自己去申請——這個
工具本身如果之後也申請了這類簽章服務，涵蓋的只會是**這個工具自己發布的
`InstallerBuilder.exe`／CLI 版**，不會、也沒辦法涵蓋任何用這個工具打包出來
的第三方安裝檔。第三方安裝檔要簽章，還是要靠第 5 節提到的「數位簽章憑證」
欄位（你自己的憑證），或是你自己專案另外申請的簽章服務。

## 12. 疑難排解

**「找不到 ui 資料夾或 ui/index.html 基礎資源」**
`InstallerBuilder.exe` 沒有寫入權限，或第一次執行時自動解壓失敗。確認 exe 放在你自己有完整權限的資料夾。

**打包安裝檔時卡在「存取被拒」**
通常是上一次編譯出來的 exe 還在執行中，或被防毒軟體掃描鎖住。關閉相關程式再試一次。

**中文路徑相關的錯誤**
在製作工具裡把「安裝資料夾名稱」改成純英數字，跟「應用程式名稱」分開設定即可。

**安裝/解除安裝時一直卡在「檔案使用中」，按了「關閉此程式」也沒用**
安裝程式已經會自動嘗試釋放鎖定（先關掉相關的檔案總管視窗，不夠才暫時終止並自動重啟檔案總管本身）。如果按了「關閉此程式」之後畫面還是持續跳出來，很可能是電腦上的防毒/端點防護軟體把「終止系統關鍵行程（例如檔案總管）」這個動作列管、直接在系統核心層擋下來了——這是防毒軟體合理、正常的保護行為，安裝程式不會（也不應該）嘗試繞過。請到防毒軟體的設定裡找「進程保護」「敏感動作防護」之類的項目（例如火絨的「關鍵進程保護」→「資源管理器」），暫時允許這個動作，或先關閉即時防護再重試安裝。
