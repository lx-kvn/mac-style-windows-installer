# 技術規格文件 — mac-style-windows-installer

給接手這個專案的工程師（含 AI coding agent）讀的技術交接文件。這份文件假設讀者不了解專案背景，會從架構講到每一個容易踩坑的實作細節。使用者面向的說明另外見 `使用說明書.md` / `README.md`，那兩份是給「使用這個工具的人」看的，這份是給「維護這個工具的人」看的。

---

## 1. 專案是什麼

一個 Windows 桌面工具，把任意應用程式打包成 macOS DMG 風格「拖曳圖示到資料夾」的安裝體驗，取代傳統 Windows「下一步、下一步」精靈式安裝。

全部用 **Python + [pywebview](https://pywebview.flowrl.com/)**（畫面）+ **[PyInstaller](https://pyinstaller.org/)**（打包成 exe）做成，沒有用任何前端框架，HTML/CSS/JS 都是原生手寫、單一檔案。

---

## 2. 架構：三顆獨立的 exe（#1 現在有 GUI/CLI 兩種介面）

這是理解整個專案最關鍵的一件事——**很多 bug 都是因為沒搞清楚這三顆東西的關係造成的**：

| # | exe | 原始碼 | 誰執行 | 怎麼產生 |
|---|---|---|---|---|
| 1 | `InstallerBuilder.exe`（GUI）／`builder_cli.py` 編出來的 CLI exe | `gui_config.py`（GUI）／`builder_cli.py`（CLI），共用 `packaging_core.py` + `builder.py` | 開發者本人，拿來設定並編譯安裝檔 | `python build_config_tool.py`（互動 GUI）或 `python build_config_tool.py --cli`（非互動，兩顆都編） |
| 2 | `Setup_XXX.exe`（開發者自訂檔名） | `installer_core.py` | 終端使用者，雙擊安裝軟體 | 由 #1（GUI 或 CLI 皆可）執行時，呼叫外部 `pyinstaller` 現場編譯 |
| 3 | `uninstall.exe` | `uninstall.py` | 終端使用者要移除軟體時 | 由 #1 執行時，呼叫外部 `pyinstaller` 現場編譯，打包進 #2 裡面 |

**關鍵理解**：#1 執行「開始編譯安裝檔」時，是**再開一個 `pyinstaller` 子行程**去編譯 #2 和 #3，不是把編譯這件事也內建在 #1 裡面。這代表：
- 操作 #1 的機器，必須裝有 `pyinstaller` + `pywebview`（`pip install -r requirements.txt`，套件清單與各項用途見該檔）
- #1 本身雖然可以被打包成 exe，但**打包成 exe 不會消除這個外部依賴**，只是把 #1 自己的 UI 邏輯包起來而已
- #2、#3 是完全獨立、自我完備的 exe，終端使用者不需要裝 Python

**#1 的 GUI/CLI 拆分**（見 §8.17）：`gui_config.py` 只剩 GUI 專屬的 `ConfigAPI`（視窗拖曳/縮放、檔案選擇對話框、背景執行緒 + JS 進度回報）；真正的驗證/環境檢查/工作目錄準備邏輯搬進不依賴 pywebview 的 `packaging_core.py`，GUI 的 `ConfigAPI.start_pack()` 跟 CLI 的 `builder_cli.py`（`init`/`pack` 子指令）都呼叫同一份，不會有兩邊規則兜不起來的問題。使用方式分別見 `使用說明書.md`（GUI）跟 `CLI_USAGE.md`（CLI）。

### 3.1 `ui/` 的檔案結構與載入順序

介面原本是三份互相獨立的 HTML，共用的邏輯以複本的形式各自內嵌。現在共用的
部分抽成三個 `.js`，由 HTML 以 `<script src>` 載入。

| 檔案 | 職責 | 誰載入 |
|---|---|---|
| `spring.js` | 彈簧求解器。`createSpring()` 回傳一個帶 `step(dt)`／`atRest()`／`settle()` 的物件 | `index.html`、`uninstall.html` |
| `drag_to_target.js` | 自繪拖曳手勢本體。`createDragToTarget(config)` 回傳 `{ cancel, isActive, isAbsorbing }`，手感常數集中在 `DRAG_TUNING_DEFAULTS` | `index.html`、`uninstall.html` |
| `i18n.js` | 翻譯機制。`createI18n(tables, fallbackLang)` 回傳 `{ t, apply, getLang }`，`apply()` 處理 `data-i18n`／`data-i18n-title`／`data-i18n-placeholder`／`data-i18n-html` 四種標記 | 三份介面都載入 |

**載入順序有相依性**：`drag_to_target.js` 在建立控制器時會呼叫
`createSpring()`，因此 `spring.js` 必須排在它前面。`i18n.js` 與另外兩個之間
沒有相依關係，順序自由。

**兩端共用同一份拖曳實作**，只有目的地自己的回應以 callback 參數化：
`onHoverChange`（安裝端是 CSS class，解除安裝端還要掀開垃圾桶蓋）與
`onAbsorb`（資料夾吞一下 vs 垃圾桶闔蓋）。安裝端專屬的資料夾吞嚥常數
（`SWALLOW_MS`／`SWALLOW_SQUASH`）留在 `index.html`，不放進共用檔案。
完整的取捨見 [`docs/adr/0002`](adr/0002-drag-to-install-self-rendered-drag.md)。

**新增 `ui/` 底下的檔案時不需要更新任何清單**：`ensure_workspace_files()` 的
覆蓋策略是白名單反轉——白名單 `USER_CUSTOMIZABLE_UI_ASSETS` 只列使用者可以
自訂的資源（`folder_icon.png`、`trash_body.svg`、`trash_lid.svg`，這些是
「缺少才補、已存在就不動」），其餘一律覆蓋。這跟 §3 架構筆記講的 `.py`
共用模組不同，那邊仍然要手動登記兩份清單。

## 4. 內嵌資源與「工作目錄」機制（重要，容易出 bug 的地方）

`InstallerBuilder.exe`（打包 #1 的 GUI 版時）用 PyInstaller 的 `--add-data` 把這些內嵌進去：`ui/`（整個資料夾）、`installer_core.py`、`uninstall.py`、`splash_helper.py`，加上 §8.11/§8.13 的共用深模組跟 `packaging_core.py`；`builder_cli.py` 編出來的 CLI 版 exe 內嵌的清單類似，但沒有 `splash_helper.py`（CLI 沒有 Tkinter 載入畫面），見 §8.17 `build_config_tool.py` 的 `_GUI_ADD_DATA`/`_CLI_ADD_DATA`。

執行時，`packaging_core.py` 的 `get_workspace_dir()` 決定一個「工作目錄」：
- `.py` 直接執行：工作目錄就是目前的工作目錄（跟原始碼同一層）
- frozen exe：固定用 **exe 所在的資料夾**

`ensure_workspace_files(workspace_dir)` 負責確保工作目錄底下有這些必要檔案，因為 `builder.py` 之後要對它們執行 `pyinstaller` 子行程，這些檔案必須**實際存在於磁碟上**，不能只存在於 `_MEIPASS`（PyInstaller onefile 執行時的暫存解壓縮目錄）裡。GUI（`gui_config.py`）跟 CLI（`builder_cli.py`）都呼叫這同一份 `packaging_core.ensure_workspace_files()`，不會有兩邊各自維護一份、行為兜不起來的問題。

**⚠️ 這裡曾經有一個重要 bug，修過但要留意不要迴歸**：`installer_core.py` / `uninstall.py` / `ui/index.html` 這三個是內部實作檔案，**每次執行都要無條件覆蓋**，不能用「只在缺少時才複製」的邏輯——後者會導致重複用同一個工作目錄打包新版 `InstallerBuilder.exe` 時，工作目錄裡卡著的舊版本永遠不會被換掉，任何後續修正都不會真的生效，而且沒有任何錯誤訊息。`ui/folder_icon.png` 這類**使用者可能自訂過的靜態資源**則相反，要維持「只在缺少時才補」，不能覆蓋使用者的客製化。這個「哪些該覆蓋、哪些不該」的判斷邏輯全部在 `packaging_core.py` 的 `ensure_workspace_files()` 裡，改動前務必重讀一次這個函式的註解。

`splash.py` 的 `_resolve_helper_script()` 也有同一類邏輯（複製 `splash_helper.py` 到 `%TEMP%`），同樣是每次無條件覆蓋，理由相同。

## 5. 資料結構（Schema）

### 5.1 `installer_config.json`

由 `builder.py` 的 `build_all()` 產生，打包進 #2 裡，`installer_core.py` 的 `load_config()` 讀取。**這是 #1 和 #2 之間唯一的資料傳遞管道**（沒有其他 IPC，就是一份靜態 JSON）。

```json
{
    "app_name": "顯示名稱，可以是中文",
    "folder_name": "安裝路徑用的名稱，建議英數字，留空時等於 app_name",
    "version": "1.0.0",
    "publisher": "發行者",
    "main_exe": "MyApp.exe（相對於安裝目錄的路徑）",
    "eula_texts": {"zh-TW": "EULA 全文（繁體中文）", "en": "EULA full text (English)"},
    "eula_default_lang": "zh-TW",
    "dependencies": ["vcredist_x64", "dotnet_desktop"],
    "file_associations": [".xyz", ".abc"],
    "doc_icon": "doc_icon.ico 或空字串（空字串代表沿用 main_exe 圖示）",
    "doc_icons": {".xyz": "doc_icon_xyz.ico"},
    "add_to_path": true,
    "path_target_exe": "",
    "local_appdata_files": [],
    "restart_explorer_on_update": false,
    "password_protected": false
}
```

`password_protected`（見 §8.36）：這份安裝檔的應用程式檔案有沒有被加密、
安裝時要不要先過密碼關卡。**只有這個布林值，密碼本身絕對不寫進這份設定檔**
——它會被打包進安裝檔、跟著送到每一位終端使用者手上。`installer_core.py`
用它決定要不要顯示密碼輸入畫面，以及複製來源要取內嵌的 `app_contents/`
還是解密後的暫存資料夾。

`restart_explorer_on_update`：更新覆蓋安裝或解除安裝時，如果應用程式註冊了 Windows 檔案總管殼層擴充功能（Shell Extension DLL）或有其他背景程式持有安裝目錄下檔案的控制代碼，覆寫/刪除會失敗（`PermissionError`，跟系統管理員權限無關）。勾選這個選項後，`uninstall.py` 會用 `restart_manager.py`（Windows Restart Manager API）實際偵測是哪些進程鎖住了要刪除的檔案，逐一結束真正的鎖定者，不是隨便假設一定是 `explorer.exe`；刪除完畢後，只有剛好結束掉 `explorer.exe` 才會自動重啟它。無人值守（更新覆蓋）直接套用，互動式（手動解除安裝）會先跳確認對話框列出偵測到的進程，見 §7、§8.12 與 `uninstall.py` 的 `_kill_processes()` / `_restart_explorer()`。預設不啟用，因為如果需要結束檔案總管，會讓使用者畫面短暫閃爍、所有檔案總管視窗被關閉。

`eula_texts` / `eula_default_lang`（多語言 EULA，見 §8.13）：`eula_texts` 是語言代碼對應文字的字典，由開發者在 `config.html` 打包時自行新增幾種語言、自己貼上每種語言的全文（不做機器翻譯），空字典代表不顯示同意頁（沿用原本「空字串=跳過」的行為）。`installer_core.py` 的 `get_eula_text()` 依序嘗試：偵測到的系統語言完全對到 → `eula_default_lang` 指定的回退語言 → 字典裡第一筆（保底）→ 空字串。`eula_default_lang` 只有在 `eula_texts` 非空時才是必填（`packaging_core.py` 的 `validate_and_build_pack_data()` 會擋下「有語言但沒指定回退語言」的情況，GUI/CLI 共用同一份驗證）。

`path_target_exe`（見 §8.14）：`add_to_path` 預設把**整個安裝目錄**加進 PATH；如果應用程式除了 `main_exe` 外還附了一支獨立的命令列工具（例如放在子資料夾），可以在這裡另外指定那支執行檔（相對於安裝目錄的路徑），`installer_core.py` 的 `_add_to_path_env()` 會改成只把它所在的目錄加進 PATH，不必動到 `main_exe` 本身。空字串（預設）或指到安裝根目錄下的執行檔，效果都跟原本行為一樣。

`doc_icons`（見 §8.20）：字典 `{副檔名: 內嵌圖示檔名}`，讓不同副檔名的檔案關聯各自套用不同 ICO（例如 `.a`、`.b` 用不同圖示），不是全部共用同一張 `doc_icon`。優先序：這個副檔名自己在 `doc_icons` 裡的設定 → 共用的 `doc_icon` → `main_exe` 圖示。空字典（預設）維持原本「所有副檔名共用 `doc_icon`」的行為。

`local_appdata_files`（見 §8.19）：相對於安裝目錄（`app_dir`）的檔案路徑清單，安裝時這些檔案改裝到 `%LOCALAPPDATA%\Programs\<folder_name>`（使用者自己的目錄，不需要系統管理員權限），不是主安裝目錄，典型用途是跟主程式分開的 CLI 工具，避免使用者事後單純執行它也要提權。`path_target_exe` 如果剛好也列在這裡，PATH 會自動指向這個別位目錄。空清單（預設）維持原本行為，所有檔案都裝進主安裝目錄。

### 5.2 `install_manifest.json`

由 `installer_core.py` 的 `trigger_installation()` 在安裝完成時寫入**安裝目錄底下**，`uninstall.py` 讀取，決定解除安裝時要刪哪些東西。

```json
{
    "app_name": "...",
    "version": "...",
    "publisher": "...",
    "main_exe": "...",
    "install_path": "C:\\Program Files\\...",
    "files": ["相對於安裝目錄的每一個複製過去的檔案路徑", "..."],
    "desktop_shortcut": true,
    "start_menu_shortcut": true,
    "file_associations": [".xyz"],
    "path_added": true,
    "path_directory": "C:\\Program Files\\...\\tools",
    "restart_explorer_on_update": false,
    "installed_at": "ISO 格式時間戳"
}
```

`files` 陣列包含：`app_contents` 底下所有複製的檔案、`uninstall.exe`、`installer_config.json`、`doc_icon.ico`（如果有）、以及**它自己**（`install_manifest.json`、`install_log.txt`）。這是刻意的：`uninstall.py` 讀取這份清單、逐一刪除清單內的檔案（保留使用者事後自己在安裝目錄產生的其他檔案），刪完清單內所有檔案後才判斷資料夾是否真的清空、決定要不要連資料夾一起 `rmdir`。**如果之後新增任何會被複製進安裝目錄的檔案，記得同步加進這個 `files` 清單，不然會變成清不掉的孤兒殘留**（這正是這輪修過的一個真實 bug）。

`path_directory`（見 §8.14）：`path_added` 只是布林值，不足以讓 `uninstall.py` 知道當初實際加進 PATH 的是哪個目錄——預設是整個 `install_path`，但 `path_target_exe` 有指定時會是它所在的子目錄。`path_directory` 記錄的就是這個實際加入的目錄字串，`uninstall.py` 的 `_path_removal_target()` 用它來移除，沒有這個欄位（舊版本安裝的 manifest）才退回 `install_path`。

## 7. 安裝流程（`trigger_installation`）逐步拆解

1. 磁碟空間檢查（`_check_disk_space`，比對 `app_contents` 總大小 vs 目標磁碟剩餘空間，留 10% 緩衝）
2. 主程式執行中偵測（`tasklist` 查 `main_exe`）：偵測到執行中不會直接判定安裝失敗，回傳獨立的 `{"status": "process_running", "message": "..."}`，`ui/index.html` 收到這個狀態會跳出「關閉程式並繼續安裝／取消」彈窗（見 §8.16），不是通用的錯誤彈窗
3. **覆蓋安裝：移除舊版本**（`check_existing_install()` 偵測到 `exists=True` 才會執行）：
   - 呼叫 `run_upgrade_uninstall()` → 內部先 `_backup_existing_install()` 把舊安裝資料夾整份複製到 `tempfile.gettempdir()\{app_name}_upgrade_backup_{pid}`，再靜默呼叫舊版本的 `uninstall.exe --silent`。
   - **時機很重要**：這一步是在 `trigger_installation()` 裡執行，也就是使用者已經把圖示拖進資料夾、真正觸發安裝動作**之後**才會刪舊版本檔案，不是 `ui/index.html` 的 `confirmUpgrade()` 一按下彈窗確認鈕就立刻刪（歷史上這裡曾經是彈窗按下就立刻刪，改掉的原因：使用者按完確認鈕、還沒拖曳圖示前反悔關視窗，舊版本不該被動到）。
   - `run_upgrade_uninstall()` 回傳 `error` 時，`trigger_installation()` 直接回傳錯誤、不繼續往下建立安裝目錄或複製檔案。
4. 收集 `app_contents` 底下所有檔案，逐一複製，**複製後驗證**：先比大小，大小一致才進一步比對 CRC32 checksum（`_file_checksum`，用 `zlib.crc32`，不是密碼學等級雜湊，只是抓複製過程的損毀）
5. 任何一個檔案驗證失敗，或後續任何步驟拋出例外 → 呼叫 `_rollback(copied_rel_paths, log)`，把**這次安裝已經複製的所有檔案**清掉，包含 `uninstall.exe`、`installer_config.json`、`doc_icon.ico`（這些是額外用 `copied_rel_paths.append()` 加進去的，不是自動涵蓋，新增任何複製動作記得同步加），**並且**呼叫 `_restore_upgrade_backup()` 把第 3 步備份的舊版本檔案搬回原位（如果這次是覆蓋安裝的話）
6. 複製 `uninstall.exe`、`installer_config.json`、（有的話）`doc_icon.ico`
7. 寫登錄表（`_register_uninstall_entry`）：`DisplayName, UninstallString, QuietUninstallString, InstallLocation, Publisher, DisplayVersion, DisplayIcon, InstallDate, EstimatedSize, NoModify, NoRepair`
8. 建捷徑（`_create_shortcut`，開始功能表必建，桌面看參數）、註冊檔案關聯（含 `DefaultIcon`）、加入 PATH
9. 寫 `install_manifest.json`、`install_log.txt`
10. 安裝成功 → 呼叫 `_discard_upgrade_backup()` 清掉第 3 步的備份（沒用到就是 no-op）；`PermissionError` / 其他例外 → 呼叫 `_restore_upgrade_backup()` 復原
11. 進度回報：`_report_progress(percent, message)` 呼叫 `window.evaluate_js` 更新前端進度條，複製階段佔 0-80%

**復原機制的已知限制**：`_restore_upgrade_backup()` / `close_window()`（使用者在覆蓋安裝流程跑到一半就關視窗，等同取消）只復原「檔案」，`run_upgrade_uninstall()` 呼叫舊版 `uninstall.exe` 時一併移除的登錄表項目（解除安裝登錄、檔案關聯、PATH、捷徑）不會被復原——這次的範圍聚焦在使用者明確要求的「檔案復原」，如果要完整復原需要額外重新註冊這些登錄表項目。

**修正紀錄（真實抓到的 bug）**：`_backup_existing_install()` 原本用 `os.environ.get("TEMP", ".")` 算暫存路徑，這個寫法只有在 `TEMP` 這個環境變數整個不存在時才會用預設值 `"."`；如果它存在但是空字串（實測發生在某些提權執行的情境下，環境變數區塊沒有正確帶出 `TEMP`），`.get()` 照樣回傳空字串，`os.path.join()` 算出來的會是相對路徑，實際落點變成「安裝程式執行當下的工作目錄」——如果使用者剛好把新安裝檔放在舊安裝目錄本身執行更新，備份資料夾會被建立在 `install_path` 底下，`shutil.copytree()` 變成對自己複製（`copytree` 對這種情況沒有防呆機制，會邊複製邊把剛建立的子資料夾也當成來源的一部分，越複製越亂，最後多半拋例外收場，留下爛尾的子資料夾且完全沒有備份到東西）。已修正：改用 Python 標準函式庫的 `tempfile.gettempdir()`（依序檢查 `TMPDIR`/`TEMP`/`TMP`，保證回傳真實存在的絕對路徑，不會有空字串/相對路徑陷阱），並加一道保險：算出來的備份路徑如果還是落在 `install_path` 底下，直接拒絕備份、回傳 `None`。`run_silent_install()` 的靜默安裝 log、`uninstall.py` 的解除安裝 log 也有同樣手動讀 `TEMP` 的寫法，一併換成 `tempfile.gettempdir()`。

## 8. 關鍵技術決策與踩過的坑（維護前必讀）

這節是最重要的部分——記錄「為什麼這樣做」，避免之後重新踩同一個坑。

### 8.1 前端進度條動畫（`config.html`）

`builder.py` 只在少數固定 checkpoint 回報真實進度（例如 5、10、15、35、40、97、100），中間可能要等數十秒。前端**不是直接顯示後端傳來的數字**，而是自己用 `requestAnimationFrame` 維護一條漸進趨近曲線：追上真實 checkpoint 前用「跟目標的差距」決定速度，追上之後如果還沒到下一個 checkpoint，用 `cap - (cap - 起始值) * e^(-經過秒數/時間常數)` 這條公式自己往前爬，每個階段的 `cap`（這階段最高能爬到多少）跟 `time_constant`（爬升快慢）由 `builder.py` 的 `report()` 呼叫決定，是**跟後端商量好的兩個額外參數**，不是前端憑空亂算。動畫只有在真的收到 `currentTarget >= 100` 時才會補到 100%，失敗時（`packComplete('error', ...)`）動畫會停在原地不動，不會繼續往前爬。

`window.updateProgress` / `window.packComplete` 這兩個 window 掛載函式是 `evaluate_js` 呼叫的橋樑，改動時要注意 Python 端傳的參數順序跟 JS 端接收順序要對上。

### 8.2 自訂視窗拖曳（`config.html`、`index.html`）

**沒有**用 pywebview 內建的 `pywebview-drag-region`：那個機制拖曳開始瞬間會讓視窗跳一下才跟上游標，100% 縮放下也會發生，判斷是機制本身的問題（不是 DPI 造成的，這個排查過程繞了一點路，先前一度誤判成 DPI 問題）。改成完全自己算：`mousedown` 記錄基準點、`mousemove` 算位移量呼叫 Python 的 `window.move()`。

**有一個容易忽略的邊界情況**：如果放開滑鼠時游標剛好在視窗外（拖到螢幕邊緣很常見），`mouseup` 事件可能收不到，導致「正在拖曳」的狀態卡死、視窗之後永遠跟著滑鼠跑。修法是在 `mousemove` handler 裡順便檢查 `e.buttons`，沒有偵測到左鍵仍按著就強制結束拖曳，不要等一個可能不會來的 `mouseup`。

動畫迴圈（`requestAnimationFrame`）**只在真的按下滑鼠時才啟動**，放開後利用「檢查旗標，false 就不排下一幀」讓迴圈自然停止——早期版本是無條件在頁面載入時就啟動一個永遠跑的迴圈，是不必要的常駐消耗，已修正。

### 8.3 自訂視窗縮放（僅 `config.html` 有）

`gui_config.py` 建立視窗時 `frameless=True`，無邊框視窗沒有系統原生縮放邊界，`resizable=True` 那個參數形同虛設。做法是在 HTML 裡放三條看不到的縮放感應區（右邊緣、下邊緣、右下角），邏輯跟拖曳共用同一套「記基準點 + rAF 節流」模式。`index.html`（安裝端視窗）**沒有**做這個，因為安裝端視窗是固定尺寸的體驗，沒有縮放需求。

### 8.4 DPI 感知

用 `SetProcessDpiAwareness(1)`（**PROCESS_SYSTEM_DPI_AWARE**，不是等級 2 的 Per-Monitor）。曾經誤判拖曳跳動是 DPI 等級 2 造成的，改成等級 1 之後才發現真正原因是 §8.2 講的 pywebview 內建機制問題（100% 縮放下一樣會跳）。等級 1 保留下來是因為它確實解決了原本的文字模糊問題，跟拖曳 bug 無關，兩件事不要混為一談。四個地方都要一致：`gui_config.py`、`installer_core.py`、`splash.py`、`splash_helper.py`。

### 8.5 載入畫面（Splash）

**只接在 `InstallerBuilder.exe`（#1），沒有接在 `Setup_XXX.exe`（#2）**——這是刻意的產品決策：使用者明確表示安裝檔本身要盡量簡潔，只要求游標顯示 Windows 內建的 `IDC_APPSTARTING`（箭頭+小圈圈）游標即可，不要開額外視窗。`installer_core.py` 的 `_show_starting_cursor()` 就是做這件事。

#1 的 splash 機制：**不是**用 PyInstaller 原生的 `--splash`（那個只能放靜態圖片），是用 `splash.py` + `splash_helper.py` 這對檔案：`splash.py` 呼叫系統上真正的 `python.exe`/`pythonw.exe` 去跑 `splash_helper.py`（一支只依賴 tkinter 的獨立腳本），開一個貨真價實會轉動的進度條視窗。這樣做的取捨：exe 剛雙擊、bootloader 解壓縮那一兩秒沒辦法蓋到（因為 Python 都還沒開始執行），只能蓋到「Python 開始執行」之後、視窗真正出現之前那段。原生 `--splash` 能蓋到更早，但只能放靜態圖，兩者無法兼得，這次選了「真的會動的視窗」。

### 8.6 命令行視窗閃爍

所有從 `--noconsole` 編譯的 GUI 程式呼叫的 `subprocess` 都要加 `creationflags=getattr(subprocess, "CREATE_NO_WINDOW", 0)`，不然 Windows 會短暫跳出一個命令提示字元視窗。這個修正散布在：`splash.py`（呼叫 python 執行 splash_helper）、`builder.py`（呼叫 pyinstaller）、`gui_config.py`（環境檢查的 subprocess）、`installer_core.py`（`_is_process_running` 的 tasklist、`run_upgrade_uninstall` 的靜默解除安裝）、`uninstall.py`（`is_process_running`）、`build_config_tool.py`。**新增任何 subprocess 呼叫都要記得加這個旗標**。

### 8.7 靜默 / 命令列安裝

`Setup_XXX.exe` 支援 `/S`、`/D=路徑`、`/NODESKTOPSHORTCUT`、`/LOG=路徑`（見 `installer_core.py` 的 `_parse_cli_args()`），結果用 process exit code 回報（0=成功）。**這支 exe 是 `--noconsole` 編譯的，即使從 cmd 執行，也沒有主控台可以印字**——`print()` 完全無效，這是修過的一個真實坑：曾經寫了一堆 `print()` 訊息，實際上等於印給空氣看。現在改成把訊息收集起來，統一寫進紀錄檔，exit code 本身不受影響。

**紀錄檔路徑原本寫死是 `%TEMP%\<app_name>_silent_install_log.txt`，不可自訂**——企業批次部署（MDM/群組原則/登入腳本）如果要統一集中收集多台機器的安裝紀錄，沒辦法指定一個共用的網路路徑或固定位置，只能各自散落在每台機器自己的 `%TEMP%`。已修正：新增 `/LOG=路徑` 命令列參數（`Setup_XXX.exe`、`uninstall.exe` 都支援），有帶就優先寫到指定路徑（自動建立父目錄），寫入失敗（路徑不存在、沒有寫入權限）會退回原本的 `%TEMP%` 路徑並在 log 內容裡加一行警告，不讓「紀錄寫不進去」變成整個靜默安裝/解除安裝失敗；沒帶這個參數行為完全不變。這是**執行期**的旗標，不是打包時的設定欄位，`builder_cli.py`/`packaging_core.py` 不需要跟著改。

**這個坑不只出現在靜默安裝**：`_register_file_associations()`、`_register_uninstall_entry()`、`_add_to_path_env()` 這幾個寫登錄表的函式，原本失敗時也是用 `print()` 回報、被靜默吞掉，導致登錄表實際上沒寫成功，但安裝流程仍舊回報「安裝成功」，使用者完全查不出原因。已修正：這三個函式現在不再吞例外，失敗時直接往外拋，讓 `trigger_installation()` 既有的外層 `except`（本來就會 `_rollback()` + 回傳明確錯誤訊息）接住，統一走已經存在的失敗處理路徑。`_create_shortcut()` 是例外——捷徑建立失敗是刻意設計成「可忽略、不影響安裝」，這次維持該行為不變，只是把回報管道從 `print()` 換成呼叫端傳入的 `log()` callback，至少讓失敗訊息進得了 `install_log.txt`。**新增任何登錄表寫入邏輯，記得不要用 `print()` 回報錯誤，要嘛讓例外往外拋、要嘛透過 `log()` 寫進安裝紀錄檔。**（後續架構收斂：`_register_file_associations()` 這個方法本身已經不存在了，邏輯搬進 `file_assoc.py` 的 `register()`，見 §8.11；不吞例外的行為原封不動保留。）

### 8.8 環境檢查效能

`check_build_environment()`（`packaging_core.py`，`gui_config.py` 的 `ConfigAPI.check_environment()` 跟 `builder_cli.py` 的 `pack` 子指令都呼叫它）每次工具開啟（GUI）或執行 `pack`（CLI）都會觸發（GUI 是 `config.html` 的 `pywebviewready` 事件）。曾經是分兩次 `subprocess.run` 分別測 `import webview`、`import win32com.client`，每次都要重新啟動一個 Python 直譯器，開銷明顯。已合併成一個 `python -c` 呼叫，用一支小腳本印 `WEBVIEW_OK` / `PYWIN32_OK` 兩個標記字串，解析 stdout 判斷，直接砍半這個固定成本。

後來增加第三個標記 `MSIX_BACKEND_OK`（`import winrt.windows.management.deployment`，見 §8.37），沿用同一個子行程，不另外起一次。三個標記之中只有 `WEBVIEW_OK` 進入 `ready`：`pywin32` 與 `winrt-*` 都只影響部分功能，把它們算進總結論會讓用不到那些功能的人被擋在門外。

### 8.9 打包體積

`installer_core.py` 和 `gui_config.py` 都 `import webview`，PyInstaller 靜態分析是保守做法，只要程式碼「有可能」用到某個 pywebview 支援的 GUI 後端就整包塞入，即使 Windows 上實際只會用 EdgeChromium。實測過的 build log 裡有 `PyQt5.QtCore/QtGui/QtWidgets/QtNetwork` 的 hook 被處理，代表 PyQt5 整包（通常幾十 MB）被打包進去卻一行都用不到。`builder.py`（編 #2）跟 `build_config_tool.py`（編 #1）的 PyInstaller 指令都加了：

```
--exclude-module=PyQt5 --exclude-module=PyQt6
--exclude-module=PySide2 --exclude-module=PySide6 --exclude-module=gi
```

`uninstall.py` 沒有 `import webview`，不受影響，不需要加這些排除。

### 8.10 三個名稱的分工（容易搞混）

- **`exe_name`**：安裝檔本身的檔名（例如 `Setup_MyApp`），只在編譯階段用，不寫進 `installer_config.json`
- **`app_name`**：顯示名稱，可以是中文，寫進登錄表 `DisplayName`、安裝介面文字
- **`folder_name`**：只用來組安裝路徑，建議英數字，留空時 fallback 成 `app_name`

早期版本有個 bug：`app_name` 這個參數完全沒有從 `gui_config.py` 傳到 `builder.py`，`installer_config.json` 裡的 `"app_name"` 欄位其實是拿 `exe_name` 冒充，使用者填的「應用程式名稱」欄位從未真正生效。已修正，`builder.build_all()` 現在明確收 `app_name` 跟 `folder_name` 兩個獨立參數。

### 8.11 收斂檔案關聯登錄表邏輯 + 拆出共用深模組

`installer_core.py` 的 `_register_file_associations()` 跟 `uninstall.py` 的 `remove_file_associations()`，原本是兩個互不相依的檔案裡，各自維護一份幾乎一樣的登錄表操作（ProgID 命名慣例、關聯機碼、`UserChoice`/HKCU 覆寫/`OpenWithProgids`/`OpenWithList` 清除、`SHChangeNotify`），只靠註解跟命名慣例維持對稱——§8.7、§9 記錄的那幾輪 `UserChoice`/HKCU 覆寫修復，就已經因為這個原因漏改過一次。現在收斂進 `file_assoc.py`，暴露 `register()`/`unregister()` 兩個介面，兩邊呼叫同一份實作，不再是兩份要手動對齊的清單。

`register()`/`unregister()` 都吃一個 `registry` 參數，預設是真正的 `winreg` 模組；測試用 `tests/_fakes.py` 的 `FakeWinReg`（介面跟 `winreg` 一致）當這個參數傳進去，不需要 monkeypatch `sys.modules` 或模組屬性——這是「登錄表」這個概念在整個專案裡唯一的注入點。

同一輪順便把 `InstallerAPI` 裡兩塊幾乎不碰其他 class 狀態的邏輯拆成獨立模組：

- **`window_drag.py`**：`WindowDragController`，`gui_config.py` 的 `ConfigAPI` 跟 `installer_core.py` 的 `InstallerAPI` 原本各自寫了一份幾乎一樣的拖曳邏輯（前者用 `self._window`，後者用模組全域變數 `window`），現在共用同一份實作，呼叫端把目前的 window 物件當參數傳進去即可。
- **`disk_space.py`**：`check_drive_space()`/`required_install_size()`，純函式，不需要建構 `InstallerAPI()`（連帶觸發 `load_config()` 的檔案 I/O）就能測。`check_drive_space()` 接受一組「落地目錄 → 需要多少空間」，依磁碟代號分組加總後逐一檢查每顆磁碟：安裝內容可能同時落在安裝目錄、`%LOCALAPPDATA%\Programs\<folder_name>`（`local_appdata_files` 指定的檔案）與 `%TEMP%`（覆蓋安裝時舊安裝資料夾的整份備份），三者不保證位於同一顆磁碟。

`trigger_installation()` 本身（複製檔案 + 完整性驗證 + 失敗回滾的協定，148 行）**沒有拆**：套用刪除測試，拆開之後回滾協定的複雜度會原封不動在別處重現，不是真的拆掉了什麼，只是搬家。

**⚠️ 這三個新檔案（`file_assoc.py`、`window_drag.py`、`disk_space.py`）都要記得同步更新 §4 講的兩份清單**：`gui_config.py` 的 `ensure_workspace_files()` 的 `required_scripts`，跟 `build_config_tool.py` 的 `--add-data` 清單——因為 `installer_core.py`/`uninstall.py` 會被 `builder.py` 另外拉去重新編譯成獨立 exe，這三個共用模組必須實際存在於磁碟上（工作目錄）才能被那次編譯找到，忘記同步是跟 §4 記錄的舊 bug 一樣的成因。

另外新增了 `CONTEXT.md`，記錄「檔案關聯」「使用者關聯覆寫」「registry seam」這幾個這輪確立下來的概念名稱，跟這份文件互補：這份文件寫「為什麼」「踩過什麼坑」，`CONTEXT.md` 寫「這個詞叫什麼」。

### 8.12 更新覆蓋安裝或解除安裝時，可選擇偵測並結束鎖定檔案的進程

真實情境：應用程式如果註冊了 Windows 檔案總管殼層擴充功能（Shell Extension DLL，例如右鍵選單擴充），只要 `explorer.exe` 還活著就會把這支 DLL 常駐載入在自己的記憶體裡；也可能是其他背景進程持有安裝目錄下某些檔案的控制代碼。更新覆蓋安裝或解除安裝時，`uninstall.py` 依照 `install_manifest.json` 清單刪除舊檔案，如果清單裡有被鎖住的檔案，`os.remove()` 會直接失敗——**這跟系統管理員權限完全無關**（不是 §9 記錄的 pending-delete 競態，是另一個處理程序真的持有這個檔案的控制代碼，不會自己放手），重試也沒用，只能真的把持有它的處理程序關掉。

修法是打包時新增選填選項 `restart_explorer_on_update`（`installer_config.json` → `install_manifest.json` 一路帶過去），啟用後 `uninstall.py` 用 `restart_manager.py`（包 Windows 官方的 Restart Manager API，`Rstrtmgr.dll`——Windows Installer、PowerToys 的 File Locksmith 判斷「這個檔案被誰鎖住」用的是同一套機制）在「正在刪除安裝目錄下的檔案」之前，實際偵測是哪些進程持有這批檔案的控制代碼，用 `_kill_processes()` 逐一結束真正的鎖定者——不是無差別假設一定是 `explorer.exe`。刪除完畢後，如果剛好結束掉的進程裡有 `explorer.exe`（用 `_process_image_name()` 查真正的執行檔檔名判斷，Restart Manager 回傳的 `strAppName` 是給使用者看的友善名稱，不能直接拿來比對），才會自動重啟它；其他進程通常是使用者自己的應用程式，不會自動重新開啟。閘門條件見 `_wants_lock_release()`：不分互動或無人值守都會套用，但互動式（使用者手動解除安裝）會先跳 `_confirm_kill_locking_processes()` 確認對話框，列出實際偵測到的進程名稱，取得同意才真的結束，避免無預警強制關閉使用者正在用的其他程式。預設不啟用，只有真的有殼層擴充功能之類會鎖住檔案的情況才建議勾選。

**修正紀錄（真實抓到的 bug，導致行為「時好時壞」）**：`run_upgrade_uninstall()` 呼叫的是**舊版本**的 `uninstall.exe --silent`，這支舊版 exe 判斷要不要關閉檔案總管，原本只看它自己那份 `install_manifest.json`（舊版本安裝當下寫的），跟使用者這次重新打包、剛勾選的新設定完全是兩回事——checked 這個選項只會影響「以後這個新版本自己被解除安裝」的行為，完全不會影響「這次拿舊版本的 uninstall.exe 來移除它自己」這個當下的行為。實際後果：每次安裝嘗試（不論成功或失敗）都可能在磁碟上留下不同版本的 `install_manifest.json`，這次更新覆蓋到底會不會關閉檔案總管，取決於上一輪剛好留下哪份 manifest，不是使用者這次的選擇，看起來就是隨機的「時好時壞」。已修正：新增 `--restart-explorer` 命令列旗標，`installer_core.py` 的 `run_upgrade_uninstall()` 帶著**這次（新版本）**的 `restart_explorer_on_update` 設定明確傳給舊版 `uninstall.exe`；`uninstall.py` 的 `_should_restart_explorer(silent, manifest, argv)` 優先看這個旗標，沒帶旗標時（手動雙擊解除安裝、或不是被更新流程觸發的純靜默解除安裝）才退回讀 manifest 自己的設定。**已知限制**：如果目前安裝的舊版本本身是用更早、還沒有這個 `--restart-explorer` 支援的舊版 `uninstall.exe`，這個旗標對它沒有意義（舊版 exe 根本不認得這個參數，會被忽略）——這種情況第一次遷移仍需要使用者手動處理一次鎖定的檔案，等新版本安裝完成、往後再次更新時才會是「新版本呼叫新版本」，`--restart-explorer` 才能正常生效。

**修正紀錄（真實抓到的 bug，導致「手動解除安裝後 DLL 還在，下次安裝時誤報權限不足」）**：這個選項原本只在無人值守（`silent`）情境套用，理由是「不該無預警把使用者的檔案總管視窗全部關掉」——但這麼一來，只要應用程式有勾選 `restart_explorer_on_update`，使用者**手動雙擊解除安裝**時這個保護完全不會生效：被鎖住的檔案刪不掉，`os.remove()` 的例外又被靜默吞掉只寫進 log（畫面上不會提示），檔案就這樣留在安裝目錄。下次重新安裝到同一路徑，複製流程想覆寫這個仍被鎖住的檔案就會失敗，`installer_core.py` 把這類失敗一律顯示成「安裝失敗：權限不足」，使用者以管理員身分重試依然失敗（跟權限完全無關，只有真的把持有它的處理程序關掉才有用），非常容易誤判。已修正：判斷函式拿掉 `silent` 參數與早期短路，不分互動或無人值守，只回答「設定上想不想要」；互動情境改由 `main()` 額外跳一次 Yes/No 確認對話框，取得使用者同意後才真的執行結束進程；選「否」的話解除安裝仍會繼續，只是被鎖住的檔案可能刪不掉（跟修正前手動解除安裝的既有行為一致，只是現在使用者知情、可以選擇）。

**修正紀錄（真實抓到的 bug，也是使用者實測回報：手動解除安裝後仍有殼層擴充功能 DLL 殘留，導致下次安裝誤報權限不足）**：上面這個修正讓互動式解除安裝也會嘗試釋放鎖定的檔案，但當時的做法仍然是寫死「一定是 `explorer.exe` 鎖住」，直接 `taskkill /im explorer.exe`——只涵蓋殼層擴充功能這一種特定情境，治標不治本：如果卡住檔案的其實是別的進程（例如某個背景服務、或另一個掛勾進來的第三方程式），完全偵測不到也處理不了，使用者得像用 PowerToys 的 File Locksmith 那樣手動找出真正持有控制代碼的進程才能解決。已修正：新增 `restart_manager.py`，用 ctypes 呼叫 Windows 官方的 Restart Manager API（`RmStartSession`/`RmRegisterResources`/`RmGetList`/`RmEndSession`，不需要額外安裝套件），實際偵測「目前是哪些進程持有指定檔案的控制代碼」，回傳 `[(pid, 使用者友善名稱), ...]`。`uninstall.py` 的 `_kill_processes()` 取代原本的 `_kill_explorer()`，逐一 `taskkill /f /pid <pid>` 結束真正的鎖定者；`_process_image_name()` 用 `tasklist` 另外查每個 pid 真正的執行檔檔名（Restart Manager 的 `strAppName` 是 localized 友善名稱，例如 `explorer.exe` 常顯示成「Windows 檔案總管」，不能直接拿來判斷是不是 `explorer.exe`），只有結束掉的進程剛好是 `explorer.exe` 才自動重啟；互動式確認對話框（`_confirm_kill_locking_processes()`，取代原本的 `_confirm_restart_explorer()`）也改成列出實際偵測到的進程名稱，不再一律寫死「檔案總管」。`restart_explorer_on_update` 這個打包欄位名稱維持不變（避免破壞既有打包設定的相容性），只是底層機制從「固定關閉 explorer.exe」改成「偵測真正的鎖定者」。

### 8.13 多語言介面 + 多語言 EULA

對應 §10 backlog 舊項目 #4（已實作）。三個子系統各自的語言決定方式不一樣，刻意設計成不同機制：

- **打包工具介面（`config.html`）**：語言可由開發者手動切換（標題列的下拉選單），初次開啟預設呼叫 `ConfigAPI.get_system_language()`（內部呼叫 `lang_detect.detect_system_language()`）偵測開發者本機的系統語言；手動切換過的選擇存進瀏覽器端的 `localStorage`（key: `builder_lang`），下次開啟這個工具沿用，不需要每次重選。
- **安裝檔介面（`ui/index.html`）**：語言**不給終端使用者選**，`InstallerAPI.__init__()` 呼叫同一個 `lang_detect.detect_system_language()` 算出 `self.ui_language`，`index.html` 在 `pywebviewready` 一開始就呼叫 `get_ui_language()` 並套用翻譯表，早於其他任何初始化步驟。
- **多語言 EULA**：見 §5.1 對 `eula_texts`/`eula_default_lang` 的說明，`installer_core.py` 的 `get_eula_text()` 是回退鏈的唯一實作位置。

**共用語言偵測模組**：`lang_detect.py` 的 `detect_system_language(supported, default)`，用 `ctypes.windll.kernel32.GetUserDefaultLocaleName()` 取得類似 `"zh-TW"`／`"en-US"` 的 BCP-47 標籤，依序嘗試完整標籤比對 → 只比對主語言代碼（`"en-US"` 的 `"en"` 對到 `supported` 裡的 `"en"`）→ 都對不到就回傳 `default`。這是整個專案唯一一個讀 Windows 系統語言的地方，`gui_config.py`、`installer_core.py` 都呼叫它，不重複實作。**跟 §8.11 的 `file_assoc.py`/`window_drag.py`/`disk_space.py` 一樣，是要被 `installer_core.py`（跟 `gui_config.py` 自己）匯入的共用深模組，一樣要記得同步 §4 講的兩份清單**（`ensure_workspace_files()` 的 `required_scripts`、`build_config_tool.py` 的 `--add-data`），這輪已經加好。

**介面字串抽離的做法**：`ui/config.html`、`ui/index.html` 各自內嵌一份 `I18N` 翻譯表（JS 物件，不用外部檔案或建置工具），靜態文字用 `data-i18n`/`data-i18n-placeholder`/`data-i18n-title`/`data-i18n-html` 屬性標記對應的 key，`applyI18n(lang)` 統一套用；JS 組出來的動態訊息（例如覆蓋安裝三態提示裡帶版本號的句子）改用 `t(key, {變數: 值})`，翻譯表裡對應字串用 `{{變數}}` 佔位符。

**已知限制（刻意的範圍界定，不是遺漏）**：
- 目前只支援**繁體中文、英文**兩種安裝介面 chrome 語言，對應 `SUPPORTED_UI_LANGUAGES`（`installer_core.py`）跟 `BUILDER_UI_LANGUAGES`（`gui_config.py`）這兩個清單；EULA 文字語言不受此限制，開發者可自訂任意語言代碼。
- `builder.py` 在編譯過程中透過 `progress_callback` 回報的階段性進度文字（例如「正在編譯解除安裝助手...」），以及 `installer_core.py` 在 `trigger_installation()`／`run_upgrade_uninstall()` 過程中回報的進度與錯誤訊息（例如「磁碟空間不足」），這次**沒有**字串抽離，不論打包工具或安裝介面切成哪個語言，這些訊息都固定顯示繁體中文。原因是這些字串目前是 Python 端直接組好的完整句子（很多還內嵌動態數值），要翻譯需要先把它們也改成「傳 key + 參數」的形式，範圍已經超出這次「介面 chrome + EULA」的既定範圍，之後有需要可以用同一套 `I18N`/`t()` 模式擴充。
- `uninstall.py` 互動模式（使用者手動雙擊解除安裝跳出的確認對話框）文字固定繁體中文，同樣尚未納入這次範圍。
- 安裝流程中，`ui/index.html` 顯示的單一實例鎖對話框（webview 視窗建立**之前**跳出的原生 `MessageBoxW`）沒辦法套用 JS 翻譯表，改成在 `installer_core.py` 的 `__main__` 區塊直接呼叫一次 `lang_detect.detect_system_language()`，從寫死的中英文兩句二選一。
- **真實抓到的落差（直接比對 `ui/index.html` 的 `I18N["zh-TW"]`/`I18N["en"]` 兩個物件的 key 才發現，不是設計上刻意的範圍界定）**：`index.html` 的英文字典漏了 7 個 key——`process_running_title`／`btn_close_and_continue`／`btn_force_continue`（偵測到主程式正在執行那組畫面）、`file_locked_title`／`btn_close_locking_process`（檔案使用中畫面）、`upgrade_older_title`／`upgrade_older_msg`（偵測到已安裝較新版本畫面）。`t()` 對到英文字典缺 key 時會靜默 fallback 回 `zh-TW` 的值（不會拋錯、不會有任何警示），所以英文系統的使用者裝到這三種情境時會突然看到繁體中文，其餘畫面都是正常英文——沒有被以前任何一次「英文語系手動過一遍畫面」的驗收流程抓到，因為這三種情境（主程式正在執行/檔案被鎖住/偵測到較新版本）平常測試不容易觸發。`ui/uninstall.html`（23/23）跟 `ui/config.html`（106/106）兩份字典經比對過完全對齊，只有 `index.html` 有這個缺口。修正時把這 7 個 key 加進 `I18N["en"]` 即可，不需要改動任何 HTML/JS 邏輯。

### 8.14 「加入 PATH」可以指定跟主程式不同的 exe

對應 §10 backlog 舊項目 #1（已實作）。原本 `add_to_path` 只會把**整個安裝目錄**加進 PATH——有些應用程式同時附一個 GUI 主程式跟一支獨立的 CLI 工具（例如放在安裝目錄底下的子資料夾），開發者可能只想讓 CLI 工具能被全域呼叫，不需要（或不希望）整個安裝目錄下所有 exe 都變成全域可呼叫。

新增選填欄位 `path_target_exe`（`installer_config.json` → `installer_core.py`）：`config.html` 在「加入 PATH」勾選之後，多一個下拉選單（沿用 `list_exe_files()` 現成的掃描機制，跟 `main_exe` 那個下拉選單用同一份清單），開發者可以另外指定一支執行檔；不選就是空字串，維持原本「整個安裝目錄」的行為。

`installer_core.py` 新增 `_path_target_dir()`：`path_target_exe` 有值就回傳 `os.path.dirname(os.path.join(self.selected_path, path_target_exe))`，空字串或指到安裝根目錄下的執行檔（`dirname` 算出來是空字串）都回傳 `self.selected_path`。`_add_to_path_env()` 改用這個目錄寫入登錄表 `Path`，並**回傳實際加入的目錄字串**——這個回傳值很關鍵，因為 `trigger_installation()` 要把它寫進 `install_manifest.json` 的新欄位 `path_directory`（見 §5.2），解除安裝時才知道當初到底加了哪個目錄，不是每次都假設是 `install_path`。

`uninstall.py` 新增 `_path_removal_target(manifest, current_dir)`：優先用 `path_directory`，沒有這個欄位（舊版本安裝時這個功能還不存在，寫入的 manifest 缺這個 key）才退回 `install_path`，維持舊版本的行為不受影響。

### 8.15 修正「更新覆蓋安裝回報成功，但檔案沒有複製完整」的競態

使用者實際回報的真實 bug：安裝視窗顯示「安裝成功」，但安裝目錄裡的檔案沒有 100% 複製完整，**只發生在更新/覆蓋安裝**。根因是兩個既有機制疊加出的競態：

1. `installer_core.py` 的 `run_upgrade_uninstall()` 用 `subprocess.run(cmd, timeout=30, ...)` **同步**呼叫舊版本的 `uninstall.exe --silent`，等它的行程結束就繼續往下跑。
2. `uninstall.py` 的 `main()` 尾端「自我刪除」那段本身是 **fire-and-forget**：前景清理（登錄表、捷徑、檔案關聯、PATH、依清單刪檔）做完之後，最後才呼叫`subprocess.Popen(cmd_command, shell=True, ...)` 開一個**不等待**的背景 `cmd.exe`，內容是先 `ping 127.0.0.1 -n 2` 製造約 1 秒延遲（讓 `uninstall.exe` 自己的行程先真正結束，Windows 不能刪除還在執行中的 exe），延遲過後才真正 `del` 自己、視情況 `rmdir /s /q` 整個安裝目錄。

`Popen()` 呼叫完立刻回傳，`uninstall.exe` 馬上 `sys.exit(0)`——`run_upgrade_uninstall()` 這邊的 `subprocess.run()` 幾乎瞬間就返回，這時候那個延遲約 1 秒後才會真正執行的 `rmdir /s /q` 根本還沒發生。`_wait_for_selected_path_writable()` 當時只是重試 `os.makedirs(selected_path, exist_ok=True)`，這時候目錄通常本來就還存在（延遲還沒過），`makedirs` 立刻成功，完全沒有真的等到那段背景指令跑完。於是 `trigger_installation()` 馬上開始把新版本的檔案複製進這個目錄——**跟延遲後才觸發的 `rmdir /s /q` 同時搶同一個資料夾**：如果複製時間跨過那 1 秒視窗，背景指令觸發時會把整個資料夾（含已經複製好的新檔案）一起砍掉；沒跨過就相安無事。這正好解釋「有時候會、有時候不會」、且「只有更新覆蓋安裝才會」的症狀——`trigger_installation()` 的完整性驗證只在複製當下比對來源/目的地，抓不到「複製完之後、回報成功之前，檔案被背景行程事後刪掉」這種情況。

**修法**：`run_upgrade_uninstall()` 呼叫舊版 `uninstall.exe` 時一律加上新的 `--upgrade` 命令列旗標。`uninstall.py` 新增 `_is_upgrade_call(argv)` 判斷這個旗標，`_should_schedule_self_delete(is_upgrade)` 在 `is_upgrade` 為真時回傳 `False`——`main()` 尾端完全跳過整段自我刪除背景指令（不排 `ping`/`del`/`rmdir`，前景清理完直接 `return`）：

- 這支舊版 `uninstall.exe` 的行程本身已經確定執行完畢即將結束，它自己的 exe 檔案已經沒有任何行程占用，不需要靠延遲的背景指令才能刪除。
- `trigger_installation()` 稍後本來就會把新版本自己的 `uninstall.exe` 複製到同一個路徑蓋過去（約 85% 進度那一步），舊的那份不刪也會被直接覆蓋。
- 資料夾本身也不需要 `rmdir`——新版本安裝流程接下來就要重用這個目錄。
- `run_upgrade_uninstall()` 之後的步驟如果失敗，既有的 `_restore_upgrade_backup()` 機制會把整個舊目錄從備份搬回來，不受這次改動影響——備份是在舊 `uninstall.exe` 執行「之前」拍的快照，跟它有沒有自刪無關。

這個修法徹底消除競態視窗，不是靠調整延遲時間、猜測夠不夠久這種治標做法。只影響「被更新覆蓋流程呼叫」這一種情境，一般使用者手動雙擊解除安裝、或企業批次 `--silent`（非更新觸發）完全不受影響，繼續用原本的行為。`_wait_for_selected_path_writable()` 保留下來，但職責改成只處理殘餘的、影響小得多的單一檔案層級 pending-delete 情況（例如防毒軟體掃描造成的短暫延遲），不再是防禦這個整個資料夾被非同步刪除的競態。

**已知限制**：如果目前安裝的舊版本本身是用更早、還沒有 `--upgrade` 支援的舊版 `uninstall.exe`，這個旗標對它沒有意義（舊版 exe 根本不認得這個參數，會被忽略，仍照舊排出那段有競態風險的背景自我刪除指令）——跟 §8.12 `--restart-explorer` 的已知限制是同一類情況，第一次從這麼舊的版本更新可能仍會遇到這個問題，等新版本安裝完成、往後再次更新時才會是「新版本呼叫新版本」，這個修正才能確實生效。

### 8.16 安裝時偵測到主程式執行中，改成互動式「關閉／取消」

原本 `trigger_installation()` 偵測到 `main_exe` 正在執行時直接回傳
`{"status": "error", ...}`，逼使用者自己找到並手動關閉程式後重新執行一次
安裝檔。改成回傳獨立的 `{"status": "process_running", "message": "..."}`，
`ui/index.html` 收到這個狀態會跳出專屬彈窗（`#processRunningModal`），
提供「關閉程式並繼續安裝」／「取消」兩個按鈕：

- 「關閉程式並繼續安裝」→ 呼叫新增的 `InstallerAPI.close_running_main_exe()`
  （`taskkill /f /im <main_exe 檔名>`，寫法比照 `uninstall.py` 既有的慣例：
  `CREATE_NO_WINDOW`、吞例外、回傳布林值，不做「先禮貌關閉、失敗才強制」
  的分層）→ 重新呼叫一次 `trigger_installation()`。
- 「取消」→ 關閉彈窗，把進度條/路徑預覽重置回安裝前的樣子，不做任何事。

`ui/index.html` 把「呼叫 `trigger_installation()` 並依結果分流」這段
從原本寫死在 `drop` 事件處理常式裡，抽成獨立的 `attemptInstall(
createDesktopShortcut)` 函式，`drop` 事件跟「關閉程式並繼續安裝」按鈕
共用同一個函式，避免安裝觸發邏輯要維護兩份。

### 8.17 打包工具 GUI/CLI 雙介面

#1（打包工具）原本只有 `gui_config.py`（pywebview GUI）一種介面。新增
`builder_cli.py`，讓開發者可以純靠指令把應用程式資料夾打包成安裝檔，
不需要開視窗（例如寫進 CI 腳本）。使用方式見 `CLI_USAGE.md`。

**拆分方式**：`gui_config.py` 原本的模組層級函式（`get_resource_path`、
`get_workspace_dir`、`check_build_environment`、`ensure_workspace_files`、
`validate_and_build_pack_data`）其實從來不依賴 `pywebview`——真正 GUI
專屬的只有 `ConfigAPI` 這個 class（視窗拖曳/縮放、檔案選擇對話框、
`start_pack()` 的背景執行緒 + `window.evaluate_js()` 進度回報）。但
`gui_config.py` 檔案開頭就 `import webview`，只要 `builder_cli.py` 直接
`from gui_config import ...`，就會強迫 CLI 使用情境也要裝 pywebview——
對「純指令、可能沒有 GUI 環境（例如 CI 容器）」的使用情境不合理。所以
把這幾個函式搬進新檔案 `packaging_core.py`（完全不 import pywebview），
`gui_config.py` 改成 `from packaging_core import ...`，`builder_cli.py`
也直接 import 它，兩邊共用同一份驗證/環境檢查/工作目錄準備邏輯，不會
有兩邊規則兜不起來的問題。比照這個專案既有「拆出共用深模組」的慣例
（見 §8.11、§8.13 的 `lang_detect.py`）。

**`builder_cli.py` 的介面**：`init`（產生範本 JSON 設定檔）跟 `pack`
（驗證 + 編譯）兩個子指令。輸入方式是 **JSON 設定檔為主，額外支援用
命令列參數覆蓋個別欄位**（CLI 優先於 JSON）——`_load_pack_input()` 負責
這個合併邏輯：先讀 JSON（沒給 `--config` 就從空字典開始），再用命令列
有帶值的參數覆蓋對應欄位。`need_file_assoc`/`use_custom_doc_icon` 這兩個
GUI 版靠勾選框決定的布林欄位，CLI 版直接依對應欄位（`file_associations`/
`doc_icon`）是否有內容推斷，不需要使用者額外指定一個看起來多餘的旗標。
進度回報透過 `progress_callback` 印到 stdout（`[百分比%] 訊息`），不是
`window.evaluate_js()`。

**`build_config_tool.py` 的對應調整**：這支腳本負責把 `gui_config.py`/
`builder_cli.py` 編譯成 exe（是「打包工具的打包工具」，跟 #1/#2/#3 那三顆
是不同層次的東西）。實際建置一顆 exe 的邏輯（清理 dist/build、組
PyInstaller 指令、跑子行程、串流輸出、檢查產出）抽成獨立函式
`build_one_exe(entry_script, output_name, icon_path, noconsole,
extra_add_data, on_log, on_progress)`，回傳 `(success, message, exe_path)`。
互動模式（`python build_config_tool.py`，開 Tkinter 視窗，行為跟以前一樣，
只編 GUI 版、檔名固定 `InstallerBuilder.exe`）跟新增的非互動模式
（`python build_config_tool.py --cli [--version X.Y.Z] [--icon xxx.ico]`，
依序編 GUI 版跟 CLI 版兩顆 exe，檔名嵌入版本號：
`mac-style-windows-installer_GUI_vX.Y.Z.exe` /
`mac-style-windows-installer_CLI_vX.Y.Z.exe`）都呼叫同一個函式。兩個
目標各自需要的 `--add-data` 清單不完全一樣（`_GUI_ADD_DATA` 多了
`splash_helper.py`，CLI 沒有 Tkinter 載入畫面不需要），拆成
`_GUI_ADD_DATA`/`_CLI_ADD_DATA` 兩份常數。`--cli` 模式主要是給
`/released` 這類自動化流程呼叫（見 CLAUDE 本機的 `/released` skill），
一般開發者手動編譯打包工具用互動模式通常更方便。

**版本號單一真實來源**：新增 repo 根目錄的 `VERSION` 純文字檔（一行，
例如 `0.7.0`）。`build_config_tool.py` 的 `read_version(explicit_version)`
優先用明確傳入的版本號，沒有才讀 `VERSION` 檔案；檔案不存在或是空的，
用 `"0.0.0-dev"` 這種一看就知道還沒定版的預設值，不會悄悄冒充一個正常
版本號騙過使用者。`/released` skill 發布新版本時會更新這個檔案。

### 8.18 `/released` 實際跑過一輪才發現的問題

v0.8.0 是第一次真正跑完整個 `/released` 流程（§8.17 落地後的第一次），
過程中發現兩個先前的實作跟測試都沒抓到的問題：

**`build_one_exe()` 清理舊產物時整個清空 `dist/`，多目標依序建置時
會互刪**：原本 `build_config_tool.py` 的 stale-artifact 清理邏輯是
`shutil.rmtree("dist")`，`--cli` 模式依序編 GUI、CLI 兩顆 exe 時，編
CLI 版會把剛編好、還躺在 `dist/` 底下的 GUI exe 一起刪掉。改成只清除
這次要編的目標自己的殘留產物（`dist/{output_name}.exe`、
`build/{output_name}/`、`{output_name}.spec`），不動 `dist/` 底下其他
已經編好的檔案。單元測試沒抓到是因為都 mock 掉了 `build_one_exe()`，
沒有真的連續呼叫兩次驗證兩邊的輸出都還在——之後補了
`tests/test_build_config_tool.py` 的
`test_stale_cleanup_only_touches_own_target_not_other_builds_output`
涵蓋這個情境。

**打包安裝檔時，`app_dir` 不能放在 repo 自己的 `dist/` 底下**：
`builder_cli.py pack` 呼叫的 `builder.py`/`build_all()`，執行時也會
清空自己工作目錄（`get_workspace_dir()`，`.py` 直接執行時就是目前工作
目錄）下的 `dist/`；如果拿來當「要被打包的應用程式內容」的暫存資料夾
剛好放在同一個 `dist/` 底下，還沒被讀進去打包就先被這個清理動作刪掉，
`pack` 會直接失敗並回報「找不到」該路徑。這不是程式的 bug（`dist/`
本來就被兩邊各自視為自己的工作區、互不知道對方存在），而是使用時要
避開的陷阱——`/released` skill 的步驟 6 現在明確要求暫存資料夾要放在
repo 的 `dist/` 之外。

**PATH 指令名稱固定，不隨版本號變動**：`build_config_tool.py --cli`
編出來的兩顆 exe 檔名會嵌入版本號（`..._GUI_vX.Y.Z.exe`／
`..._CLI_vX.Y.Z.exe`），如果直接拿這兩個檔名當 `main_exe`／
`path_target_exe` 打包進安裝檔，使用者裝完之後要在 CMD 打的指令也會
含版本號，每次升版都要跟著改指令、寫進腳本裡的呼叫方式也會失效。
`/released` skill 現在在打包前，把這兩顆 exe 複製一份、改成不帶版本號
的固定檔名（`mswi-gui.exe`／`mswi-cli.exe`）再餵給 `builder_cli.py
pack`，讓安裝到使用者電腦上的執行檔名稱固定不變，跟 `dist/` 底下含
版本號的建置產物檔名是兩個不同層次的東西——前者是「這次建置編出來的
是哪個版本」的紀錄，後者是「使用者實際裝到電腦上、往後每次升版都要
維持一致」的介面。

### 8.19 打包時可指定某幾支檔案改裝到 `%LOCALAPPDATA%`（不需要系統管理員權限）

**動機**：主安裝目錄常常在 `Program Files` 底下，寫入需要系統管理員權限
（安裝檔本身就是 `--uac-admin` 編譯，這點沒問題）；但如果應用程式除了
主程式外，還附了一支獨立的命令列工具（例如 mswi-cli，見 §8.17／
`CLI_USAGE.md`），這支工具平常被「執行」的頻率遠高於主程式，如果也裝
在 `Program Files` 底下，使用者事後單純想跑一個指令，很多情境下也會被
系統要求提權（例如工具自己要在自己所在的目錄寫檔案），這對一個純粹的
命令列工具來說是不必要的摩擦——這是在其他專案上實測踩到的真實問題。

**設計**：新增選填欄位 `local_appdata_files`（`config.html`／
`installer_pack_config.json`／CLI `--local-appdata-files`）：一份相對於
`app_dir` 的檔案路徑清單，安裝時這些檔案改裝到
`%LOCALAPPDATA%\Programs\<folder_name>`（使用者自己的目錄，寫入不需要
系統管理員權限），其餘沒列出的檔案維持原行為，裝進 `self.selected_path`
（主安裝目錄）。**只有「安裝/解除安裝」這個動作本身仍然需要系統管理員
權限**（要寫登錄表、PATH 等系統層級項目），改變的是「裝完之後，使用者
事後執行這支工具」不需要每次都提權。

**實作**：`installer_core.py` 新增 `_local_appdata_root()`（算出
`%LOCALAPPDATA%\Programs\<folder_name>` 這個目錄）、
`_is_local_appdata_file(rel_path)`（判斷某個相對路徑是否在
`local_appdata_files` 清單內，正規化過反斜線/正斜線差異）、
`_resolve_installed_path(rel_path)`（統一入口：清單內的檔案解析到
`_local_appdata_root()`，其餘解析到 `self.selected_path`）。原本所有
直接用 `os.path.join(self.selected_path, self.main_exe)` 這種寫法算
「檔案實際裝到哪」的地方（複製迴圈、`_register_uninstall_entry`、
`_create_shortcut`、`launch_app`、安裝結果的 `main_exe_path`），全部
改用 `_resolve_installed_path()`，不會有兩套邏輯各自算一次、之後改動
其中一邊漏改另一邊的風險。

**PATH 自動整合**：`_path_target_dir()`（見 §8.14）改用
`_resolve_installed_path(self.path_target_exe)` 算目錄，如果
`path_target_exe` 剛好也列在 `local_appdata_files` 裡，PATH 會自動指向
`_local_appdata_root()`，不需要另外設定——這是回答使用者提出這個需求時
確認過的整合方式，避免同一支執行檔要在兩個獨立欄位重複描述一次「它在
哪裡」。

**回滾與解除安裝**：`install_manifest.json` 新增 `local_appdata_files`
（清單原封不動記一份）跟 `local_appdata_dir`（`_local_appdata_root()`
解析出來的絕對路徑，供 `uninstall.py` 不需要重新推導 `folder_name` 也能
直接用）。`installer_core.py` 的 `_rollback()`（安裝失敗回滾）跟
`uninstall.py` 的清單式刪除都改成：清單內的檔案先判斷落在主安裝目錄還是
`local_appdata_dir`，分別刪除，刪完各自檢查是否清空、清空了才把該目錄
一起移除——`_local_appdata_root()` 只會被當成「這個應用程式自己專屬」
的子目錄清掉，不會動到 `%LOCALAPPDATA%\Programs\` 這個共用父目錄本身
（可能還裝著其他應用程式）。`_rollback()` 抽出共用的
`_cleanup_empty_dirs(root_dir)` 靜態方法，`uninstall.py` 也有一份對應的
`_cleanup_empty_dirs()` 函式跟 `_local_appdata_resolver(manifest)`（同樣
的清單比對邏輯，讀 manifest 而不是讀 `self`，因為 `uninstall.py` 是
獨立腳本、沒有 `InstallerAPI` 這個物件）。

**已知限制**：如果安裝程式是用跟目前登入使用者不同的系統管理員帳號提權
執行（例如切換帳號的 UAC 提示），這裡解析出來的 `%LOCALAPPDATA%` 會是
提權帳號的，不是原本操作安裝程式那個使用者的目錄——多數情境下 UAC
沿用同一個帳號的提權權杖，不會踩到這個邊界案例，這裡先記錄，沒有實際
處理跨帳號的情況。`doc_icon`／`uninstall.exe`／`installer_config.json`
這幾個非 `app_dir` 內容的檔案不支援改裝到別位目錄，固定留在主安裝目錄
（解除安裝助手需要跟 manifest 放在一起才找得到）。

### 8.20 檔案關聯可以幫不同副檔名各自設定不同圖示

**動機**：原本 `doc_icon` 是單一欄位，勾選「自訂文件圖示」之後，所有
`file_associations` 列出的副檔名全部共用同一張 ICO。如果應用程式關聯
了多種副檔名，各自代表不同的檔案類型（例如 `.a` 是專案檔、`.b` 是匯出
檔），使用者會希望在檔案總管裡一眼就能靠圖示分辨，而不是全部長得一樣。

**設計**：新增選填欄位 `doc_icons`（`config.html`／
`installer_pack_config.json`／JSON only，沒有對應的命令列 flag，理由
跟 `eula_texts` 一樣——字典結構塞進單一命令列參數不實際）：一份
`{副檔名: ICO 來源路徑}` 的對照表。`packaging_core.py` 的
`validate_and_build_pack_data()` 驗證每個副檔名都要先出現在
`file_associations` 清單裡（避免打字錯誤、或設定了根本沒關聯的副檔名）、
每個值都要是 `.ico` 結尾。

**打包階段**（`builder.py`）：每個副檔名各自複製一份固定命名的圖示
（`doc_icon_<副檔名去掉點>.ico`，例如 `.xyz` → `doc_icon_xyz.ico`），
避免不同副檔名剛好選了同名但內容不同的原始檔案時互相覆蓋；每一張都
各自 `--add-data` 內嵌進安裝檔；寫進 `installer_config.json` 的
`doc_icons` 是 `{副檔名: 內嵌檔名}` 這個轉換後的對照表（來源絕對路徑
不會外洩進設定檔裡）。

**安裝階段**（`installer_core.py`）：`_resolve_doc_icon_ref(main_exe_path,
ext)` 決定某個副檔名要用哪張圖示，依序 fallback：這個副檔名自己在
`doc_icons` 裡的設定 → 共用的 `doc_icon` → `main_exe` 圖示；
`_resolve_doc_icon_refs(main_exe_path)` 幫 `file_associations` 裡每個
副檔名都算好，組成字典交給 `file_assoc.register()`。`file_assoc.py`
的 `register()` 簽名也跟著從單一 `icon_ref` 改成 `icon_refs` 字典——
每個副檔名本來就有自己獨立的 ProgID（`prog_id()`）、獨立的
`DefaultIcon` 子機碼，天生互不影響，這裡只是把「所有副檔名共用同一個
圖示」這個呼叫端假設拿掉，`unregister()`／解除安裝端的清除邏輯完全
不受影響（清除只需要副檔名清單，不需要知道圖示）。

**GUI**（`config.html`）：勾選「需要註冊檔案關聯」並輸入多個副檔名後，
「個別副檔名的專屬圖示」區塊會依輸入框內容動態列出每一個副檔名，各自
可以選一張 ICO（新增後端方法 `select_extension_icon()`，故意獨立於
`select_doc_icon()`／`self.doc_icon_path`，避免兩個各自獨立的圖示選擇
互相污染對方的後端狀態）；不選的副檔名維持原本的 fallback 行為。

### 8.21 安裝失敗訊息依真正的 Windows 錯誤碼分類，不再一律歸類成「權限不足」

**真實情境（使用者實測回報）**：`trigger_installation()` 原本不管複製檔案
時實際發生什麼錯誤，只要是 `PermissionError` 就一律顯示「安裝失敗：權限
不足，請以管理員身分執行」。但這支安裝程式（`--uac-admin` 編譯）本身
Windows 執行前就已經先跳出 UAC、要求使用者同意用系統管理員身分執行——
執行到這裡的程式碼**一定已經是系統管理員權杖**，「以管理員身分重試」這
個建議在這裡幾乎不可能是真正有效的解法，反而最常見的真正原因是檔案正被
其他進程鎖住（Windows 的 sharing violation，Python 一樣包成
`PermissionError`，但成因跟系統管理員權限完全無關），把這麼多種不同成因
的錯誤全部混在一起顯示成同一句話，會誤導使用者反覆做沒有用的事（例如
一直用管理員身分重跑，而真正該做的是先關掉鎖住檔案的程式）。

**修法**：新增 `_describe_install_os_error(error, dest_file)`，用
`error.winerror`（Windows 特有，`OSError` 除了 `errno` 之外還會帶原始的
Win32 錯誤碼）分辨真正的成因：

- `ERROR_SHARING_VIOLATION` (32) / `ERROR_LOCK_VIOLATION` (33)：檔案被
  其他進程開著——用 `restart_manager.find_locking_processes()`（跟
  `uninstall.py` 解除安裝時偵測鎖定進程用的是同一套 Restart Manager
  API，見 §8.12）實際查出是哪個進程鎖住了這個檔案，能查到就直接在訊息
  裡點名，讓使用者知道要關掉什麼，而不是只丟一句「權限不足」讓使用者
  自己猜。
- `ERROR_ACCESS_DENIED` (5)：安裝程式已經是系統管理員身分，還被拒絕
  存取，比較可能是防毒軟體、Windows 防勒索軟體的「受控資料夾存取」，
  或企業網域原則限制了這個安裝路徑——訊息明確排除「以管理員身分重試」
  這個沒有用的建議，改指向真正可能的成因。
- `ERROR_WRITE_PROTECT` (19)：目標磁碟或媒體本身是唯讀狀態。
- 查不到 `winerror`（例如非 Windows 特有的 `PermissionError`）：退回一個
  沒有過度承諾特定原因、但一樣明確排除「系統管理員權限問題」的通用訊息。
- 非 `PermissionError` 的其他 `OSError`：直接顯示原始例外訊息，不強加
  分類。

`trigger_installation()` 主要複製迴圈與其他幾個複製點（`uninstall.exe`、
`installer_config.json`、`doc_icon`、`doc_icons`）都新增 `current_copy_target`
追蹤「目前正在寫入哪個目的地路徑」，複製失敗時才有辦法把正確的檔案路徑
餵給 Restart Manager 查詢；原本單一的 `except PermissionError:` 改成
`except OSError as e:`（`PermissionError` 是 `OSError` 的子類別，範圍更廣，
涵蓋所有複製/寫入時可能發生的作業系統層級錯誤），呼叫
`_describe_install_os_error()` 產生訊息；其餘非 `OSError` 的例外（例如
`RuntimeError`，見登錄表/檔案關聯/PATH 那幾個已經有專屬前綴訊息的寫入
步驟）維持原本 `except Exception as e:` 的處理，不受影響。

### 8.22 相依元件可以自動下載＋靜默安裝，不再只是提示手動下載

**動機（使用者實測回報）**：`dependencies` 欄位原本只做「登錄表存在與否」
的偵測，缺少時彈出 `#depModal` 列出名稱＋一個「前往下載」連結，只有一個
「仍要繼續安裝」按鈕——完全不阻擋、也不會幫使用者做任何事，使用者要自己
去官網下載、手動裝完、回來繼續拖曳安裝。使用者希望這段自動化。

**設計**：`DEPENDENCY_CHECKERS` 每個項目從 `(check_fn, 顯示名稱, 下載連結)`
擴充成 `(check_fn, 顯示名稱, 下載連結, 靜默安裝參數)`。`#depModal` 新增
「自動安裝」按鈕（原本的「仍要繼續安裝」保留當次要按鈕，維持不阻擋的
行為），按下去依序對每個缺少的元件呼叫新增的 `InstallerAPI.install_dependency(key)`：

1. 下載官方安裝檔到 `%TEMP%` 底下固定命名的暫存檔（分段讀寫＋依
   `Content-Length` 算進度）。
2. 用 `subprocess.run([暫存檔路徑] + 靜默參數, ...)` 執行（`/install
   /quiet /norestart`），**不管子程序的結束碼**。
3. 裝完後（不論子程序結束碼是什麼）重新呼叫這個元件自己的 `check_fn()`
   查登錄表，確認「現在到底裝好了沒」才是最終依據，回傳成功/失敗給前端。

**為什麼不能信任子程序的結束碼**：Microsoft 官方文件明講，Visual C++
Redistributable 如果偵測到機器上已經裝了更新版本，`/quiet` 模式下會
回傳非 0 的錯誤碼，但這其實不是真正的失敗；只看結束碼判斷會把「其實沒
問題」的情況誤判成失敗。重新查登錄表才是這個功能原本就在用的、真正可靠
的偵測依據（`_check_vcredist_x64()`/`_check_dotnet_desktop()`）。

**進度顯示沿用既有的 backend 推播模式，不新增前端輪詢**：
`trigger_installation()` 既有的 `_report_progress()`（見 §8.15/§8.21
附近程式碼）是安裝期間 backend 主動呼叫 `window.evaluate_js()` 推播進度
給前端，前端完全沒有 `setInterval` 輪詢 backend 的先例。`install_dependency()`
沿用同一套模式：新增的 `_report_dependency_progress()` 推播到前端新的
`window.updateDependencyInstallProgress`；前端單純 `await` 這一個 async
呼叫、拿到最終結果就切頁——比額外維護一個輪詢迴圈更簡單可靠。多個相依
元件缺少時，一次「自動安裝」按鈕依序處理全部，裝完（不論成功失敗）才
切回拖曳頁面（`setMainViewVisible(true)`），底部顯示一個短暫的小提示
（`#depToast`，列出成功/失敗的元件名稱），失敗的元件仍保留手動下載連結
當備援。

**兩個相依元件的下載連結來源**：

- `vcredist_x64`：`https://aka.ms/vc14/vc_redist.x64.exe`，這是
  Microsoft 官方文件（[Latest Supported VC++ Redist
  Downloads](https://learn.microsoft.com/en-us/cpp/windows/latest-supported-vc-redist)）
  明講的「Permalink for latest supported x64 version」，永遠指向最新版，
  不需要維護。
- `dotnet_desktop`：`https://aka.ms/dotnet/10.0/windowsdesktop-runtime-win-x64.exe`。
  **這個連結沒有版本無關的永久別名**——`aka.ms/dotnet/<major.minor>/...`
  這個格式一定要指定確切的頻道版本號，這裡先固定用「10.0」（2026 年寫
  這段文件時的最新 LTS，.NET 8/9 已於 2026-11-10 到期）。**已知限制**：
  .NET 10 支援到期（約 2028-11 前後）之後，這個版本號需要手動更新成
  下一個 LTS，否則舊連結雖然還能用，但裝到的會是過期的舊版本——這是
  刻意接受的維護負擔，不是遺漏，跟 vcredist 的永久別名性質不同。

**已知限制（安全性取捨）**：這裡只靠 HTTPS 憑證驗證＋官方網域字串本身
當作「這個下載來源可信任」的保證，沒有額外做 Authenticode 簽章驗證再
執行——跟 §9 現有「這個專案本身沒有數位簽章」的既有基調一致，不是這次
才引入的新風險等級，但這裡是自動下載＋自動執行一個外部可執行檔，風險
性質跟其他既有限制不完全一樣，值得使用者知情。

**已知限制（frozen exe 的 SSL 憑證）**：Windows 上 Python 的 `ssl` 模組
驗證 HTTPS 憑證時，不一定會自動採用系統憑證存放區；`.py` 直接執行時
開發機環境可能剛好有 `certifi` 之類的套件間接把憑證鏈補齊，但打包成
frozen exe 之後環境更精簡，實際下載有可能因為憑證驗證失敗
（`CERTIFICATE_VERIFY_FAILED`）而出錯。如果實測遇到這個問題，備案是
額外內嵌 `certifi` 套件，改用
`ssl.create_default_context(cafile=certifi.where())` 明確指定信任的
憑證清單。

### 8.23 相依元件清單不再寫死在原始碼裡（`custom_dependencies`）

**動機（競品比較後發現的落差）**：跟 Inno Setup/NSIS/WiX/InstallShield/
Advanced Installer 比較後發現，這些工具都能讓封裝者自訂任意「先決條件」，
我們原本的 `DEPENDENCY_CHECKERS`（`installer_core.py`）是模組層級寫死的
`dict`，只有 `vcredist_x64`/`dotnet_desktop` 兩個 key，封裝者完全沒辦法
加一個自己的相依元件（例如某個內部工具的執行環境）。

**設計**：新增泛用登錄表檢查函式 `_generic_registry_check(hive, path,
value_name=None, expected=None)`，`_check_vcredist_x64`/`_check_dotnet_desktop`
改成呼叫這個泛用版本（函式名稱維持不變，相容既有測試）。新增
`custom_dependencies` 設定欄位（只能透過 JSON，跟 `eula_texts`/`doc_icons`
同樣理由——巢狀結構塞進命令列不實際），每筆是 `{key, display_name,
download_url, silent_args, registry_check: {hive, path, value_name,
expected}}`。`InstallerAPI.load_config()` 讀入後，用
`_build_dependency_checkers()` 跟內建的兩個合併成**實例層級**的
`self.dependency_checkers`（不是動 module-level 的 `DEPENDENCY_CHECKERS`，
避免同一個 process 內如果曾經有多個 `InstallerAPI` 實例——例如測試——
彼此的自訂相依元件互相污染）。`get_dependency_warnings()`/
`install_dependency()` 改讀 `self.dependency_checkers`。`packaging_core.py`
的 `validate_and_build_pack_data()` 負責擋掉 key 撞名/重複/必填欄位缺漏。

`vcredist_x64`/`dotnet_desktop` 的顯示名稱/下載連結/靜默參數本體搬進新的
`dependency_defs.py`（`BUILT_IN_DEPENDENCIES`），`installer_core.py`（安裝端
偵測用）跟 `builder.py`（§8.24 的 `bundle_dependencies` 打包端下載內嵌用）
共用同一份，避免兩邊各自維護一份 URL 悄悄不同步。

### 8.24 相依元件可以打包時內嵌，不再只能安裝時線上下載（`bundle_dependencies`）

**動機**：§8.22 的自動安裝一律在安裝當下連網下載，如果目標機器沒有網路
（常見於企業內網、隔離環境）就完全裝不成。

**設計**：新增 `bundle_dependencies` 設定欄位（字串陣列，列出 `dependencies`
裡要內嵌的 key），`packaging_core.py` 驗證這些 key 必須同時也列在
`dependencies` 裡。打包當下（`builder.py` 的 `build_all()`），對每個要
內嵌的 key，用 `_download_file()`（跟 `installer_core.py` 的
`install_dependency()` 內部下載邏輯是同一套邏輯的另一個副本——刻意不強行
合併，一個要考慮打包時同步失敗即中止、一個要考慮安裝時推播進度給前端，
兩邊硬併會互相遷就對方不需要的參數）把安裝檔下載到工作目錄，命名成
`<key>.exe`，用 `--add-data={路徑};dependencies` 掛進 Setup.exe 的
`dependencies/` 子目錄（掛載路徑固定，`install_dependency()` 用
`get_resource_path(os.path.join("dependencies", f"{key}.exe"))` 查找）。
下載失敗直接讓整個 `pack` 流程失敗，不產出一份「號稱有內嵌、其實沒裝進去」
的安裝檔。

`install_dependency(key)` 執行時，先檢查 `key` 是否在 `self.bundle_dependencies`
裡且對應的內嵌檔案存在：有的話直接執行內嵌檔案（進度直接從 55% 起跳，
略過下載階段），沒有才 fallback 到原本的線上下載路徑；`finally` 清理暫存檔
時特別排除內嵌檔案（那是這次安裝檔自己的資源，不是我們下載到 `%TEMP%` 的
暫存檔，不能刪除）。

取捨：內嵌會讓安裝檔明顯變大（vcredist ~15-25MB、dotnet desktop runtime
~60MB+），預設（不列進 `bundle_dependencies`）仍是線上下載，內嵌是明確
選用（opt-in），封裝者自己權衡「安裝檔大小」vs「目標機器有沒有網路」。

### 8.25 免系統管理員權限（per-user）安裝模式（`no_admin_install`）

**動機**：這個工具產出的安裝檔原本一律 `--uac-admin` 編譯、一律裝到
Program Files，跟 Inno Setup 這類工具「同一支安裝檔可以選擇免 UAC 的
per-user 安裝」的能力比起來是明顯落差——單一使用者自己安裝、不需要讓
電腦上其他使用者共用的情境，沒有必要被強迫跳 UAC。

**設計**：新增 `no_admin_install` 布林設定欄位，開啟後：

- `builder.py`：`uninstall.exe`/`Setup.exe` **兩支都不帶** `--uac-admin`——
  整個 app（含解除安裝）提權設定要一致，不然單獨對 uninstall.exe 提權會
  很突兀（使用者裝的時候全程不用管理員權限，解除安裝卻突然跳 UAC）。
- `installer_core.py`：預設安裝根目錄改成既有的 `_local_appdata_root()`
  （`%LOCALAPPDATA%\Programs\<folder_name>`，本來就是給 `local_appdata_files`
  用的使用者層級目錄，這裡直接重用）而不是 Program Files；`_register_uninstall_entry()`/
  `check_existing_install()` 改寫入/讀取 `HKEY_CURRENT_USER`（每個使用者
  自己的解除安裝清單）而不是 `HKEY_LOCAL_MACHINE`；`_add_to_path_env()`
  改寫使用者層級的 `HKCU\Environment`（本來就不需要提權即可寫入）而不是
  `HKLM\...\Session Manager\Environment`；`_create_shortcut()` 改建在目前
  使用者自己的桌面/開始功能表（`%USERPROFILE%\Desktop`、`%APPDATA%\...\Start
  Menu`）而不是所有使用者共用的 Public Desktop/ProgramData。
- `install_manifest.json` 新增 `no_admin_install` 欄位，`uninstall.py`
  讀這個欄位決定：（1）`main()` 開頭是否要求 `is_admin()`（原本無條件要求，
  現在 `no_admin_install` 開啟時完全跳過這個檢查，且這個判斷提前到讀完
  manifest 之後、`is_admin()` 檢查之前，因為要先知道這支安裝裝的時候有沒有
  要求提權）；（2）`remove_registry_entry()`/`remove_from_path()`/
  `remove_shortcut()` 都新增 `no_admin_install` 參數，讀寫對應的使用者層級
  位置，維持跟安裝端一致。

**已知限制**：`no_admin_install` 是整個 app 的全域開關，不是逐檔案設定——
跟 `local_appdata_files`（只挑部分檔案改裝到使用者目錄，主程式仍在
Program Files）是兩個不同層級的功能，可以視情境擇一使用，但目前沒有
「主程式也要免提權，但額外還想要系統層級 PATH」這種混合模式。

### 8.26 安裝前置/後置自訂腳本（`pre_install_script` / `post_install_script`）

**動機**：這個工具原本完全沒有讓封裝者在安裝流程中插入自訂邏輯的方式——
Inno Setup/NSIS/WiX 都有對應的 custom action / script hook 機制，我們沒有
任何等效物。

**設計**：新增 `pre_install_script`/`post_install_script` 設定欄位（相對於
`app_dir` 的路徑，指向一支 `.bat`/`.exe`/`.ps1` 等）。打包時（`builder.py`）
比照 `doc_icon` 的做法：複製一份固定命名（`pre_install_script<原始副檔名>`/
`post_install_script<原始副檔名>`，保留副檔名是因為執行方式由副檔名本身的
關聯決定）到工作目錄，用 `--add-data={路徑};.` 掛進安裝檔根目錄。

`installer_core.py` 的 `trigger_installation()` 新增兩個執行點：

- **pre**：`selected_path` 建立之後、檔案複製迴圈開始之前。執行失敗
  （非 0 結束碼、逾時、找不到檔案以外的例外）視為安裝失敗，中止並回報
  錯誤——主程式可能依賴這個腳本先做的事（例如停用某個會鎖住待複製檔案
  的服務），腳本沒成功執行完，後面的複製流程不該假裝沒事繼續跑。
- **post**：登錄表/捷徑/檔案關聯/PATH 都寫完、`install_manifest.json`/
  `install_log.txt` 寫入之前。執行失敗只記錄警告、**不**讓整體安裝回報
  失敗——此時主程式已經是可用狀態，不該因為收尾腳本（例如額外的環境
  設定）失敗就整個作廢。

`_run_install_script()` 統一負責執行（`CREATE_NO_WINDOW`、逾時 120 秒、
找不到腳本檔案視為 no-op），兩個呼叫點只是「失敗時要不要中止安裝」這一點
處理方式不同，不是重複實作。

**已知限制**：腳本以這支安裝程式當下的權限層級執行（一般是系統管理員，
或 §8.25 `no_admin_install` 開啟時是一般使用者），跟主程式檔案複製本來就
有的能力等級一致，不是新增的風險類別——但這代表這個機制等同「安裝檔可以
執行任意程式碼」，封裝者引入外部/不受信任的腳本檔案要自行承擔風險，這個
工具不做腳本內容的安全性驗證。

### 8.27 數位簽章自動化（signtool 整合，`signing`）

**動機**：跟競品比較後確認的落差之一——但**這裡不解決「怎麼取得憑證」**
（要跟憑證機構購買或用公司行號申請），只解決「取得憑證之後，簽章這個
步驟要手動執行，還是打包流程自動幫你做」。

**設計**：新增 `signing` 設定欄位（只能透過 JSON，結構化）：
`{"cert_path": "...", "cert_password_env": "環境變數名稱", "timestamp_url":
"..."}`。**密碼不放在 JSON 明文，只存環境變數名稱**，打包當下從
`os.environ[cert_password_env]` 讀取，避免密碼被寫進設定檔或版本控制。
`packaging_core.py` 的 `validate_and_build_pack_data()` 在打包**當下**就
確認 `cert_path` 檔案存在、`cert_password_env` 對應的環境變數確實有值
（不等到 `signtool` 真的執行時才發現密碼沒設定）。

`builder.py` 的 `_sign_file()`：`Setup.exe`、`uninstall.exe` 兩支都
編譯完成後各自呼叫一次 `signtool sign /f <cert_path> /p <password> /fd
sha256 /tr <timestamp_url> /td sha256 <檔案路徑>`。MSIX 引擎的 `.msix` 也
由同一個函式簽——`signtool` 對兩者的用法完全相同。函式名稱不用
`_sign_executable`，因為那個名字會讓人以為 `.msix` 需要另一條路徑，進而
寫出第二份重複的實作。找不到 `signtool` 或簽章
失敗，直接讓整個 `pack` 流程失敗——既然使用者特地設定了 `signing`，簽不成
不該悄悄放行一份沒簽到的檔案。沒有設定 `signing` 欄位：行為完全不變，直接
跳過，不強迫沒有憑證的使用者處理這個欄位。

**`signtool` 的檢索改由 `sdk_tools.py` 負責（2026-08-31）。** 原本是
`shutil.which("signtool")`，只檢索 PATH，而 Windows SDK 安裝後不會把這些
工具加進 PATH——對已正確安裝 SDK 的使用者，該實作會回報找不到，並要求他們
去做一件不會成功的事（訊息原文要求「確認它在 PATH 裡」）。現在四個來源
依「使用者表達意圖的明確程度」排序：`sdk_tools_dir` 設定 → `fetch-sdk-tools`
下載的快取 → PATH → 系統上的 Windows SDK，找不到時的錯誤訊息附一行可直接
複製執行的取得指令。`makeappx`／`makepri`（MSIX 模式用）與 `signtool` 共用
同一套，理由與五項決定見 `docs/adr/0008`，詞彙見 `CONTEXT.md`「SDK 工具」
一節。`_sign_file()` 的 `find_tool`／`run` 是測試接縫，比照
`file_assoc.py` 的 registry seam。

`timestamp_url`（時間戳記伺服器）的作用：讓簽章在憑證本身過期之後依然
有效（Windows 驗證時看的是「簽章當下憑證有效」，不是「現在憑證有效」），
沒填的話預設用 DigiCert 的公開時間戳記伺服器。

### 8.28 解除安裝助手改用 pywebview 視窗，套用跟 Setup.exe 一致的 macOS 風格彈窗

**動機（`/apple-design` 檢視發現的落差）**：`Setup_XXX.exe` 的
`ui/index.html` 已經有一套完整的 `.nice-modal-*` 自訂彈窗系統（圓角、
`backdrop-filter` 模糊、HIG 色票），但 `uninstall.py` 原本是純 console
程式（`builder.py` 沒有給它加 `--noconsole`），互動三個關鍵時刻（確認
刪除、偵測到鎖定檔案的程式、主程式執行中）全部是原生 `MessageBoxW`，
雙擊執行還會跳出一個黑底命令提示字元視窗印步驟訊息——這是「兩套系統拼
在一起」最明顯的來源，跟這個工具「還原 macOS DMG 拖曳安裝畫面」的產品
定位不符。

**設計**：比照 `installer_core.py` 的 `InstallerAPI` 模式（pywebview 視窗 +
JS API class + 前端驅動流程），新增：

- `ui/uninstall.html`：跟 `ui/index.html` 共用同一套設計語彙（字型堆疊、
  色票、`.nice-modal-*`、藥丸按鈕、frameless + 自訂拖曳 + 左上角 X 關閉），
  畫面狀態用 class 切換：`confirmView`（確認刪除）→（視情況）
  `processRunningView`（主程式執行中）或 `lockingProcessesView`（偵測到
  鎖定檔案的程式，是/否）→ `progressView`（複用
  `.install-progress-*` 樣式）→ `doneView`/`errorView`。
- `uninstall.py` 新增 `UninstallerAPI` class：`get_app_name()`/
  `get_ui_language()`、`check_main_exe_running()`、
  `get_locking_process_names()`（偵測結果快取在 `self._locking_processes`，
  供接下來的 `run_uninstall()` 用，避免使用者看過名單、按了是/否之後，
  重新掃一次可能得到不一致的結果）、`run_uninstall(kill_locking_processes)`
  （實際執行登錄表/捷徑/檔案關聯/PATH/清單式刪除，進度透過
  `window.evaluate_js` 推播，寫法照抄 `_report_progress()`）、
  `finish_and_exit()`（寫 log + 排自我刪除 + 關閉視窗）、`cancel()`。
- 原本 `main()` 一路線性執行到底、靠 `MessageBoxW`/`print()` 中斷的邏輯，
  拆成幾個可重用的函式：`_load_uninstall_context()`（讀 manifest 算基本
  資訊，互動/靜默共用）、`_compute_locking_processes()`（取代原本的
  `_confirm_kill_locking_processes()`——現在只負責偵測，不負責問，問的
  動作搬進 HTML/JS）、`_perform_uninstall_steps()`（實際刪除步驟，互動
  跟靜默共用同一份，只有 `kill_locking_processes` 從哪裡決定、要不要
  推播進度這兩點不同）、`_write_uninstall_log()`/`_schedule_self_delete()`
  （log 寫入、自我刪除排程，同樣互動/靜默共用）。
- 靜默/更新覆蓋路徑（`--silent`）**行為完全不變**：不開視窗、不問、跑完
  寫 log、排自我刪除，`run_silent_uninstall()` 就是原本那段邏輯搬過去，
  唯一差異是現在會回傳明確的 exit code（0/1）——`installer_core.py` 的
  `run_upgrade_uninstall()` 呼叫這支 exe 時本來就不檢查結束碼，這個改動
  是安全的附帶改善，不影響既有整合。
- `is_admin()` 檢查失敗時的訊息，維持用原生 `MessageBoxW`（跟
  `installer_core.py` 單一實例鎖對話框同樣的例外——這個時間點 webview
  視窗還沒建立，沒有 HTML 畫面可以顯示）。

**`builder.py` 改動**：`uninstall_cmd` 加上 `--noconsole`（移除黑底命令
提示字元視窗）、`--add-data=ui;ui`（掛載整個 `ui/` 資料夾，讓
`uninstall.html` 跟著 `index.html` 一起進去）、跟主安裝檔一樣的
`--exclude-module=PyQt5/PyQt6/PySide2/PySide6/gi`（因為 `uninstall.py`
現在也 `import webview` 了）。`no_admin_install` 為 True 時仍然不加
`--uac-admin`，沿用既有邏輯不受影響。

**`packaging_core.py` 改動**：`ensure_workspace_files()` 的 ui 資料夾覆蓋
邏輯，`uninstall.html` 跟 `index.html` 一樣是「內部實作、必須無條件
覆蓋」，判斷式改成 `if name in ("index.html", "uninstall.html")`。

### 8.29 主安裝畫面的視窗尺寸／版面規格（供其他畫面比照，不要另外發明標準）

這節純粹是把 `installer_core.py`/`ui/index.html` 既有的視窗尺寸與版面
數字**記錄下來**（先前沒有寫進規格文件），起因是解除安裝助手的
`confirmView`（見 §8.28）第一版另外發明了一套縮小尺寸（480x420 視窗、
64px 圖示），跟主安裝畫面擠在同一個產品裡看起來像兩套不同標準的介面。
之後任何畫面要做「圖示＋箭頭＋目的地」這種 workspace 版面，直接套用這裡
記錄的數字，不要重新設計一套。

- **視窗本身**：`installer_core.py` 的 `webview.create_window(width=600,
  height=420, resizable=False, frameless=True, easy_drag=False)`。
- **`.workspace`**：三欄（來源圖示／箭頭／目的地圖示）橫向排列置中的容器。
- **`.icon-box`**：單一圖示欄，`width: 160px`，內容（圖示＋文字標籤）
  垂直置中。
- **`.icon-wrapper`**：實際圖示大小 `90x90px`，`cursor: grab`，按住時
  `transform: scale(0.95)`。
- **`.arrow-box`** / **`.arrow-svg`**：中間的箭頭，`.arrow-box` 高度
  `90px`（跟 `.icon-wrapper` 對齊），箭頭本身 `.arrow-svg` 是 `28x28px`。

`ui/uninstall.html` 的 `confirmView`（拖曳 App 圖示到垃圾桶＝解除安裝，
見 §8.28）直接沿用以上 class 名稱與大部分數字（`.workspace`/`.icon-box`/
`.arrow-box`/`.arrow-svg`），`uninstall.py` 建立視窗的尺寸也同步改成
`600x420`。**兩個圖示的實際大小是這裡唯一刻意跟主安裝畫面數字不同的地方**：
垃圾桶圖案本身線條較粗、留白較少，跟 App 圖示（`.icon-wrapper`）做一樣的
`90x90px` 會顯得垃圾桶偏小，但放大到 `120x120px` 又太大；來回微調後定案
在 App 圖示 `100x100px`、垃圾桶（`.trash-can`，桶身/蓋子兩張圖疊在一起）
`110x110px`，兩邊視覺份量才接近平衡。這兩個數字是針對「這個垃圾桶素材」
實測調出來的，換一張線條粗細不同的垃圾桶圖案時要重新試，不是固定比例。

**另一條既有慣例（同樣先前沒有寫進規格文件，補記在這裡）：圖示區塊要當成
一組獨立置中，任何搭配的文字/勾選項要當成另一組，掛在圖示區塊下方，兩者
不能被當成同一包內容一起參與置中計算。** 原因：如果文字/勾選項跟圖示區塊
放在同一個會被整包置中的容器裡，文字的高度會把圖示的視覺中心往上推，圖示
因此不是真正置中在視窗裡，而是偏在「圖示+文字整包」的上半部。`index.html`
當初就是因為這個理由，把「建立桌面捷徑」勾選項獨立成 `.bottom-bar`
（`position: fixed; bottom: 20px`），不參與 `.main-view` 的置中計算（見
`ui/index.html` 檔案開頭的修正紀錄）。`ui/uninstall.html` 的 `confirmView`
比照這個慣例：`.workspace` 用 `position: absolute` 獨立定位，文字
（`.confirm-text`，包住 `.nice-title`/`.nice-message`）是另一個獨立定位
的區塊，掛在 `.workspace` 下方固定距離，不影響 `.workspace` 本身的定位
結果。

**真實抓到的問題（`/apple-design` 橫向比對安裝檔實測發現）：圖示區塊真的
精確置中在視窗正中央（`top: 50%`）反而看起來不平衡。** 圖示視覺上比較
「重」，下面又掛著同樣有重量的文字（`confirmView` 是標題+訊息兩行，比
`index.html` 單行標籤更重），兩者相加的視覺重心自然落在偏下的位置，視窗
上半段變成一大片空白、下半段被塞滿，跟 `index.html` 檔頭修正紀錄提到的
「圖示應該幾乎置中、只微幅偏上」是同一個問題的翻版——只是這裡文字比較重，
偏移幅度也要比 `index.html` 的 `margin-top: 8px`（約 2% 視窗高度）更明顯。
最後把 `.workspace` 的垂直錨點從 `top: 50%` 改成 `top: 44%`（`.confirm-text`
對應改成 `top: calc(44% + 68px)`），視窗上下留白的視覺份量才比較對等。
**這個 44% 是針對「圖示+兩行文字」這個組合實測調出來的數字，不是放諸四海
皆準的黃金比例**——之後如果有別的畫面也要做「圖示置中＋掛文字」的版面，
文字份量（幾行、多大）不同的話，這個垂直錨點也要跟著重新試，不能直接照抄
44% 這個數字，但「圖示不要真的精確置中、要往上偏移一點」這個方向性原則
是共通的。

### 8.31 安裝位置三選一，取代原本「免系統管理員權限」單一核取方塊

原本打包時只有一個「免系統管理員權限（`no_admin_install`）」核取方塊，勾選就整個裝到使用者層級（`%LOCALAPPDATA%\Programs`），不勾就固定裝到 `Program Files`。改成 `config.html` 提供三選一：「Program Files（需要系統管理員權限）」／「使用者目錄（`%LOCALAPPDATA%\Programs`，免系統管理員權限）」／「自訂路徑」，並保留一個獨立的「這個路徑需要系統管理員權限」覆寫勾選（給使用者選了自訂路徑、但那個路徑本身在系統層級的情境用）。三選一 JS 送出時換算回既有的 `no_admin_install`（布林）+ 新增的 `custom_install_dir`（字串，選了自訂路徑才有值，逐路徑寫入 `installer_config.json`，`installer_core.py`/`builder.py` 原封不動使用，不做展開），對底層邏輯完全透明。

同一輪順便修掉一個真實 bug：`builder_cli.py` 的 `--no-admin-install` 這個命令列旗標過去因為 `_SCALAR_OVERRIDE_FIELDS`/`argparse` 沒有正確接上，設了也不會反映到最終的 `installer_config.json`，一路都是走 `False` 的預設值——CLI 使用者不管有沒有帶這個旗標，打包出來的安裝檔一律裝到 `Program Files`。

`config.html` 的「個別檔案改裝到其他位置」（`local_appdata_files`）欄位同一輪也從純文字、逗號分隔的手動輸入，改成勾選、可摺疊的巢狀檔案分支圖（`renderLocalAppdataFileTree()`）：遇到資料夾會遞迴渲染成可摺疊節點，勾選資料夾會連動勾選/取消底下所有檔案（`collectDescendantFiles()`），已展開的節點狀態靠 `expandedTreeFolders` 這個 Set 在重新渲染之間保留，不會因為勾了一個子項目就把整棵樹收合回去。`builder_cli.py` 新增 `list-files` 子命令（`packaging_core.list_app_dir_files(app_dir)`，純函式、`os.walk` + 相對路徑排序），讓 CLI 使用者可以在下 `pack` 之前，先查一次 `app_dir` 底下實際有哪些檔案可以選，跟 GUI 的檔案樹背後是同一份掃描邏輯。

### 8.32 安裝/解除安裝遇到鎖定的程式，改成互動式關閉並重試（含保底「略過偵測」選項）

`trigger_installation()` 複製檔案途中如果遇到 sharing/lock violation，且 Restart Manager 能查到是誰鎖住的，會回傳結構化的 `file_locked` 狀態（`processes`/`path`），讓 `index.html` 跳出「關閉此程式／取消」的互動彈窗，使用者按下「關閉此程式」呼叫 `close_locking_processes(processes, path)` 之後直接重試安裝，不用逼使用者自己去工作管理員手動關閉——查不到是誰鎖住的話（沒東西可以讓使用者按）維持原本的 `error` 狀態。解除安裝端（`uninstall.py`/`ui/uninstall.html`）比照加上「關閉應用程式並繼續解除安裝」的對等流程。

兩端都額外加了一個保底選項：「略過偵測，強制繼續」，因應偵測本身卡死的邊緣情況（實測案例：某支程式在系統匣選單 callback 裡崩潰，Windows 工作管理員已經看不到它，但行程表裡的殭屍紀錄還在，`tasklist`/`taskkill` 都對它沒有效果，重開機前會一直被判定「還在執行」）——這種情況讓使用者被迫在「關閉程式並重試」的迴圈裡打轉沒有意義，需要一個明確的出口。`trigger_installation(create_desktop_shortcut, skip_process_check=False)` 多了 `skip_process_check` 參數，`True` 時直接跳過主程式執行中偵測。

同一輪也修掉 `close_running_main_exe()` 的一個真實 bug：原本只要 `subprocess.run()` 呼叫本身沒有拋例外就一律回傳成功，沒有檢查 `taskkill` 真正的 `returncode`——找不到目標行程時 `taskkill` 會用非 0 的 `returncode` 表示失敗，但呼叫端從沒檢查過，改成如實反映有沒有真的成功。

**修正紀錄（真實抓到的 bug）**：原本如果 `close_locking_processes()` 關閉的程式裡剛好有 `explorer.exe`，會額外呼叫 `subprocess.Popen(["explorer.exe"])` 主動重啟它。實測發現：`explorer.exe` 沒有引數執行時，只有「目前完全沒有任何 shell 實例在跑」才會直接成為桌面/工作列（不開視窗）；如果呼叫當下殼層其實已經自己復原了，執行 `explorer.exe` 會被解讀成「開一個新的瀏覽視窗」——這個明確重啟的呼叫本身就是多餘的，還會多跳出一個使用者沒有要求的視窗，已拿掉（見 §8.34 對這整個題目的完整修正）。

**修正紀錄（真實抓到的 bug）**：「偵測並結束鎖定檔案的程式」（`restart_explorer_on_update`）原本是打包時可以勾選/關閉的選填選項；改成永遠內建開啟，不再是設定項——最終要不要真的結束偵測到的進程，互動式安裝/解除安裝本來就一定會先跳確認畫面問過使用者，讓開發者關掉這個偵測反而只是徒增要理解的設定項，沒有實質防護效果。`config.html` 打包表單移除對應的核取方塊/說明文字/i18n。

### 8.33 跨 `no_admin_install` 模式的升級偵測與跨 UAC 呼叫

真實抓到的 bug：`check_existing_install()` 原本只查「這次打包設定」算出來的單一 hive，如果舊版本是用不同的 `no_admin_install` 設定裝的（例如舊版本用預設設定裝在 `Program Files`、登錄表寫在 `HKLM`，這次改用「使用者目錄」重新打包），完全查不到舊版本的登錄表紀錄，誤判成「沒裝過」，跳過「是否要更新」的提示，新舊兩份安裝各自獨立存在，沒人清掉舊的。修正：兩邊 hive 都查（先查這次設定對應的 hive，查不到再查另一邊），回傳值多一個 `"hive"` 欄位（`"HKLM"`/`"HKCU"`）。

延伸出另一個問題：`run_upgrade_uninstall()` 呼叫舊版 `uninstall.exe` 原本一律用 `subprocess.run()`（底層是 `CreateProcess`）。Windows 的 manifest 自動提權（跳 UAC 詢問）只有透過 `ShellExecute` 這條路徑才會被認得，`CreateProcess` 不會觸發提權，會直接用目前（未提權）行程的權杖把子行程跑起來——如果舊版本需要管理員權限（`hive == "HKLM"`）但這次新安裝檔是免權限執行，舊版 `uninstall.exe` 會在寫入 `Program Files`／刪除 `HKLM` 機碼時默默失敗，卻不拋出任何例外，看起來像是清乾淨了、實際上沒有。修正：新增 `_is_current_process_elevated()`（`IsUserAnAdmin()`）判斷目前行程是否已提權，`hive == "HKLM"` 且未提權時改用 `_run_uninstall_exe_elevated()`（`ShellExecuteExW` + `"runas"` 動詞 + `WaitForSingleObject` 等待完成）跨 UAC 呼叫，其餘情況維持原本的 `subprocess.run()`。

**已知限制**：這條路徑的真實 UAC 互動沒辦法在開發環境模擬，只能用 mock 驗證 `ShellExecuteExW`/`WaitForSingleObject`/`CloseHandle` 有沒有被正確呼叫、參數對不對；使用者按下同意/取消 UAC 提示之後的真實行為，需要在實機上驗證。

### 8.34 檔案鎖定釋放改成分層策略：先關瀏覽視窗，不夠才強制終止殼層（`explorer_lock_release.py`）

§8.32 拿掉的「結束 `explorer.exe` 後主動重啟它」這個步驟，後續使用者實測回報：按下「關閉此程式」後，安裝進度會卡在複製到一半的某個檔案，再次跳出「檔案使用中」——這其實不是砍不掉，而是「砍了但幾乎瞬間又自動復活」：Windows 的 `AutoRestartShell`（`HKCU\Software\Microsoft\Windows NT\CurrentVersion\Winlogon`）機制預設會在 `explorer.exe` 結束時自動重啟它，如果它剛好開著目標資料夾，會在檔案操作完成前就搶著重新鎖住同一個檔案。

新增 `explorer_lock_release.py`，把釋放邏輯拆成兩層：

1. **`close_windows_browsing_path(target_path)`**：先用 `Shell.Application` COM 物件列舉目前開啟的檔案總管視窗，只關閉正在瀏覽 `target_path`（或其子路徑）的那幾個視窗（呼叫 `.Quit()`），完全不動 `explorer.exe` 這個殼層行程本身——工作管理員裡「應用程式」跟「Windows 處理程序」兩個 `explorer.exe` 項目行為不同就是這個道理：前者是單一視窗，關掉不影響桌面/工作列；後者才是整個殼層行程。依賴 pywin32，跟 `_create_shortcut()` 一樣是選用依賴，沒裝就 best-effort 略過。
2. **`release_locking_processes()`**：關窗之後如果 `explorer.exe` 仍然鎖著檔案（有給 `find_locking_processes` 的話會重新查一次確認），才進到「強制關閉殼層」這條路：把 `AutoRestartShell` 暫時設成 `"0"`（保證它不會自動復活）、終止 `explorer.exe`，回傳一個狀態物件；呼叫端（`trigger_installation()`/`_perform_uninstall_steps()`）在檔案操作完成後（不管成功或失敗，都用 `try/finally`）呼叫 `restore_after_lock_release()` 手動重啟 `explorer.exe`、把 `AutoRestartShell` 寫回原值——這個值只有 `explorer.exe` 結束的那個瞬間才會被 Windows 讀取，寫回去本身不會觸發任何動作，順序上一定要「手動重啟」先做。

**修正紀錄（真實抓到的 bug，實測重現）**：終止行程原本沿用 `taskkill.exe`，對一般程式沒問題，但對 `explorer.exe` 這類跑在使用者互動 session 的行程，`taskkill.exe` 即使呼叫端本身已經是系統管理員權限執行，仍會回報 `returncode=1`、`ERROR: 無法終止 PID xxxx 的處理程序。原因: 存取被拒。`——原因是 `taskkill.exe` 預設不會啟用行程權杖裡的 `SeDebugPrivilege`（admin token 雖然帶著這個權限，但 Windows 預設是停用狀態，要自己呼叫 `AdjustTokenPrivileges` 才會真的生效），這正是工作管理員（自己會啟用這個權限）能砍得掉、外部呼叫 `taskkill.exe` 卻不行的真正差異。已修正：改成直接呼叫 Windows API——`OpenProcessToken`/`LookupPrivilegeValueW`/`AdjustTokenPrivileges` 啟用 `SeDebugPrivilege`，再 `OpenProcess`+`TerminateProcess`，跟工作管理員做的事一致。

**修正紀錄（真實抓到的 bug）**：改成直接呼叫 ctypes 之後，第一輪測試 `OpenProcessToken` 仍然無條件失敗——根本原因是這些 Windows API 呼叫完全沒宣告 `restype`/`argtypes`，ctypes 在沒有宣告的情況下預設把回傳值/參數當成 32-bit 的 `c_int` 處理，在 64-bit Windows 上，`GetCurrentProcess()` 這類回傳 `HANDLE`（指標大小）的函式，回傳值可能被截斷/錯誤解讀，導致後續拿著這個「壞掉」的參數呼叫 `OpenProcessToken()` 直接被拒絕（不會拋 Python 例外，只是靜靜回傳失敗）。已修正：明確宣告這幾個函式的 `restype`/`argtypes`（用 `ctypes.wintypes.HANDLE` 等對應的指標寬度型別），讓 ctypes 正確處理。

**已知限制（實測確認，不是這支安裝程式能修的問題）**：即使上述兩個修正都到位，`OpenProcess` 成功拿到帶有 `PROCESS_TERMINATE` 權限的 handle 之後，`TerminateProcess` 仍然可能回報 `ERROR_ACCESS_DENIED`（錯誤碼 5）——實測案例是第三方安全軟體（火絨的「關鍵進程保護」→「資源管理器」→自動阻止）在核心層攔截了針對 `explorer.exe` 的終止請求，這種攔截發生在 handle 已經合法建立之後，`OpenProcess` 不會失敗，只有 `TerminateProcess` 本身被否決。這是防毒/端點防護軟體的正常合理行為（許多此類軟體會把終止系統關鍵行程的動作特別列管，因為這是勒索軟體/惡意程式的常見手法），**這支安裝程式不會、也不應該嘗試繞過**——`_describe_install_os_error()` 在 sharing/lock violation 的訊息裡補上一句提示，告知使用者這種持續卡住的情況可能要去檢查防毒/安全軟體的相關防護設定。新增 `%TEMP%\mswi_explorer_lock_debug.log`（`installer_core.py._log_explorer_lock_release()`），把 `explorer_lock_release.py` 各步驟（關窗結果、pid 解析出的真正執行檔名稱、`AutoRestartShell` 讀寫、`TerminateProcess` 的 `GetLastError()` 錯誤碼與訊息）落地成可事後翻閱的除錯紀錄，這一整輪追查（從「看起來砍不掉」到「其實是防毒軟體攔截」）都是靠這份紀錄逐層排除掉別的可能性。

### 8.35 打包出來的 exe 帶上 Win32 VERSIONINFO 資源（`version_info.py`）

使用者回報：在檔案總管對打包出來的 exe（不論是這個工具自己的 GUI/CLI，
還是它幫使用者製作的 Setup.exe/uninstall.exe）按右鍵「內容 → 詳細資料」，
FileDescription/ProductName/FileVersion/CompanyName/LegalCopyright 這些
欄位全部是空白——根本原因是 PyInstaller 只有在明確給它一個
`--version-file` 參數時才會把 Win32 VERSIONINFO 資源嵌進 exe，這個專案
從一開始就沒有生成/傳遞過這個檔案，即使「應用程式版本號」「發行者」這些
欄位早就存在於 GUI 表單裡，也從未真正流進被打包 exe 的資源區塊。

新增 `version_info.py`，一個純函式、無 side effect 的深模組：

- `render_version_file(*, product_name, file_version, file_description, company_name="", legal_copyright="", product_version=None, ...)`：組出 PyInstaller `--version-file` 要求的文字格式（回傳字串，不寫檔）。`file_version`/`product_version` 接受 `"0.12.0"` 這種字串，內部 `_parse_version_tuple()` 解析成 4 個整數的 tuple（不足 4 段補 0，超過 4 段或有非數字段落直接拋 `ValueError`，讓呼叫端在建置當下就發現版本字串寫錯，而不是生出一份 PyInstaller 唸不懂的檔案）。`product_version` 省略時預設等於 `file_version`。
- `write_version_file(path, **fields)`：`render_version_file()` 的結果寫入指定路徑，供 `build_config_tool.py`/`builder.py` 產生暫存檔餵給 PyInstaller。

`language`/`codepage` 固定用英文（`0x0409`/`0x04B0`）——這只是 Windows
用來決定「同一份資源有多語系版本時要挑哪一份」的代碼，這個工具只會生成
一份，不影響 Explorer 顯示的實際文字內容（那些文字就是 `StringStruct`
填的字串本身，本來就可以是中文）。這個模組只在建置這個工具本身跟建置
使用者安裝檔這兩個開發機流程用到，產生的 version-file 只是餵給
PyInstaller 讀的暫存輸入檔，不會被打包進最終 exe、也不會在使用者電腦上
執行，所以不用列進 `packaging_core.py` 的 `SHARED_DEEP_MODULES`。

**兩處整合點：**

1. `build_config_tool.py`（打包這個工具自己的 GUI/CLI exe）：`build_one_exe()`
   新增 `version`/`publisher`/`file_description` 參數，有給 `version` 才會
   生成 `--version-file`（互動模式的 `BuilderGUI` 目前還沒收集這幾個欄位，
   維持原本不帶這個旗標的行為，不強迫使用者一定要填）；`ProductName`
   固定是 `mac-style-windows-installer`，`FileDescription` 依 GUI/CLI
   兩顆分別是 `"... GUI"`/`"... CLI"`。新增 `--publisher` CLI 參數（原本
   完全沒有這個欄位），`/released` skill 步驟 5 已同步更新要帶這個參數。
2. `builder.py`（打包使用者的 app 成 Setup.exe）：`build_all()` 在編譯
   `uninstall.exe` 跟編譯安裝檔本體這兩處 PyInstaller 呼叫之前，各自生成
   一份 version-file——不新增 GUI 欄位，`ProductName` 直接沿用既有的
   「應用程式名稱」（`app_name`），`LegalCopyright` 由「建置當下年份 +
   發行者」自動組成 `Copyright © <年份> <發行者>`。兩顆輸出 exe 只有
   `FileDescription` 不同（`app_name` 本身 vs. `f"Uninstall {app_name}"`），
   方便使用者在檔案總管裡分辨。版本字串格式錯誤時 `write_version_file()`
   會直接拋例外中止整個 pack 流程，不會靜默生成錯誤的資源或跳過
   `--version-file`。

**已知限制**：`LegalCopyright` 是自動組出來的固定格式，不提供客製化欄位——
如果之後有「想要跟預設格式不同的版權聲明」這個需求，再考慮要不要在 GUI
表單加欄位，這輪先不做（YAGNI）。

### 8.36 安裝密碼保護（`install_password_env` / 配置精靈的直接輸入）

**動機**：內部工具、還沒公開的版本這類安裝檔，常常只想給特定的人裝。
安裝檔本身是一顆可以隨手轉寄的 exe，沒有任何機制擋住「被傳到不該傳的
地方、然後被裝起來」。

**定位（會影響下面好幾個子決策，不要事後模糊掉）**：這是**存取控制**，
防止安裝檔被誤傳／亂用，**不是**防範有心人暴力破解的資安機制。所以密碼
錯誤不限制重試次數（擋暴力猜測是 PBKDF2 高迭代次數的責任，不是 UI 層
重試次數限制的責任），配置精靈的密碼欄位也提供「顯示密碼」切換——這個
情境下「打錯了沒發現」的風險遠高於「被旁邊的人看到」。

**加密範圍**：只加密內嵌的應用程式檔案本體（原本 `--add-data={app_dir};
app_contents` 那一塊），不加密整個安裝程式。EULA、拖曳互動、相依元件
偵測這些安裝流程本身的邏輯照常執行。演算法是 AES-256-GCM + PBKDF2
金鑰衍生，實作收在 `install_encryption.py`，用 `cryptography` 套件——不用
ctypes 直接刻 BCrypt，因為加密邏輯寫錯是資安問題，不該冒手刻 ctypes
介面出錯的風險。

**指定密碼的兩種填法，只有一種能寫進設定檔**（見
[`docs/adr/0004`](adr/0004-inline-install-password-is-gui-only.md)）：

| 填法 | 配置精靈 | 設定檔（CLI） |
|---|---|---|
| 直接輸入密碼 | 支援，且為預設 | 明白報錯 |
| 填環境變數名稱（`install_password_env`） | 支援 | 支援 |

不對等是決定，不是遺漏。`packaging_core.validate_and_build_pack_data()`
收的那包 `data`，欄位集合就是設定檔的格式，而 GUI 跟 CLI 共用同一個驗證
函式——讓「直接輸入密碼」變成 `data` 的一個一般欄位，等於同時讓設定檔也
能寫明文密碼，而設定檔會被存進專案、傳給同事、上傳到版本控制，這正是繞
環境變數一圈要避開的事。設定檔裡出現 `install_password` 這個 key（不論
值是什麼、甚至留空）一律回報欄位驗證失敗，不默默忽略。

直接輸入的密碼因此走一條獨立的參數路徑
（`ConfigAPI.start_pack(data, install_password)` →
`builder.build_all(install_password=...)`），不進 `data`、不進 `pack_data`、
不進任何檔案。`validate_and_build_pack_data()` 只收到一個布林值
（`has_inline_password`），知道「這次有沒有用直接輸入」就足以做完所有
驗證，這個純函式維持「只處理設定值」的性質。

**打包時**：`builder.build_all()` 把兩個來源解析成單一的密碼值，`app_dir`
整包加密成 `app_contents.enc` 再 `--add-data` 內嵌，**不再把明文的來源
資料夾塞進去**（不然保護形同虛設）。設定檔只寫 `password_protected` 這個
布林值（見 §5.1）。

**安裝時**：密碼輸入畫面是一道前置關卡，比照 EULA 同意頁的模式，出現在
EULA **之前**。通過後解密整份加密檔到暫存資料夾，之後完全沿用
`_trigger_installation_impl_inner()` 既有的複製迴圈／完整性驗證／回滾
邏輯，只是複製來源從 `get_resource_path("app_contents")` 換成解密後的
暫存資料夾——那段邏輯已經踩過好幾輪真實 bug 修正，不去動它。

**靜默安裝**：比照 Inno Setup 慣例，新增 `/PASSWORD=密碼` 命令列旗標。
沒帶密碼或密碼錯誤時不跳任何視窗、不卡住等輸入，直接中止並回傳非 0
exit code，原因寫進既有的靜默安裝紀錄檔。

**前置檢查**：`cryptography` 的 import 在 `install_encryption.py` 的函式
內部（那個模組會被兩個 entry point 匯入，其中一個不一定需要加密功能），
缺少時不會在匯入階段就發現。而 `build_all()` 的順序是「清空 `dist/`／
`build/` → 編譯 `uninstall.exe`（數十秒）→ 加密」，所以改成在
`validate_and_build_pack_data()` 內檢查，只有這次真的要用密碼保護時才視為
缺少——跟 §8.35 之後把版本號格式驗證前移是同一個原則：純函式的職責就是在
任何檔案系統副作用發生之前攔截設定錯誤。

**已知限制**：
- 工具無法驗證使用者輸入的密碼是不是打錯了（沒有可以比對的來源）。打錯
  的後果是產出一顆沒有人打得開的安裝檔，而且通常要到發布之後才會發現。
  緩解措施只有輸入框旁邊的「顯示密碼」切換。不做「再輸入一次」的二次
  確認欄位：兩次都貼上同一個打錯的內容並不罕見，防護效果有限，卻要多一個
  欄位與一條驗證規則。
- 「直接輸入」這條路無法寫進設定檔，也就無法納入可重複執行的自動化流程
  （CI／批次打包）。需要自動化的使用者只能用環境變數那條路——那正是環境
  變數那條路存在的情境。
- 直接輸入的密碼在打包期間以字串形式存在於工具行程的記憶體中，沒有做任何
  抹除。這與本功能的定位一致：能讀取這個行程記憶體的人，本來就能讀到更多
  東西。

### 8.37 MSIX 引擎的綁定套件在打包階段就檢查（`requirements.txt`）

**背景（2026-09-03 於 Windows 10 1809 虛擬機重現）**：以 MSIX 引擎打包出的
`Setup.exe` 在目標機器上靜默安裝失敗，安裝紀錄寫的是「無法使用 Windows 的
套件部署介面：No module named 'winrt'」。當時的環境條件全部正確（簽章憑證
已匯入、側載已允許），失敗純粹來自安裝檔內部缺少該綁定套件。

**成因**：`msix_deploy.py` 對 `winrt` 的匯入位於函式內部（讓傳統引擎的安裝檔
不必綁上這個相依），而該套件根本沒有安裝在打包機器上，PyInstaller 因此沒有
東西可以收集。整條打包流程沒有任何一處檢查這件事，工具照樣回報編譯成功。
版本庫當時也沒有任何相依宣告檔，這五個套件只出現在
`.github/workflows/test-packaging-options.yml` 的安裝步驟裡，本機開發者沒有
管道會知道要裝。CI 涵蓋不到這個缺陷，因為 CI 每次都明確安裝那五個套件——
CI 綠燈不代表本機編出來的安裝檔可用。

**處置**：

1. `check_build_environment()` 的探針多問一項
   `import winrt.windows.management.deployment`（問的是 `msix_deploy.py` 實際
   會匯入的那一支模組，不是 `winrt` 這個命名空間本身：`winrt-runtime` 單獨
   裝得起來，但少了 `winrt-Windows.Management.Deployment` 一樣拿不到
   `PackageManager`），結果放在 `msix_backend_found`，不進 `ready`。
2. `packaging_core.missing_engine_dependencies(engine, env, lang)` 把
   「引擎 × 環境」翻成一則訊息（訊息鍵 `msix.missing_dependency`，兩種語言），
   配置精靈的 `start_pack()` 與 CLI 的 `pack` 子指令各自在驗證通過之後、
   動手之前呼叫一次。位置在工作目錄檢查之前，理由與那道檢查前移一致：
   先報真正該修的那一項。
3. 新增 `requirements.txt`，五個綁定套件在其中鎖定版本，兩個工作流程改為
   `pip install -r requirements.txt`。`tests/test_dependency_manifest.py`
   斷言工作流程不自己列套件名稱。

**為什麼偵測對象是外部直譯器，不是工具自己的行程**：安裝檔由 `builder.py`
另外呼叫的 pyinstaller 子行程編出來，`winrt-*` 能不能被收進那顆 exe，取決於
那個子行程背後的 Python 有沒有裝。工具本身是 frozen exe 時，它自己的行程裡
永遠沒有 `winrt-*`（`packaging_core.py` 不匯入 `msix_deploy.py`），以行程內
的 `import` 當判準會把每一次 MSIX 打包都誤判成缺套件。這與安裝密碼保護對
`cryptography` 的檢查不同——那份加密是在工具自己的行程裡進行的，行程內的
`import` 正是對的判準。

**不需要宣告 hidden import**：實測（2026-09-03，PyInstaller 6.18.0）確認
PyInstaller 的靜態分析會跟進函式內部的 `import`，套件已安裝時五個
`winrt-*` 連同原生 `.pyd` 都會被收進產物，無須在 `builder.py` 或
`build_config_tool.py` 補宣告。

**已知限制**：探針問的是 `shutil.which("python")` 找到的直譯器，而 `builder.py`
呼叫的是 PATH 上的 `pyinstaller`。兩者屬於同一個環境是慣例而非保證，這個
前提與既有的 `pywebview` 偵測相同，不另外處理。

完整的調查過程見
[`docs/investigations/MSIX綁定套件缺失的打包階段攔截.md`](investigations/MSIX綁定套件缺失的打包階段攔截.md)。
